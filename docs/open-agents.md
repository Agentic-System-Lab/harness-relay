# Open agents

Besides `claude`, `codex` and `grok`, Harness Relay can run five open-source coding-agent CLIs. In the code they are the "open agents" (`OPEN_PROVIDERS` in `src/shared/types.ts`):

| Provider id | CLI | Protocol | Adapter |
| --- | --- | --- | --- |
| `opencode` | OpenCode (`opencode`, npm `opencode-ai`) | ACP: `opencode acp` | `src/server/agents/opencode.ts` |
| `goose` | Goose (`goose`, Homebrew `block-goose-cli`) | ACP: `goose acp` | `src/server/agents/goose.ts` |
| `cline` | Cline (`cline`, npm `cline`) | ACP: `cline --acp` | `src/server/agents/cline.ts` |
| `openhands` | OpenHands (`openhands`, `uv tool install openhands`) | ACP: `openhands acp` | `src/server/agents/openhands.ts` |
| `pi` | Pi (`pi`, npm `@earendil-works/pi-coding-agent`) | JSONL RPC: `pi --mode rpc` | `src/server/agents/pi.ts` |

They differ from the other three in what they run on: they have no sign-in of their own in Harness Relay, and use the **model backends** set up in Settings (API keys for OpenAI, Anthropic or xAI, or the user's own OpenAI-compatible endpoint). What they share is described here; each agent has its own section at the end.

Until an agent's adapter is done (`implemented: true` in its file), its runs fail at once with "not implemented yet", before anything starts, and Settings shows it as not ready.

## Model backends

**Settings → Model backends** holds what the open agents run their models on (`src/server/backends.ts`, `ModelBackendStore`, reached as `settings.backends`):

- **API backends**: `openai`, `anthropic` and `xai`, one API key each.
- **Custom endpoints**: the user's own OpenAI-compatible servers (vLLM, Ollama, LM Studio, llama.cpp), each `{ id, name, baseUrl, models }` and an optional key. The id is a lowercase slug (`ENDPOINT_ID_RE`, never one of the API backends' names) that starts its models' ids and stays when the endpoint is renamed; `models` are the model names the user typed, since Harness Relay never asks a model API anything. The base URL is http(s), without credentials, a query or a fragment, and never Harness Relay's own address on this computer (its API's port or its dev server's), however it is spelled: `localhost` and names under it, a trailing dot, 127/8, `::1`, an IPv4 address written in IPv6, the unspecified address (`0`, `[::]`), or one of this computer's own addresses (`validEndpointUrl`).

**Keys** live in the OS credential store under the service `harness-relay`, accounts `backend-<id>-api-key` and `endpoint-<id>-api-key`, with the same rules as the CLIs' API keys ([Architecture → Providers](architecture.md#providers-status-login-and-models)): without a credential store they stay in the database and Settings says so; a key found in the database while there is one is moved into it, read back and scrubbed (with a WAL checkpoint); a store that refuses a save makes the request fail, never a silent fallback; a key that could not be read at startup is marked so it can be typed again. The UI only ever gets masked keys: `••••` and the last four characters for a key of 20 characters or more, `••••` alone for a shorter one (`maskSecret`), so a short key never shows most of itself. The endpoints themselves are rows of `model_backends` (schema version 19), which also holds an API backend's key only while it is kept in the database.

**Model ids.** An open agent's model is `<backend>/<model>`, for example `openai/gpt-5.4-nano`, `anthropic/claude-haiku-5-5`, `xai/grok-4.3` or `homelab/muse-glimmer-30b-nvfp4` (examples only: take real ids from each API or the CLI's catalog). The backend is everything before the first `/`, so a model name may hold `/` itself (`parseBackendModel()`, shared by the server and the UI).

**What a run gets.** `backendRun(o.backends, o.model, …)` gives each run its backend and model, and fails with what to do when there is no model, the id is not `<backend>/<model>`, or the backend is not set up:

- the key of the run's own API backend under the variable the CLIs read (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY` or `XAI_API_KEY`), and no other: the agent's commands inherit this environment, so a run on Anthropic never holds the OpenAI key. Every key the server holds, and every model provider's key, sign-in or address it inherited from the user's shell, is taken out first (`INHERITED_BACKEND_VARS` in `backends.ts`): OpenAI's, Anthropic's and xAI's keys, base URLs, organisation and project, `CLAUDE_CODE_OAUTH_TOKEN`, Google's (`GEMINI_API_KEY`, `GOOGLE_API_KEY`, `GOOGLE_GENERATIVE_AI_API_KEY`, `GOOGLE_APPLICATION_CREDENTIALS`, `VERTEX_API_KEY`), OpenRouter's, Mistral's, Groq's, DeepSeek's, Together's, Fireworks', Azure OpenAI's, Cohere's, Hugging Face's, Perplexity's, Cerebras', NVIDIA's, Replicate's, Voyage's, Moonshot's, DashScope's, Z.ai's, LiteLLM's, Ollama's (`OLLAMA_HOST`, `OLLAMA_API_KEY`) and Bedrock's bearer token (`AWS_BEARER_TOKEN_BEDROCK`). What is not a model backend's still reaches the agent, as it does the other CLIs: `PATH`, `HOME`, the SSH agent, `GITHUB_TOKEN`, AWS's other variables. An adapter whose CLI needs every configured key says so, and why (`allBackendKeys`); none does today;
- the endpoint (base URL, key) when the model is on one: the adapter puts its key under whatever variable its CLI's config names, never into a config file;
- the hosts the run must reach (`api.openai.com`, `api.anthropic.com`, `api.x.ai`, the endpoint's `host:port`), for the relay sandbox.

The orchestrator passes the backends to every open-agent run (`RunOptions.backends`, from `SettingsStore.backendsFor()`), and to the lead agent's and the group sorter's.

**Model menus** list the models of the CLI's own catalog whose backend is set up (the adapter's `models` hook, when its CLI has a catalog), then each endpoint's typed models; a custom id can always be typed. A member left on "default" runs on the model the menu shows as the default, as with the other CLIs: Settings' default for that CLI, else its catalog's default when that model's backend is set up (`Orchestrator.modelFor`, from `ProviderService.models`). With neither, the menu says a model is needed, and a run says to pick one.

**Status.** An open agent is ready when its CLI is installed (`--version`), its adapter is done and at least one backend is set up. There is no sign-in: the login routes answer 400 for it. The Claude subscription and Grok's sign-in cannot be used by these CLIs (Anthropic does not allow its subscription in third-party agents); Settings says so, and Claude Code and Grok themselves keep using their own sign-ins.

## Agent homes

An open agent always runs in a home of Harness Relay's own, never the user's (its `~/.config/opencode`, `~/.config/goose`, `~/.cline`, `~/.openhands`, `~/.pi`…), because Harness Relay writes its config before each run: `<agent home>/<provider>` when **Settings → Agent sessions** sets a folder, else `data/agent-homes/<provider>`. `SettingsStore.env()` names it in `HARNESS_RELAY_AGENT_HOME`, and each adapter points its CLI there with the CLI's own variables (XDG folders, its home variable) through its `home` hook, which also declares:

- `statePaths`: where the CLI writes sessions, logs and caches: writable inside the relay sandbox;
- `configPaths`: every file or folder that changes what the CLI does when it starts (config, plugins, extensions, custom providers, hooks, skills, instruction files, MCP config, permission files). The adapter's `prepare` writes them before each run, and they are read-only inside the relay sandbox, so an agent cannot widen its own next run. A single file can be listed inside a writable folder, for a CLI that writes next to it.

What the home variables do not cover (a CLI that still reads `~/.agents/skills`, or every `AGENTS.md` from the working directory up) is turned off per run with the CLI's own switches, or listed as what it loads by itself.

### Each member's own state

Everything a run can write is its own: a conversation member's sessions, logs and caches are in a folder of its own, `<home>/private/<key>`, and no open agent's sandboxed run (below full access) of another conversation or another member can read or write it, nor can any other sandboxed agent write it. Claude Code, Codex and Grok below full access can read it, as they can read each other's sessions: their sandboxes keep only the protected paths from being read ([Sandboxing](sandboxing.md#what-agents-may-not-read-or-write)). With full access there is no sandbox, as for the other CLIs (a run of one conversation had appended a fake user message to another conversation's session file, which that conversation's next answer obeyed).

- **The key** comes from the orchestrator (`RunOptions.stateKey`, `stateKeys` in `src/server/agents/types.ts`): `conv.<conversation>.<member>` for a member, the same at every turn so its session resumes; `lead.<conversation>`, `revise.<conversation>` and `sort.<conversation>` for the lead agent designing the team, changing it at the user's request, and sorting the conversation into a group. A branched conversation is another conversation, so its members start with state of their own, and fresh sessions, as before. A run without a key gets a folder of its own, removed after it.
- **Writes.** The adapter's `home(root, state)` puts every writable path (`statePaths`) inside `state`; a run below full access does not start when one is outside it. What the server keeps about a key for its later runs (Goose's extension list) is in the key's sealed folder beside it (`<home>/private/.sealed-<key>`, `sealedFolder`), which no run can read or write, emptied with the state folder. The shared parts of the home (config written for each run, the model catalog) stay under `root`, never writable by a sandboxed run.
- **Reads.** Below full access the relay sandbox keeps every open agent's `private/` folder, also those in the folders the homes were in before **Settings → Agent sessions** moved them (`openAgentRoots`, given to each run as `HARNESS_RELAY_AGENT_HOMES_BEFORE`), and the folders of each run's temp folders, from being read (`privateRoots`), but the run's own folders among them (`denyRead`, with the run's own in `allowRead`). Checked on macOS with `scripts/sandbox-check.ts --only private`: the run reads and writes its own folder, and cannot read, write or list another's.
- **Caches that load code** are in the run's temp folder or turned off (below, per agent); none is shared between members, nor kept from one run to the next unless it is the member's own.
- **A permission that went up.** A member whose CLI's latest run had a lower permission (read-only → edit → full) does not resume its session: it starts a fresh one with the whole history from Harness Relay's own record, and the orchestrator empties its state folder in that CLI's home before the run (`emptyStateFolder`; the run is told too, `freshState`), so nothing a run with less permission wrote is read with more. The record is per CLI (`agent_sessions.by_cli`): a member that ran on OpenCode in read-only, then on Goose in edit, has OpenCode's folder emptied when it is back on OpenCode in edit. It also holds the home that run was in: a turn in another home (after **Settings → Agent sessions** moved them, or back in an earlier one) starts fresh the same way, its folder there emptied, whatever the permission, since that folder may hold what an older run at a lower permission left. It is written in Harness Relay's database before the run, never in a file an agent can write, with a flag that the folder still has to be emptied (`mustEmpty`), cleared only once it has been: a turn whose folder cannot be emptied does not run and says why, and the member's next turn empties it first, even at the same permission. Emptying first renames the folder aside (`private/.gone-<random>`), which needs only `private/` to be writable, so nothing a run did inside its folder (`chmod 000` on a folder, read-only files, the immutable flag `chflags uchg` on macOS, which is cleared on the folder itself first) can keep the next run from starting with a new one; the old one is then removed best-effort, never following a link, and what a run locked stays aside until a start whose sweeps of leftover processes found nothing still running: only then are the owner's permissions given back (and the immutable flags cleared) to remove it, so a link a run planted cannot make the server change or delete anything outside `private/`. When a sweep finds a survivor or cannot tell, that start gives no permission back and keeps the relay sandbox's folders and markers, by which a later start finds it. A permission never recorded counts as read-only. When the permission goes down, the session resumes.
- **What is left.** Deleting a conversation removes its members', its lead agent's and its group sorter's state folders in every open agent's home, also in the folders the homes were in before (`removeConversationState`). At start, before any run, the server removes what runs of a server that stopped during them left: every folder in `data/run-tmp`, and the state folders of runs without a key (`private/run-*`) or set aside to be removed (`private/.gone-*`) (`clearOpenRunLeftovers`).

| Agent | The member's own state (`<home>/private/<key>`) | Caches that load code | Shared, read-only for runs |
| --- | --- | --- | --- |
| OpenCode | `data/` (its sessions database, logs, tool output), `state/` (locks) | in the run's temp folder (`XDG_CACHE_HOME`: ripgrep and LSP programs, npm plugins; Bun's install cache); Bun's transpiler cache off | its config folder, the model catalog (`cache/opencode/models.json`, refreshed outside any run) |
| Goose | `GOOSE_PATH_ROOT` and `HOME`: `data/` (sessions, its catalog cache), `state/` (logs); its `config/`, `.agents/`, `.config/`… there are written each run, read-only | none (a Rust program) | the shell wrapper (`bin/bash`) |
| Cline | `data/` (`CLINE_DATA_DIR`: sessions, SQLite, hook log; its feature-flag file written each run, read-only) | in the run's temp folder (jiti, Bun's transpiler cache) | `config/` (what the status check, the catalog and the probe read) |
| OpenHands | `conversations/` (`OPENHANDS_CONVERSATIONS_DIR`) | in the run's own home in its temp folder (removed after the run) | none |
| Pi | `sessions/` (`PI_CODING_AGENT_SESSION_DIR`) | turned off (`JITI_FS_CACHE=false`, `NODE_DISABLE_COMPILE_CACHE=1`) | none (its agent folder is the run's own, in its temp folder) |

Outside a run (status, models, what it loads by itself) a CLI's state is `<home>/private/probe`, which no sandboxed run can read or write.

**Each run has its own temp folder** (below full access the relay sandbox's `data/relay-sandbox/<id>`, with full access `data/run-tmp/<provider>-<random>`; owner-only, removed after the run), in `TMPDIR`, `TMP` and `TEMP` and writable inside the sandbox. It is in Harness Relay's data folder, which no sandbox may write, not in the system's temporary folder, which every sandbox lets commands write: caches that load code (jiti, Node's compile cache, Bun's cache, Python bytecode) are moved there or turned off by the adapter, so that no run can plant code another run then loads.

Snapshots leave the open agents' homes out, wherever they are.

## The generic ACP turn

OpenCode, Goose, Cline and OpenHands speak the [Agent Client Protocol](https://agentclientprotocol.com) on stdio, and share one turn (`src/server/agents/acpTurn.ts`), built from the logic of the Grok adapter (which stays as it is). One process runs per turn:

1. **Start.** `startOpenProcess()` (`src/server/agents/open.ts`, also used by Pi) refuses an adapter that is not done, reads the run's backend, checks the relay sandbox below full access, creates the home and the run's temp folder, lets the adapter write the CLI's config (`prepare`), and wraps the command in the relay sandbox below full access.
2. **`initialize`**, with no file system or terminal of Harness Relay's (`fs.readTextFile`, `fs.writeTextFile`, `terminal` all false). Requests an agent sends anyway (`fs/write_text_file`, `terminal/create`…) are never done for it, since that would run outside the relay sandbox: they get a "method not found" error, or the answer the adapter's `clientRequest` gives (OpenCode needs `null`).
3. **The session.** A new conversation's agent gets `session/new`. A later turn resumes with `session/resume` when the agent advertises it (`sessionCapabilities.resume`; nothing is replayed), else `session/load` (`loadSession`; the history it replays as updates before its answer is dropped, not shown again), else it fails. Any failure to resume ends the turn before anything is said, so the orchestrator starts a fresh session with the whole history, as after any failed resume.
4. **Mode, model, effort**, each as the adapter says: the session mode for the permission (`session/set_mode`), the model with `session/set_model` or `session/set_config_option` (`model`, or the option of category `model`) or in the config written before the run, the effort with `session/set_config_option` (`thought_level`) or in the config; only what differs from the session's current value is sent. `afterSession` can take over all of it, for an agent whose loaded session keeps settings it must be given again in its own order, or which takes the briefing through a method of its own.
5. **The prompt** (`session/prompt`): the role briefing goes through the CLI's own system-prompt mechanism (`briefing: 'custom'`) or before the prompt (`'prompt'`); a prompt starting with `/` gets a word before it, since agents run such text as a command of their own; attached images go along when the agent takes them.
6. **Updates → events**: `agent_message_chunk` → `text`, `agent_thought_chunk` → `thinking`, `plan` → `plan`, `tool_call` / `tool_call_update` → `tool_start` / `tool_end` (with the output, or why it failed; input that only comes with a later update is shown when the call ends), `usage_update` → the cost. `filterUpdate` lets an adapter drop, fix or hold back updates first (a system prompt sent as a thought, a failed tool reported `completed`, a message that may be the agent's notice of a failure, which `heldUpdates` hands over once the prompt answers), `hideTool` and `planOf` hide a to-do tool and take the plan from its input, and updates of subagents' sessions are not shown. When the turn ends, rows the agent never closed are closed: done after a normal end, "did not finish" after a stop or a failure.
7. **End**: the answer's `stopReason` (`cancelled` by the agent itself, with its last failed tool; `refusal`), tokens from the answer's `usage` and the cost from the last `usage_update` in USD (or the adapter's `usage`, for an agent that counts for the whole conversation). Stopping sends `session/cancel` and ends the process two seconds later; a stop that comes before the prompt (while the relay sandbox is checked, the config is written, or at any step of the session's start) ends the turn there, and the prompt is never sent. The 45-minute timeout ends the turn with "Timed out", a crash with the agent's own words (the end of its stderr). Once stdin is closed the process gets `exitGraceMs` (3 s) to exit before it is stopped.

The tool library's MCP servers go in `mcpServers` (`env` and `headers` as name/value lists; HTTP servers only when the agent advertises `mcpCapabilities.http`), or, for an agent that ignores them on `session/load`, in its config.

Every difference between the CLIs is a hook of `AcpAgentSpec` in the adapter's own file: `args`, `home`, `proxyEnv`, `emptyEnv` (variables set to empty so that a project's `.env` cannot set them), `prepare`, `initialize`, `afterInitialize`, `sessionParams`, `afterSession`, `mode`, `model`, `effort`, `briefing`, `describeCall`, `decide`, `chooseOption`, `hideTool`, `planOf`, `toolName`, `rejection`, `afterRefusal`, `clientRequest`, `mcpServers`, `filterUpdate`, `heldUpdates`, `usage`, `endTurn`, `promptText`, `updateMethods`, `exitGraceMs`, `defaultModel`, and on the process `sandbox` and `cleanup` (stops what the CLI left running, before the run's temp folder is removed). The run's own data (`ctx.state`) keeps what one hook learns for another, since parallel runs share the hooks.

## Permissions

| Relay permission | The agent's own setup | Relay sandbox |
| --- | --- | --- |
| Read-only | asks about every edit and every command; reading, searching and the web run | no writes to the working directory; writes only to the run's temp folder and the agent's `statePaths` |
| Edit | edits and commands run, except pushing and publishing (`isPublishCommand()` in `commands.ts`) and a shell or interpreter running what it reads on standard input (`… \| sh`), which ask | writes to the working directory, the attachments folder, the run's temp folder and `statePaths` |
| Full access | the agent's always-allow mode | none (as for the other CLIs) |

Each adapter configures its CLI so that it asks (most ask about little by default), and its tests prove the configured behaviour. Every `session/request_permission` goes through the same steps as Grok's:

1. **Decide** under the permission (`acpPermissionDecision`): in read-only, calls of kind `read`, `search`, `think` and `fetch` run, everything else (`edit`, `delete`, `move`, `execute`, `other`, `switch_mode`) is for the user; in edit everything runs but a command that pushes or publishes; full access allows all. Which call it is comes from its kind, title and input (`acpCallInfo`; a `command` is a shell command only for a call that runs one, and one given as an argument list is read as the command line it runs, each argument quoted where the shell would split it, so `["bash", "-lc", "git push origin main"]` asks as a push: `commandLine` in `commands.ts`), or from the adapter's `describeCall`, which also sees what the agent said of the call in earlier updates and the calls updated since the last request (for an agent whose request names no call; a refusal then shows on those calls' rows). A refusal from the adapter's own `decide` is final: the user is not asked (for a call no answer could keep bounded). Subagents' requests come through the same steps.
2. **Ask** the user (`requestApproval`: the approval card in the chat, "always allow", a note when declining), or refuse automatically when the conversation is set to (`settings.approvals = "deny"`). A tool with no command, file or URL (an MCP server's) shows what it is given: its usual fields, else its input as JSON, shortened. A request that says nothing of what it is about (no title, tool, command, file, URL or input; OpenHands' request with no call announced before it) can be allowed once only: its card has no "always allow", which would allow every such request (`noRule`). A request that comes after its turn ended (one the relay sandbox queued behind another, say) is refused without a card.
3. **Answer** with the agent's `allow_once` or `reject_once` option, never an "always" one (an agent may then stop asking, or write its own config), or as the adapter's `chooseOption` picks by id. A request still coming in when the turn is stopped, or one the user was being asked about, is answered `cancelled` (ACP's answer for a turn being cancelled), not refused, and nothing is passed on to the model.
4. **Tell the model why**, as the agent can take it: in the answer (`rejection`, such as Grok's `_meta.followup_message`), with a request of its own once the answer is sent (`afterRefusal`), or, when it can take neither, in the briefing, which then says what a rejected call means. The chat shows Harness Relay's reason and the user's note either way.

**Read-only is a boundary, not only a prompt.** In read-only an edit or a command the user allows still cannot write: the relay sandbox refuses it, and the approval card says so (`readOnlySandbox`), for any other tool too (an MCP server runs in the sandbox as well); a tool that then fails with the CLI's raw "Operation not permitted" says in the chat that Harness Relay's sandbox refused it, and why. To let an agent change files, the conversation needs edit. When the permission goes up, a member starts a fresh session, its state emptied ([Each member's own state](#each-members-own-state)).

Pi has no permission prompts of its own: a small gate extension of Harness Relay's stops each of its tool calls and asks over its RPC, so it gets the same decisions and approvals; read-only also limits its tools to reading ones. The relay sandbox stays the boundary.

## The relay sandbox

Below full access, every open-agent process, and everything it starts, runs inside Harness Relay's own sandbox (`src/server/relaySandbox.ts`, on [`@anthropic-ai/sandbox-runtime`](https://www.npmjs.com/package/@anthropic-ai/sandbox-runtime)), whatever the CLI's own sandbox does:

- **Files**: writes only where the table above says; the protected paths (the browsers' folders, Harness Relay's database and temporary folder: `protectedReads()`) neither readable nor writable; the agent's `configPaths` read-only; other reads allowed, as for the other CLIs.
- **Network**: only the hosts of the run's backend; another host is asked about (an approval of kind `fetch`) when the connection can be tied to the run, otherwise refused with a reason the model sees. Refused without asking: this computer's own addresses and link-local and metadata addresses, however they are written (`127.1`, `2130706433`, `0x7f.0.0.1`, `localhost.`: each is read as the address the proxy dials, `canonicalHost`), the hosts the adapter lists as quietly denied, and any host past the 30th asked about in one run. Harness Relay's own ports (`PORT`, 8787, 8789 and 5173: `npm start`'s and the desktop app's, and `npm run dev`'s API and Vite) are never reachable. The sandbox routes the network through a local proxy (`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`) and sets `NODE_USE_ENV_PROXY=1` itself, so Node 22's `fetch` uses it; an adapter adds what else its CLI needs (`proxyEnv`; none of the five needs any today).
- **Fail closed**: when the sandbox cannot start (no `sandbox-exec`; on Linux no `bubblewrap`, `socat` or `ripgrep`), the turn fails with how to fix it; on native Windows, where it is not ready, the open agents run only with full access, and so does OpenCode on Linux (`sandboxUnsupported`; see [OpenCode](#opencode)).

[OS sandboxes by platform](sandboxing.md) covers the CLIs' own sandboxes, and what each platform needs.

## OpenCode

`src/server/agents/opencode.ts`, checked with OpenCode 1.19.5 (npm `opencode-ai`, a Bun program).

**On Linux it runs only with full access.** There the relay sandbox gives the run a network of its own (bubblewrap's), and OpenCode's server listens on that network's loopback, which Harness Relay cannot reach from outside, so it cannot watch the server (below), and a run that cannot be watched does not run. Anything inside the sandbox that could carry the server's events out (a relay, a helper) would be the agent's commands' to reach too, so it could not be trusted either. A run below full access is refused before anything starts, saying so (`opencodeSandboxUnsupported`). Found on a DGX Spark (Ubuntu 24.04, arm64) with OpenCode 1.19.5 and sandbox-runtime 0.0.82; with full access it works there.

**Command**: `opencode acp --port <the run's port>` (ACP, JSON-RPC on stdin/stdout). For the whole turn `opencode acp` serves an HTTP API of its own on 127.0.0.1, which its ACP side works through: each run gets its own port (`freeLoopbackPort()`) and a random `OPENCODE_SERVER_PASSWORD`, without which any program on the computer could drive it. It advertises `session/resume` (nothing replayed), `session/load`, images, and stdio and HTTP MCP servers; the tool library's MCP servers go in `session/new` / `session/resume` `mcpServers`, their tools named `<server>_<tool>`.

**Home** (`<agent home>/opencode`): the four XDG folders are in it (`config`, `data`, `state`, `cache`), `OPENCODE_CONFIG_DIR` is pinned to its own config folder (an inherited one would add the user's), `OPENCODE_TEST_HOME` points at an empty folder in place of what it reads from the user's home (`~/.opencode/`, `~/.claude/CLAUDE.md`, `~/.claude/skills`, `~/.agents/skills`; the only variable that moves these without changing HOME for the commands it runs: its name says test, but 1.19.5 uses it so), `OPENCODE_AUTH_CONTENT={}` (its `auth.json` may name a URL to fetch config from), `OPENCODE_PURE=1` (no external plugins). Before every start:

- The config folder holds only the `opencode.json`, `.gitignore` and `relay-shell` (the shell its commands run in, below) Harness Relay writes, read-only (0555); anything else there (a plugin, a tool, skills, another program's config) is removed. Read-only, OpenCode neither installs `@opencode-ai/plugin` from npm into it (62 MB, and `~/.npm`) nor writes `$schema` into its files; the `.gitignore` is there already, since inside the sandbox it crashes when it cannot write one.
- Its database (`data/opencode/opencode.db`) is cleared before each run of what would widen a later one, since the sandbox lets commands write it: each session's permission rules (`session.permission`, which OpenCode puts over the agent's own for every tool call of the session, so rules a command wrote there would have the next turn of the resumed session run edits, commands and pushes without asking; Harness Relay never sets any), the saved permissions (the `permission` table, the "always" answers it never gives), and the console accounts: a planted account would make a later run (a full-access one, say) fetch and merge config from the account's server. The triggers and views a command could have planted there to put them back (an `AFTER UPDATE` trigger that writes the rules again, on the server's write or on OpenCode's own) are dropped first, and what was taken out is read back, so a column a command redefined (a generated one, say) cannot keep them. When that fails, the member's state starts over, empty, and a session it would resume is not resumed: the turn starts a fresh one.
- Each run's config is in `OPENCODE_CONFIG_CONTENT` (one home may have several runs at once): the model, only the run's backend enabled (`enabled_providers`, so the free "opencode" provider, which needs no key, and its default model never come in), the permission rules, the role briefing, and no title model (each new session would cost a call of its own).
- The run's cache (`XDG_CACHE_HOME`: the ripgrep and LSP programs it downloads, npm plugins) is in the run's temp folder; only the model catalog (`models.json`, data) is read from the home, and not refreshed during a run (`OPENCODE_DISABLE_MODELS_FETCH`). Bun's transpiler cache is off, and so are snapshots (`snapshot`, a git folder in its state that another run's commands would use).

`statePaths`: `data`, `state`, both in the member's own state folder (`XDG_DATA_HOME`, `XDG_STATE_HOME`). `configPaths`: `config`, the home stand-in, `cache` (the catalog runs read), `relay` (what Harness Relay keeps of each session's cost), in the shared home.

**Model backends**: OpenAI, Anthropic and xAI through its own providers, their keys from `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `XAI_API_KEY`; a custom endpoint as an `@ai-sdk/openai-compatible` provider named `relay-<endpoint id>` (so an endpoint called lmstudio, ollama, groq or the like never merges with a provider OpenCode knows), `baseURL` its URL, its key through the provider's `env` (the variable `HARNESS_RELAY_ENDPOINT_KEY`), never a file; its models are the endpoint's typed ones plus the run's. OpenCode fills in `{env:…}` and `{file:…}` in config text and `${…}` in a URL, so Harness Relay escapes them when it writes. 1.19.5 reads the `provider` / `npm` shape (the newer `providers` / `package` is only ignored by this version).

**Model and effort**: once the session is there, with `session/set_config_option`, in OpenCode's own order: the mode `build` (a resumed session keeps the one it had), the model (`<provider>/<model>`), the effort (one of the model's variants; changing the model resets it, so it comes last). With no effort given, OpenCode decides (a new session takes the model's first variant). An endpoint's models have no effort levels. The model menu comes from `opencode models --verbose` (dummy keys only list the API backends' models; no API is called): the models that call tools, answer in text and are not deprecated, each with its efforts.

**Permissions** (OpenCode's last matching rule wins, so `"*"` comes first):

| Relay permission | OpenCode's rules | Harness Relay's decision |
| --- | --- | --- |
| Read-only | `"*": "ask"`; `read`, `glob`, `grep`, `list`, `lsp`, `webfetch`, `websearch`, `todowrite`, `skill` allowed; `task` (subagents) denied | reading (folders outside the project too), searching and the web run; edits, commands and MCP tools go to the user |
| Edit | the same, and `edit` allowed | each command asks: pushing and publishing go to the user, the rest runs |
| Full access | `"*": "allow"` | everything allowed |

"Each command asks" is OpenCode's own decision about what counts as a command: it parses the line with tree-sitter and asks about each program it runs, so a line that holds no command — only `cd`/`pushd`, a declaration (`export X=1`, `unset X`), `(( … ))`, `[[ … ]]`, `[ … ]`, a parameter expansion (`${x}`), an array literal (`arr=(a b)`), a function header (`f() { … }`), an assignment or a comment — runs without asking (and does nothing a sandbox cares about). A command substitution inside one (`export X=$(id)`, `${x:-$(id)}`) is itself a command and does ask. Below full access only, `relay-shell` refuses, before it runs, the narrow set of forms OpenCode parses as no command but the shell still executes a command in: an `eval` as a command word, or a `$(…)`/backquote that is quoted or escaped (so OpenCode does not see it) inside a subscript or arithmetic the shell then re-evaluates (`let` included, and `$(( … ))` on a line that also holds a bracket with a `$` or backquote in it, since bash evaluates a name there again) — the single-quoted-subscript trap, `x='a[$(cmd)]'; a[x]=1` or `y=$((x+1))` — with a clear message to the model. In full access the screen is off, since every command runs without asking anyway. The screen is deliberately narrow, so some forms still run a command without OpenCode asking: zsh's `=(…)` process substitution and `(e:…:)` glob qualifier in an assignment, and an evasion that assembles `$(` entirely from pieces a declaration's name re-parses, but in read-only it cannot write (and reads are open regardless), and in edit mode commands run without asking.

Below full access its subagents are off: OpenCode only sends permission requests for the sessions ACP opened, so a subagent that had to ask would hang. When a request only says "a folder outside the project" (`external_directory`), whether it reads or writes comes from the same tool call's earlier updates; for the same call repeated three times (`doom_loop`), from that tool.

**Refusals and notes**: OpenCode ignores any reason in an ACP answer, and by default ends the turn on a refusal. So before the ACP answer goes out, Harness Relay refuses the request through OpenCode's own server (`GET /permission`, `POST /permission/<id>/reply`, with the run's password) with the reason: the model reads "The user rejected permission … with the following feedback: <reason>", the user's note included, and the turn goes on. When that cannot be done (no port, say), the model only sees OpenCode's generic rejection, which the briefing explains; `experimental.continue_loop_on_deny` keeps the turn going then. After an allowed edit it also sends `fs/write_text_file` (although `initialize` said the client cannot write): answered `null`, never done (it wrote the file itself; doing it outside the sandbox would get around it).

**Events**: its to-do list only comes as the `todowrite` tool's input (`rawInput.todos`), shown as the plan and not as a row; what a tool call does only comes on its `in_progress` updates and is given back to the call when it ends, an `apply_patch` showing the first file it changes. A command that exits non-zero is a finished call with its output. Tokens are those of the turn's last model call; the cost `usage_update` reports is the session's total, and the turn's is that minus the total kept when the session's previous turn ended. A backend's error (a bad key, a model the endpoint does not have, an endpoint it cannot reach) says which backend answered and where to fix it.

**What it loads by itself**: Harness Relay's runs never read the project's own OpenCode config (`opencode.json`, `.opencode/`; `OPENCODE_DISABLE_PROJECT_CONFIG`): it is merged before Harness Relay's and keeps its own key order, and OpenCode's last matching rule wins, so a repository could turn an "ask" into "allow" (its `agent.build.permission` even comes after Harness Relay's rules). That also leaves out the project's AGENTS.md, which Harness Relay passes back as an instruction file, found as OpenCode finds it (from the working directory up to the repository root, the first of AGENTS.md, CLAUDE.md, CONTEXT.md that exists, each copy on the way). **Settings → OpenCode** lists:

- **Skills** (`opencode debug skill`): the project's `.claude/skills` and `.agents/skills`, and the built-in `customize-opencode`. All left out: `permission.skill: "deny"`, which turns off its skill tool and leaves the skills out of the system prompt; single ones: `permission.skill: { "<name>": "deny" }`.
- **Subagents** (`opencode agent list`): the built-in `general` and `explore`, left out all or one by one (`agent.<name>.disable`); below full access they are always off.
- **Instructions**: the project's instruction files above, which can be left out; an AGENTS.md in a subfolder is still added when it reads a file there, which has no switch.
- MCP servers, plugins, hooks: none of its own in Harness Relay's runs (only the tool library's MCP servers).
- **LSP and formatters are off** (`lsp: false`, `formatter: false`) at every permission, full access included: OpenCode starts project programs for them on its own (a read warms the LSP, which runs `node_modules/.bin/biome`, the project's `tsserver.js`…; an edit runs formatters), each with the server password and the backend key in its environment, so a single file read in a repository that ships such a binary would run it with no approval. Harness Relay surfaces neither diagnostics nor formatting, so this loses nothing; the agent still runs such a program when it chooses to, which asks (or is the user's yolo mode in full access).

**What the sandbox gives it** (`opencodeSandbox()`): `localPorts`, its own server's port only (without it `opencode acp` exits with `ServeError` before answering `initialize`); its commands reach no other local port, and never Harness Relay's. `quietlyDeniedHosts`: its catalog, `models.opencode.ai` (turned off in runs anyway). Bun reads the proxy variables itself; no PTY, Unix sockets or macOS trustd. Inside the sandbox stderr shows a harmless "Error starting FSEvents stream" (its file watcher).

**Its own server**: OpenCode has to reach its server's port, so the agent's commands can reach it too. Its password is not in the commands' environment (every command goes through `relay-shell`, read-only in its config folder, which drops `OPENCODE_SERVER_PASSWORD` before it starts the user's shell), but it can still be read from the OpenCode process's environment at start (`sysctl kern.procargs2` on macOS, `/proc/<pid>/environ` on Linux), and OpenCode has no Unix socket, per-request token or switch to turn API routes off. So below full access Harness Relay watches its server's events (`GET /global/event`) and stops the run, recording a security error in the chat, on any of: a permission request approved that Harness Relay did not allow; a session that is not the run's (or a subagent of it) created or set to work; permission rules set on the run's session; a terminal (PTY) opened; a command that ran without OpenCode asking about it (the un-asked check mirrors OpenCode's own tree-sitter decision, so a cd-only line, a declaration, `(( ))`/`[[ ]]`, an assignment or a comment never trips it). The watch stays armed until the prompt answers and stops then, before the process is told to exit, so its stream closing as the process exits is not read as a problem; once the user stops a turn, only that close is expected (everything else still counts), and however else a turn ends the watch is stopped when the process is disposed. A run whose server cannot be watched does not run. What remains possible: before it is seen, one thing the sandbox allows anyway done through its server (a tool call approved by itself, a program started by an MCP server added there, a message sent to the run's own session); all of it stays inside the sandbox's file and network rules, other hosts still need the sandbox's approval, and Harness Relay's port is never reachable.

**Limitations**:

- The commands it runs see its XDG folders and the run's backend key (the only API key variable a run gets). Harness Relay sets the GitHub CLI's `GH_CONFIG_DIR` back to the user's own config so that `gh` stays signed in: this means the agent can read the GitHub token in `hosts.yml` on purpose (reads are open for every agent anyway, but here `gh` is made to work). Reaching github.com still needs the sandbox's host approval.
- Without `rg` it downloads ripgrep from GitHub into the run's cache; inside the sandbox that asks about github.com.
- Tokens count the turn's last model call only; an endpoint's models report no cost.
- When it asks about an MCP tool, the approval card cannot show the tool's arguments (OpenCode's request has none).
- Unlike some Bun CLIs, the compiled `opencode` binary does not read the project's `bunfig.toml` (a `preload`) or any `.env` variant (`.env`, `.env.local`, `.env.<NODE_ENV>`…) from the folder it starts in, so it runs no code and loads no variables from the repository at start (checked live for `opencode acp` and `opencode models`); it is started in the working directory.

## Goose

Adapter: `src/server/agents/goose.ts`, checked with Goose 1.58.1 (Homebrew `block-goose-cli`).

**Command.** `goose acp`, one process per turn, through the generic ACP turn. It advertises `loadSession` (no `session/resume`), images, embedded context and HTTP MCP servers.

**Home.** Goose's home is Harness Relay's own: `GOOSE_PATH_ROOT` points its config, data, state and `.agents` folder at the member's own state folder (`<agent home>/goose/private/<key>`: it moves them together), and so does `HOME`, since Goose still finds skills and recipes through `$HOME` (`~/.agents/skills`, `~/.claude/skills`, `~/.config/agents/skills`, `~/.goose/recipes`). Its shell commands get the user's own `HOME` back: Harness Relay gives it a small wrapper as its shell (`GOOSE_SHELL` → `<home>/bin/bash`, which sets `HOME` and runs bash), so git, rustup, nvm and the like keep working. So Goose's commands can read the user's real home, as every agent's can: reads are open for all of them, only the protected paths are refused, and below full access the network block of the relay sandbox is the boundary. The keyring is off (`GOOSE_DISABLE_KEYRING`; keys come from the environment only, so the macOS Keychain is never asked), and so are telemetry and session naming (an extra model call per new session). `/etc/goose/config.yaml`, a system-wide layer Goose reads first, cannot be moved.
- `statePaths`: `data/` (sessions in SQLite, its model catalog cache) and `state/` (logs, and `llm_request.*.jsonl`, full copies of its last model requests).
- `configPaths`: `config/` (`config.yaml`, an empty `permission.yaml`, `custom_providers/`), `.agents/`, `.config/`, `.claude/`, `.goose/`, in that folder and written before each run, and `bin/` (the shell wrapper) in the shared home. Before each run they are emptied of anything Harness Relay did not write there (a plugin, a skill, a recipe, a hints file a full-access run left), so a member's later read-only run cannot load what an earlier one planted.

Goose reads `config.yaml` again on every access and takes any config key from its upper-case variable first, so everything a run decides goes in variables, never in the shared file (parallel runs would race): `GOOSE_PROVIDER`, `GOOSE_MODEL`, `GOOSE_MODE`, `EXTENSIONS`, `PLUGINS`, `CONTEXT_FILE_NAMES`. Variables the server inherited that would change what Goose does (every `GOOSE_*`, `OPENAI_HOST`, `ANTHROPIC_HOST`, `XAI_HOST`, `EXTENSIONS`…) are taken out first, and so is every tracing variable Goose reads (`OTEL_*`, such as `OTEL_EXPORTER_OTLP_ENDPOINT`, and `LANGFUSE_*`), which would send the turn's prompts and replies elsewhere. `config.yaml` holds only what never differs between runs.

**Model backends.** `openai`, `anthropic` and `xai` are Goose's own providers, with the key from `OPENAI_API_KEY`, `ANTHROPIC_API_KEY` or `XAI_API_KEY` (OpenAI goes through its Responses API). Each custom endpoint is a provider file `config/custom_providers/relay-<id>.json` (`engine: openai`, its base URL, its typed models), its key in `HARNESS_RELAY_ENDPOINT_<ID>_API_KEY`, never in the file. A new session takes the provider and model from the variables; a loaded session keeps its own, so after every `session/load` Harness Relay sets them again with `session/set_config_option`, in Goose's order: `provider` (which resets the model to the provider's default), `model`, `thinking_effort` (`off`, `low`, `medium`, `high`, `max`; a custom endpoint offers only `off`, and then runs with it), then the mode. The model menu comes from Goose's own catalog (`_goose/unstable/providers/list`, no key needed), filtered to the configured backends, then each endpoint's models. A wrong key, an unknown model and an endpoint Goose cannot reach end the turn with a plain message saying which.

**Permissions.**

| Relay permission | Goose |
| --- | --- |
| Read-only | `approve` mode: Goose asks about every tool call. Reading tools (`tree`, `analyze`, `load_skill`, `load`, `read_image` of a file), subagents (`delegate` without a source: their own calls are asked about one by one) and its todo notes run; a `delegate` that names a source (a recipe or agent, the project's own among them) or resumes a subagent asks, since a source starts the extensions it declares, commands included. So do shell commands that only read, since Goose has no tool that reads a file and reads with its shell: no word bash would rewrite before the program sees it (no `$` outside single quotes, so no variable, `$'…'` or `$"…"`; no unquoted `*`, `?`, `[`, `{`, `~`, `#`, `(` or `)`, so no subshell, `((…))` or `[[…]]`), no redirection; each command starting with a reading program's own name (`cat`, `ls`, `rg`, `grep`, `find`, `sort`, `head`…; not `./cat`, and not behind `xargs`, `env`, `timeout`, `nohup`, `eval`, a shell, or a variable set on the line); and each of its options on that program's allowlist (none that writes a file, runs another program or sets a variable: `printf` takes no option, since `printf -v` assigns one; not `sort -o` or `--compress-program`, `find -exec` or `-delete`, `rg --pre` or `-z`, `tree -o`, `tail -f`; git not at all, since a repository's own config can make its read commands run programs). Every edit and every other command goes to the user. |
| Edit | `approve` mode: everything runs but a command that pushes or publishes, which goes to the user. |
| Full access | `auto` mode: Goose asks about nothing. |

The mode is set explicitly every turn (`session/set_mode`), since a loaded session keeps the mode it had. `permission.yaml` is written empty before each run, so no rule of its own lets a call past Harness Relay. Only `allow_once` or `reject_once` is ever answered: Goose writes `permission.yaml` for the "always" options, and `smart_approve` would write it on every model call (with its folder read-only, Goose then panics and the turn hangs), so neither is used. Goose ignores a reason sent with the answer (`_meta.followup_message`): it tells its model only that the user declined, and to stop. So once a refusal is answered, Harness Relay sends its reason and the user's note into the running turn with `_goose/unstable/session/steer`, as a user message; the model reads it right after the declined call and goes on. Subagents' calls are asked about under the parent session.

**Briefing.** `_goose/unstable/session/system-prompt/set` (append, key `harness-relay`), sent every turn so a loaded session's earlier one is replaced; it also says how Harness Relay shows Goose's todo notes.

**Events.** Goose's tool calls carry no ACP `kind`, so what a call is comes from its tool's name (`_meta.goose.toolCall.toolName`, or the title's first part for a subagent's): `shell`, `write`, `edit`, `tree`, `analyze`, `read_image`, `load_skill`, `load`, `delegate`, `<extension>__<tool>`. Rows show the command or path; an edit's row says what changed (Goose sends no diff); a command that exits with an error is a failed row. The `todo` extension's notes are shown as the plan (`- [ ]`, `- [~]`, `- [x]` and plain list items), not as a row; Goose sends no ACP `plan`. Thinking comes as `agent_thought_chunk` (Anthropic, xAI, and a reasoning model on an endpoint). A cancelled call gets no update from Goose; its row is closed as not finished. Tokens are those of the turn's last model call; Goose's cost is the session's total, so a turn's cost is what it added (the total is kept between turns in `relay-cost/` of the shared home, which Harness Relay writes and no sandboxed run may, so the agent cannot change what its turns are said to cost; a custom endpoint has none).

**Extensions.** Each run has `developer` (shell, write, edit, tree, read_image), `analyze`, `summon` (subagents) and `todo`, through `EXTENSIONS`. `apps`, `extensionmanager` (which would let the model turn on other extensions, such as computer control), `scheduler`, `tom`, `chatrecall`, `summarize` and `code_execution` are off. The tool library's MCP servers go in `mcpServers` (stdio and HTTP); a session keeps its extension list when it is loaded, with the tool library's servers added. Goose keeps that list in the session's row of its database (`sessions.extension_data`), in the member's state folder, which the run's commands may write, and starts every extension in it when the session is loaded, a stdio one's command included, without asking; it ignores a list sent with `session/load` (checked with 1.58.1). So right after `session/new`, before the prompt, Harness Relay seals the list Goose made in the key's sealed folder (`private/.sealed-<key>`, which no run can read or write), and before a run resumes the session it puts that list back in the row (`restoreGooseSession`). Before every run, the triggers and views a command could have planted in that database are dropped first (one could write the planted list back once the row is put right, or change a new session's row before it is sealed), and the row is read back once written. Without one (a session started before this), only the session's own platform extensions are kept: the tool library's servers come back with the load, a plugin's MCP servers in a new session. It also clears what Harness Relay never sets there (`recipe_json`, `user_recipe_values_json`, `system_prompt_override`, `system_prompt_extras_json`, whose briefing is set again after the load, and `container_id`). When the row cannot be checked, the member's state starts over, empty, and the turn starts a fresh session. Checked in the relay sandbox on Linux too (DGX Spark): a run's own command wrote a stdio extension into the row, and the run that resumed the session did not start it. (Goose may start it within the run that planted it, which gains nothing: it runs with the same sandbox and permission as the command that wrote it.) A stdio server runs with Goose's environment, whose `HOME` is the member's state folder, so it gets the user's real `HOME` back, as the shell does; in the relay sandbox, where neither home is writable, the caches `npx`, `uvx` and `pip` write (`npm_config_cache`, `XDG_CACHE_HOME`, `UV_CACHE_DIR`, `PIP_CACHE_DIR`) go in the run's temp folder. What the tool library sets for a server wins.

**What it loads by itself** (Settings → Goose; asked with `_goose/unstable/sources/list` and by reading the folders it reads):
- **Instructions**: `.goosehints` and `AGENTS.md` from the working directory up to the repository root, and Goose's own in its home (not `CLAUDE.md`). Left out per run with `CONTEXT_FILE_NAMES` (all of them).
- **Plugins**: each folder in the project's `.agents/plugins/` (and its home's), with its hooks (`hooks/hooks.json`), skills and MCP servers (`.mcp.json`), on by default. Left out all at once or one by one (`PLUGINS`, by folder); a plugin's MCP servers from a new conversation on.
- **MCP servers** it starts by itself (plugins'): left out with the whole extension list of a new session (`_meta.enabledExtensions`: the extensions above and the tool library's servers only); a loaded session keeps the list it started with.
- **Skills**: the project's `.goose/skills`, `.claude/skills` and `.agents/skills`, its home's, and two built-in ones. Goose has no switch for them: they always load (the user's own `~/.claude/skills` and the like do not, since its home is Harness Relay's).
- **Recipes and agents**: the project's `.goose/recipes`, `.agents/recipes`, `.agents/agents` and `.claude/agents` (and `GOOSE_RECIPE_PATH`, taken out), which the model can `load` or `delegate` to. Goose has no switch for the project's: they are always found. A recipe can declare extensions, a command among them, which a `delegate` to it starts: in read-only such a `delegate` asks; in edit it runs, as a command would.

**The relay sandbox** (below full access). Writable: `data/`, `state/` and the run's temp folder (below full access the sandbox's own, `data/relay-sandbox/<hex>`, in `TMPDIR`; with full access `data/run-tmp/goose-<random>`), and in edit mode the working directory and attachments; `configPaths` read-only. Rust's reqwest takes the sandbox's proxy as it is. What Goose asks for (`gooseSandbox()`):
- `allowTlsTrustd` (macOS) when the run talks HTTPS (an API backend, an HTTPS endpoint or an HTTPS MCP server): Goose verifies certificates through the macOS Security framework (rustls-platform-verifier), which needs `com.apple.trustd.agent`; without it every HTTPS request fails ("invalid peer certificate: OSStatus -26276"), and neither `GOOSE_CA_CERT_PATH` nor `SSL_CERT_FILE` avoids it. This opens that one service, a possible way to carry a little data out (see [Harness Relay's own sandbox](sandboxing.md#harness-relays-own-sandbox)). A plain-HTTP endpoint does without.
- `quietlyDeniedHosts`: `models.dev` (its model catalog, fetched at every start, with no switch to turn it off), `api.osv.dev` (a malware check before an `npx` / `uvx` MCP server starts, which lets the server start when it fails) and `us.i.posthog.com` (telemetry, off anyway).
- `connectPorts`: the ports of the tool library's HTTP MCP servers on this computer, which Goose reaches through the proxy; connect only: the sandbox may not listen on them, so no command can take over the port of a server that is down.

**Limitations.**
- Read-only allows plain reading commands without asking (above); the sandbox keeps the folder unwritable whatever runs.
- Its shell commands run with the user's real `HOME` (`GOOSE_SHELL`: a fixed wrapper script that takes that home and the user's bash from `HARNESS_RELAY_USER_HOME` and `HARNESS_RELAY_GOOSE_BASH`, then removes them), so they can read the user's home, as any agent's commands can; the network block is the boundary.
- Skills and the project's recipes and agents cannot be left out; a loaded session keeps the extensions and plugin MCP servers it started with.
- A refusal's reason reaches the model as a user message of the turn (steer), after Goose's own "declined, stop".
- On macOS with an HTTPS backend, the trustd service is open (above).
- `/etc/goose/config.yaml`, if an administrator wrote one, still applies.

## Cline

Checked with `cline` 3.0.74 (npm `cline`; its source at the tag `cli-v3.0.74`), on macOS with each backend. Adapter: `src/server/agents/cline.ts`; `test/cline.test.ts` replays messages recorded from the real CLI (`test/fixtures/cline/`).

**Command.** `cline --acp`, ACP on stdio; `--auto-approve true` with full access; `--thinking none|low|medium|high|xhigh` for the effort (its only effort setting: without it a turn runs with thinking off). The `cline` on `PATH` is a small Node launcher that starts the Bun-compiled CLI next to it. `-P`, `-m`, `-s`, `--config` and `--data-dir` do nothing with `--acp`.

**Where it starts.** Bun, which Cline runs on, reads by itself the `.env`, `.env.local`, `.env.development` (`.env.<NODE_ENV>`, and its `.local`) and `bunfig.toml` (whose `preload` runs code) of the folder it starts in; not those of a parent folder, nor `~/.bunfig.toml` (checked). A project's `.env` could so set Cline's own variables (where it reads its rules, its plugins' bootstrap, its JavaScript runtime…), and its `bunfig.toml` could run code before anything is asked. So Cline starts in the run's own temp folder (`processCwd`), while its session is the project: its tools, rules and `AGENTS.md`, relative paths and `git` work in the project as before (checked, also in the relay sandbox, with a planted `.env`, `.env.local`, `.env.development` and `bunfig.toml`: none was read, and none ran). The native probe also starts in an empty folder of its own, about the project (`--cwd`); the tool library's stdio MCP servers start in the working directory, as with the other CLIs. Every `CLINE_*` variable of the server's environment besides those of its home is taken out (it reads about a hundred).

**Its home** (`<agent home>/cline`):

- `data/` (`CLINE_DATA_DIR`), in the member's own state folder (`<agent home>/cline/private/<key>/data`): its sessions (`sessions/<id>/<id>.json`, `<id>.messages.json`), SQLite (`db/`), hook log and caches: the state, writable in the sandbox.
- `config/` (`CLINE_DIR`, and the settings files the status check, the catalog and the probe read) and `data/cache/feature-flags.json` (written fresh before each run): read-only.
- Each run gets a `CLINE_DIR` of its own in its temp folder, with `rules/harness-relay-briefing.md` (the briefing), `global-settings.json`, `mcp.json` and `providers.json` (named by `CLINE_GLOBAL_SETTINGS_PATH`, `CLINE_MCP_SETTINGS_PATH`, `CLINE_PROVIDER_SETTINGS_PATH`): read-only in the sandbox, removed with the folder. Parallel runs never share a briefing or settings, and sessions still resume from `data/`.
- `CLINE_SESSION_BACKEND_MODE=local`: otherwise its runtime joins a running Cline "hub" (the user's own, on port 25463) or starts one in the background that outlives the run. `E2E_TEST=true`: its feature flags, fetched from data.cline.bot even with telemetry off, become a no-op. `CLINE_NO_AUTO_UPDATE=1`. `BUN_RUNTIME_TRANSPILER_CACHE_PATH` in the run's temp folder (Bun's cache of the plugins it loads; jiti's goes to `TMPDIR`). Its variables that would move its data, swap its program (`CLINE_BIN_PATH`), replay or record requests (`CLINE_VCR`, `CLINE_CAPTURE_*`), add hooks (`CLINE_HOOKS_DIR`) or point it at a hub are set empty, and any other `CLINE_*` the server has is taken out.
- **Telemetry**: the published build sends OpenTelemetry to otel.cline.bot directly, past any proxy. `"telemetryOptOut": true` in its global settings, written for every start, turns it off (checked: no connection to it afterwards).
- **`cli-node-extra-ca-certs.pem`**: at every start, `cline --version` included, the Node launcher writes the OS's trusted certificates into `CLINE_DIR`, which is `~/.cline` when the variable is not set. It writes nowhere outside `CLINE_DIR`. A `~/.cline/cli-node-extra-ca-certs.pem` that appeared on the machine this was built on came from a version check made before the adapter set `CLINE_DIR`; Harness Relay now sets it for every start (status check, catalog, probe, runs), so Cline never writes in `~/.cline`.
- `HOME` is left as it is, so the agent's commands keep the user's git and ssh setup. Cline therefore still reads `~/.agents/AGENTS.md`, `~/.agents/skills`, `~/.agents/plugins`, `~/Documents/Cline/{Rules,Workflows,Hooks,Plugins}` and `~/Cline/Rules` (see what it loads by itself).

**Model backends.** One provider per run, in `CLINE_PROVIDER`: `openai-native`, `anthropic`, `xai`, or `openai-compatible` for an endpoint, whose `baseUrl` goes into the run's `providers.json` (never a key). The key is `CLINE_API_KEY`, which Cline sends to that provider; an endpoint without a key gets a placeholder, since Cline's ACP refuses to start a session without one. The backends' own `OPENAI_API_KEY`, `ANTHROPIC_API_KEY` and `XAI_API_KEY` are taken out of its environment. Nothing goes to Cline's own account: `authenticate` is never called, and it looks up organisations only for its own providers. The model is set with `session/set_config_option` (`model`): `CLINE_MODEL` (set too) counts only for a model in Cline's catalog, and any other would silently become the provider's default. A model or backend changed between turns takes effect in the resumed session. **Catalog**: `session/new` for each API backend, with a placeholder key (nothing is sent anywhere), as `<backend>/<model>`; the default is the one of the first API backend with a key.

**Permissions.** Over ACP Cline asks about every tool call, reading included (its ACP sessions have `toolPolicies: {"*": {autoApprove: false}}`), so the generic decision applies as it is: read-only runs `read_files`, `search_codebase`, `fetch_web_content` and `skills` (which only reads a skill's instructions) and asks about the rest; edit asks only about pushing and publishing (each command of a `run_commands` call, one per line); full access is `--auto-approve true`. The session always stays in `act`: Cline's `session/set_mode` does not reach a session `session/load` started, so its plan mode would hold for new sessions only. Its tools: `read_files`, `search_codebase`, `run_commands`, `fetch_web_content`, `editor` (or `apply_patch` for OpenAI models: an edit, whose patch names the files), `skills`, `spawn_agent` (whose subagents ask too), and the MCP servers' tools as `<server>__<tool>`. A provider's own web search (OpenAI's) runs on the provider's side, without asking.

- Its options are `allow_once`, `allow_always` (which it treats as once) and `reject_once`. **A refusal reaches its model only as Cline's own fixed text** ("User rejected the tool call…"): it ignores anything else in the answer, so the user's note is shown in the chat only, and the briefing says what a refused call means.
- Stopped while it waits for an answer, Cline does not end the turn until the request is answered: the adapter answers it `cancelled` at once.

**Briefing.** A rules file in the run's own `CLINE_DIR/rules`, read at every start, so a resumed session takes a changed briefing too. Cline reads no `_meta`, and `-s` does nothing with `--acp`.

**Tool library.** Its MCP servers go into the run's MCP settings file (stdio: `command`, `args`, `env`; HTTP: `type: "streamableHttp"`, `url`, `headers`), since Cline ignores the `mcpServers` of `session/new` and `session/load`. Skills come through the briefing, as for every agent.

**Events.** Text and thinking chunks; no plan or to-do events (it has no to-do tool over ACP). Its tool updates are put right before the generic turn reads them (`filterUpdate`): a call it asks about comes first as a `tool_call_update` (its row starts there) and again as a `tool_call` after the answer; the output is in `rawOutput` (a list of `{query, result, success, error}`, an MCP result, a provider's search), not `content`; a failed command or edit often comes `completed` with `success: false`, and is shown as failed. It advertises images but takes only a prompt's text (an attached image's path is in the prompt, and its file reader opens it). Usage is not in ACP: the turn's tokens and cost are what its session record (`data/sessions/<id>/<id>.json`, written as the turn ends) gained in the turn; an endpoint's turns have no cost.

**Resume.** `session/load` (it advertises `loadSession`, not `resume`); an unknown session is `-32002 Resource not found`, and the orchestrator starts a fresh one with the history.

**Errors.** A refused key, a model the backend does not have and an endpoint it cannot reach each get a message that says what to do, with the provider's own words.

**What it loads by itself**, asked with `cline config <kind> --json` for rules, skills, hooks, agents and plugins (they only read files; `cline config --json` alone is not used: it builds Cline's runtime in "auto" mode, which joins a running hub or starts one). Below full access hooks and plugins run inside the relay sandbox; with full access they run as the user.

- Instructions: the project's `AGENTS.md`, `.clinerules` (a file or a folder) and `.cline/rules`; `~/.agents/AGENTS.md`, `~/Documents/Cline/Rules`, `~/Cline/Rules` (no `CLAUDE.md`). No switch.
- Skills: the project's `.clinerules/skills`, `.cline/skills`, `.claude/skills` and `.agents/skills`, and `~/.agents/skills`. **Left out all at once** by turning off its `skills` tool (`disabledTools`). `cline config skills` lists them anyway, so the probe marks what the run's switches leave out itself (skills, single tools and plugins: `leftOut`, with `asRun`).
- Hooks (`TaskStart`, `PreToolUse`… scripts in `.clinerules/hooks`, `.cline/hooks`, `~/Documents/Cline/Hooks`): they run, without asking. No switch.
- Plugins (JavaScript or TypeScript in `.cline/plugins`, `~/Documents/Cline/Plugins`, `~/.agents/plugins`): their code runs when a session starts. **Left out one by one**, by path (`disabledPlugins`).
- Built-in tools: **left out one by one**, by name (`disabledTools`).
- Workflows (slash commands) are not listed: Harness Relay's prompts never start with `/`.

**Sandbox needs.** Writable: `data/` and the run's temp folder; read-only: `config/`, `data/cache/feature-flags.json` and the run's own `CLINE_DIR`. Its one opt-in is `quietlyDeniedHosts`: otel.cline.bot, data.cline.bot and api.cline.bot, its own services, which are off in every run, so they are refused without an approval card if it still tries. No loopback port (no hub), no PTY, no Unix socket, no macOS trustd: Cline runs on Bun, whose TLS goes through the sandbox's proxy with its own certificate list (the launcher's look at the OS trust store fails in the sandbox and prints "failed to copy trust settings", harmlessly). Checked on macOS with every backend, in read-only and edit: the agent works; writes outside the allowed folders fail; another host is asked about; Cline's own hosts are refused quietly; the protected paths and Harness Relay's port cannot be reached; Cline itself is gone after the turn, and so is the run's temp folder. Cline adds loopback to `NO_PROXY` by itself whenever a proxy is set, so an endpoint on this computer (Ollama, LM Studio) is reached around the proxy: allowed directly on macOS and relayed onto the sandbox's own loopback on Linux ([Sandboxing](sandboxing.md#harness-relays-own-sandbox)). Without that it could not reach such an endpoint below full access on either system. As for Claude Code, Codex and Grok, Harness Relay stops the process tree of the turn when it ends; a process that a command or a project hook detaches from that tree (`nohup … &`, `setsid`) is outside it, and with full access, where there is no sandbox, it keeps running. Checked on Linux too (DGX Spark, arm64), with an endpoint on loopback.

**Limitations.** A declined note does not reach its model; plan mode is not used; the effort is set per process (`--thinking`), not per session; images go as their paths; its session record keeps the model the session started with (`model`), though each turn uses the one set; the project's hooks, rules and workflows have no switch, plugins only one by one.

## OpenHands

`openhands acp` (PyPI `openhands`, installed with `uv tool install openhands`; built and checked with 1.16.0, which brings openhands-sdk 1.21.0 and LiteLLM 1.108.4), in `src/server/agents/openhands.ts`. One process per turn, through the generic ACP turn. OpenHands never exits when its stdin closes, so it is stopped as soon as the turn is over (`exitGraceMs: 0`); it takes about 2.5 s to start and answer `initialize`.

**Its home.** OpenHands' settings are a whole serialized agent (`agent_settings.json`), and only those, `mcp.json` and its sessions follow `OPENHANDS_PERSISTENCE_DIR`; its skills, hooks, subagents and caches follow `HOME`. So each run gets a home of its own inside the run's temp folder (`data/run-tmp/openhands-<random>` with full access, the relay sandbox's `data/relay-sandbox/<id>` below it; `HOME`, `OPENHANDS_PERSISTENCE_DIR`, and `PERSISTENCE_DIR`, which its `cli_config.json` reads), written before the run and removed after it, and only the sessions are kept, in the member's own state folder (`OPENHANDS_CONVERSATIONS_DIR` = `<agent home>/openhands/private/<key>/conversations`, its `statePaths`). Members on different models can run at once without changing each other's settings. In the run's home Harness Relay writes, read-only inside the relay sandbox (`configPaths`): `agent_settings.json`, `mcp.json`, the briefing as a skill, a placeholder that turns off its public skills, and `.bashrc` (below).

**Variables.** OpenHands loads the `.env` of the folder it starts in into its environment, for every variable not set already, and its terminal (`bash -i`) gets that environment as it is: a project's `PROMPT_COMMAND` (or `PS0`, or `LD_PRELOAD` on Linux) would run at every turn's start, before any approval. So it starts in the run's temp folder (`processCwd`), where there is none; the session's folder is still the project (`session/new`'s `cwd` and `OPENHANDS_WORK_DIR`), where its tools, its terminal and the project's skills, hooks and `AGENTS.md` are (checked live: `pwd` is the project, a project `.env`'s `PROMPT_COMMAND` and variables do not reach its commands, `AGENTS.md` still applies). `LITELLM_MODE=PRODUCTION` stops LiteLLM loading the first `.env` above its own install folder (`~/.env`, say). A project's `.env` now reaches only a program that reads it itself (the project's own code, run as a command). Every variable the adapter relies on is set for each run all the same (the folders above, `OPENHANDS_WORK_DIR` = the working directory, `TMUX_TMPDIR` with full access, `OPENHANDS_SUPPRESS_BANNER=1`, LiteLLM's `LITELLM_LOCAL_*` switches to its bundled copies, the XDG folders), and the ones that would send a key elsewhere or turn on tracing are set empty (`emptyEnv`: `OPENAI_BASE_URL`, `ANTHROPIC_BASE_URL`, `XAI_API_BASE`, `LMNR_PROJECT_API_KEY`, `OTEL_*`, `LLM_API_KEY` / `LLM_MODEL` / `LLM_BASE_URL`, `DEBUG`, `LOG_TO_FILE`…: every base URL LiteLLM and the OpenAI and Anthropic SDKs read for OpenAI, OpenAI-compatible endpoints, Anthropic and xAI, `OPENAI_BASE_URL`, `OPENAI_API_BASE`, `ANTHROPIC_API_BASE` (read before `ANTHROPIC_BASE_URL`), `ANTHROPIC_BASE_URL`, `XAI_API_BASE`, Azure's, and LiteLLM's proxy and gateway URLs; with full access the proxy variables too, which below full access the sandbox sets). Its terminal's shell sources the run's `.bashrc`, which gives commands the user's own `HOME` and XDG folders back.

**Model backends.** The model is chosen in `agent_settings.json` only (ACP's `session/set_model` is missing, `session/set_config_option` does nothing), as a LiteLLM name: `openai/<model>`, `anthropic/<model>`, `xai/<model>`; an endpoint as `openai/<model>` with its `base_url`, its key under `OPENAI_API_KEY` for that run (`no-key` when it has none). No key is written to the file: LiteLLM reads `OPENAI_API_KEY`, `ANTHROPIC_API_KEY` and `XAI_API_KEY`. The file is read at every start, so a member's model can change between turns of the same session, even to another backend. Retries are cut to 2 (OpenHands' default retries an unreachable backend for minutes). The **effort** is its `reasoning_effort` (`low`, `medium`, `high`, `xhigh`), written when one is chosen unless LiteLLM's model information says the model does not reason (a model it has no information on, such as an endpoint's, gets the effort chosen, and one that refuses it fails the turn with what to set instead); at `none` or when none is chosen nothing is sent (OpenHands' own default would send `high`, which some models refuse); for Claude Sonnet 4.5 / 4.6 and Haiku 4.5, which OpenHands gives extended thinking, also a thinking budget (2 048 to 64 000 tokens). The menu offers each model only the efforts LiteLLM says it takes (none for a model that does not reason, `xhigh` only where it says so). xAI refuses an effort for several models LiteLLM marks as reasoning (grok-code-fast-1, the grok-4.20 models, grok-build): such a turn fails with what to set instead (`none`). The **model menu** is LiteLLM's own list from the OpenHands install (`litellm/model_prices_and_context_window_backup.json`, found from the `openhands` program's `#!` line; nothing is run or fetched): OpenAI, Anthropic and xAI chat models that call tools, without fine-tune templates, audio or search models, nor dated snapshots of a listed model, by family with the newest first, each with its efforts.

**Permissions.** It runs in its own `always-ask` mode below full access (every action asks except `think` and `finish`) and in `always-approve` with full access (`session/set_mode`). Its permission request names no action (`confirmation-<session>`, kind `other`): the decision is made about the actions it holds waiting, read from the session's own log when the request comes (OpenHands stores each action in `conversations/<id>/events` before it announces it and asks), which are the tool calls it announced just before (`describeCall`); when they are not exactly those calls (an update that came late, a log changed by something else), the request is asked about whatever the permission. Of those calls, `file_editor view` and `task_tracker` count as reading, `invoke_skill` as `other` (invoking a skill runs the shell commands its `SKILL.md` holds inline, `!` followed by a command in backticks), its other `file_editor` commands as edits, `terminal` as a command, MCP tools as `other`; an MCP tool's card names the tool (from the session's log: its update names only the model's summary of the call) and shows its input as compact JSON, and **always allow** goes by the tool. A request covering several calls (a model that calls tools in parallel) lets them all run with one answer, so it runs without asking only when the permission covers every one of them; otherwise the card lists them all and is keyed for **always allow** by all of them (all their commands, one per line; all their files, one per line, for edits; or, for calls of different kinds, the whole list, which only the same calls match again). When the conversation refuses such a request by itself, each call's row says why: its own reason, or that it was refused along with the rest of its batch. A request with no call announced before it (as for an action an earlier turn left waiting) is never allowed by itself: it is asked about, or refused when the conversation refuses. It is answered with its own option ids `accept` or `reject`, never `always_proceed` (which would stop it asking) or `risk_based`.

- **Subagents** (its `task` tool, and the older `delegate`) run their own commands and edits without asking once started, so below full access the tool is taken out of its tools (`filter_tools_regex`), and refused without asking the user (`decide`) if one still comes. With full access they are there.
- **Refusals**: OpenHands passes the model only its own fixed words ("User rejected the action. Please ask the user how they want to proceed."), never Harness Relay's reason or the user's note; the briefing says what a refused call means, and the chat row shows Harness Relay's reason and the note.

**Briefing.** A skill without triggers in the run's home (`skills/harness-relay-briefing.md`), which OpenHands puts in its system prompt (in its repository-context block). Its system prompt is kept in the session when it starts, so when the briefing has changed since (another permission, another team), a resumed session gets the new one before the prompt too.

**Tool library.** Its MCP servers go into the run's `mcp.json` (stdio and HTTP), for new and resumed sessions alike: `session/load` ignores ACP's `mcpServers`.

**Sessions.** Resumed with `session/load` (it advertises no `session/resume`); its replay of the history is dropped. An unknown session id would "load" as a new empty session, so a missing `conversations/<id>/base_state.json` fails the turn before OpenHands starts, and the orchestrator starts afresh with the whole history. **Actions an earlier turn left** (a command running when the turn was stopped, or an approval left waiting when the server went down) would run before anything else on resume, without asking and without a row (OpenHands' "implicit confirmation" of unmatched actions): before resuming, the adapter rejects each of them as OpenHands records a rejection (a `UserRejectObservation` event after the session's last one), so they never run and the model reads that they did not; when that cannot be written, the session is not resumed and the orchestrator starts afresh. The log is read exactly as OpenHands reads it (the files named `event-<five digits>-<id>.json` from index 0 up to the first gap; from the newest back, the actions no later observation, rejection or error answers), and a log OpenHands alone would not have written is not resumed either: any other file, a gap, two files for one index, an event that JSON.parse cannot read (OpenHands' own parser takes `Infinity` and `NaN`) or that lacks its fields, or a session left waiting for a confirmation with nothing waiting.

**Events.** It does not stream: each message comes whole. The adapter drops the system prompt it sends as a thought when a session starts, its "Conversation Paused" note and the "Error: …" message it sends right before the prompt fails (a message that only looks like one, such as a reply that begins "Error: AssertionError…", is held back and shown once anything comes after it or the prompt answers); it takes its headers off thoughts (`**Reasoning**:`, `**Thought**:`), the rendering of its `finish` call and a trailing reasoning summary or list of skills off replies. A tool's result comes from its observation: its own output (without the command a plain terminal echoes, and without the terminal's control sequences: bash 5.1 and later turns bracketed paste on and off around each command, seen on Linux), failed when the observation says so (an error, a non-zero exit code, a timeout), since OpenHands reports such tools as `completed`. Its plan comes as `plan` updates; its `task_tracker` calls are not rows. Tokens and cost: OpenHands counts them for the whole session, across resumes; the turn's are what it counted at the end less what the session's `base_state.json` held before (no cost for an endpoint).

**Errors.** A refused key (401), a model the backend does not have, a rate limit, an unreachable backend (also when the relay sandbox's proxy says so: `502 Bad Gateway`, LiteLLM's `BadGatewayError`) and a terminal that cannot start are said as such, with the backend's name; anything else with OpenHands' own words, without its log-folder hint. **A stuck stop**: its stuck detector ends a turn that keeps repeating the same action or getting the same error (seen with xAI after seven identical failing calls) as an ordinary end, with nothing said; only the session's `base_state.json` says `execution_status: stuck`. Such a turn fails with what happened and what to try (ask again, put it differently, or another model; `endTurn`), and the next turn goes on in the same session.

**Its terminal, and the relay sandbox.** OpenHands runs commands in a tmux server (socket `openhands` under `TMUX_TMPDIR`) when `tmux -V` works, else in a plain pseudo-terminal; it has no other switch that works (the SDK's `terminal_type` tool parameter would be one, but the CLI replaces the tools of `agent_settings.json` with its own at `session/new`, and with the stored session's at `session/load`: with `terminal_type: "subprocess"` there, tmux still ran, checked live), and no terminal without a pseudo-terminal on macOS or Linux (its pipe-based one is Windows' PowerShell; leaving the `terminal` tool out does not help, since it starts its terminal before it filters its tools). **Below full access it never runs tmux**: a command backgrounded there (`nohup … &`) outlived the turn, since the tmux server closes the descriptors the relay sandbox finds a run's processes by, and stopping the server only hangs up on its shells, which such a command ignores. A `tmux` that fails is put first on its `PATH` (`<run temp folder>/bin/tmux`, read-only), so it runs its plain pseudo-terminal, whose commands the sandbox stops with the run. With full access tmux runs, its socket in the run's temp folder (or a short folder of its own when that path is too long for a socket), and once the turn is over its server and every process under it are killed (SIGKILL), then the server is told to stop (`cleanup`).

Below full access its pseudo-terminal needs `allowPty` (without it every turn fails at once, `fork failed`, even one with no tools); no Unix socket is opened. **On macOS** `allowPty` opens `/dev/ptmx` and every `/dev/ttys*`, so the run's commands could print text into the user's other terminal windows, read what is typed there and change their settings, such as turning echo off (checked on a pseudo-terminal of our own: writing, reading and `tcsetattr` work; `TIOCSTI`, typing into it, is refused). So there OpenHands runs below full access only when the user turns on **Settings → OpenHands → "Let OpenHands use a terminal in the sandbox: its commands can then read and write your other terminal windows"** (off by default; kept with its provider settings, `provider_settings.sandbox_terminal`, and given to each run as `RunOptions.sandboxTerminal`). Without it the turn fails before OpenHands starts, naming the switch and what it opens, or full access. **On Linux** no switch is needed: bubblewrap gives the sandbox a `/dev/pts` of its own (a new devpts instance that holds only the sandbox's own terminals; the host's are not there), and it binds a terminal on `/dev/console` only when its own output is one, which a run's never is (its output goes to pipes). Checked in Docker with bubblewrap 0.8.0 and sandbox-runtime 0.0.82, by comparing the devpts mounts and the entries of `/dev/pts` inside and outside, without opening a terminal.

Nothing is quietly denied: the fetches it would make at every start (its public skills from GitHub; LiteLLM's price list and its Anthropic beta headers, the latter on calls to Claude models with extended thinking) are turned off instead. Python's `httpx` (under LiteLLM) and `git` use the sandbox's proxy as they are.

**What it loads by itself** (Settings → its card: read from the files it reads; it has no command that lists them): `AGENTS.md`, `agent.md`, `CLAUDE.md`, `GEMINI.md` and `.cursorrules` of the working directory and its repository root, as instructions; skills in `.agents/skills`, `.openhands/skills` and `.openhands/microagents` there; subagents in `.agents/agents` and `.openhands/agents`; hooks in the working directory's `.openhands/hooks.json` (not the project's `.env`: see Variables). None of them can be left out of a run (no switch), and the hooks run shell commands on its events: inside the relay sandbox below full access, unsandboxed with full access. Nothing comes from its home, which is Harness Relay's, and its public skills (about 70 skills from `github.com/OpenHands/extensions`, fetched at every start) are always turned off: a plain file where it would clone them (`cache/skills/public-skills`). Its system prompt tells the model to use `AGENTS.md` as its memory, so it may edit that file.

**Limitations.** A declined note never reaches the model, neither in that turn nor in a later one (only OpenHands' own words do); it shows only in the chat. Cancel pauses OpenHands but does not stop a running command, so a stopped turn ends its process (and, with full access, its tmux server) after two seconds. A refused write says so on its row ("Harness Relay's sandbox refused it: this conversation is read-only."), and a refused read of a protected path says that it is one (Harness Relay's database and temporary files, browsers' data). Its file editor's `insert` command leaves the file it changed with mode 0600 (it writes a temp file and moves it over; that is OpenHands, not the adapter). Its plain pseudo-terminal (always, below full access) echoes each command, which the adapter takes off, and now and then reports a command with the previous one's exit code and no output: the row then shows a failure that did not happen. Its condenser summarises long sessions with extra calls to the same model. Image prompts, HTTP MCP servers and Linux were not tried with the real CLI (on Linux, only its sandbox's terminals were checked, in Docker).

## Pi

Adapter: `src/server/agents/pi.ts`, with its gate extension `src/server/agents/piGate.js`. Checked with Pi 1.5.1 (npm `@earendil-works/pi-coding-agent`, Node ≥ 22.19).

**Command and protocol.** One process per turn: `pi --mode rpc --model <provider>/<model> --no-extensions --no-skills --no-prompt-templates --no-themes --no-approve`, plus `-e <gate>` below full access, `-e builtin:mcp` with tool-library servers (else `--no-mcp`), `--append-system-prompt <file>` for the role briefing, `--session <file>` to resume, `--tools …` in read-only, `--thinking <level>` with an effort, and `--no-context-files` when instruction files are left out. Pi's RPC is JSONL: commands on stdin, responses and events on stdout, one JSON object per line, **LF only** as the separator (`PiLines` splits the raw bytes; a generic line reader may also split on U+2028/U+2029 or a lone CR). A turn is `get_state` (the session and model) → `get_commands` (the gate is loaded) → `get_available_thinking_levels` / `set_thinking_level` → `prompt` → events → **`agent_settled`**, the end of the turn (`agent_end` is not: retries and queued messages can follow it); then stdin is closed and Pi exits. The turn's outcome is the last assistant `message_end`: `stopReason` `error` fails the turn with its `errorMessage` put in words (a rejected key, a model the backend does not have, an endpoint it cannot reach, also when the sandbox's proxy says so: `HTTP 502` rather than undici's words), `aborted` without a stop of ours fails it too.

**Events.** `message_update` → `text` (`text_delta`, closed at `text_end`) and `thinking` (`thinking_delta`); `tool_execution_start` / `_end` → tool rows named `Read`, `Bash`, `Edit`, `Write`, `Grep`, `Find`, `List`, or `mcp__<server>__<tool>`, with the file, command or pattern, the output (an edit's numbered diff) or the failure. Usage is summed over the turn's assistant messages (input with the cached tokens, output; the cost Pi prices from its catalog for OpenAI, Anthropic and xAI, none for an endpoint or a model it does not know). Pi has no plan or to-do events. Role `system` messages (the prompt Pi sends on a session's first request) are not shown. OpenAI's reasoning summaries come as thinking when its API sends them (some turns have none).

**Approvals: the gate.** Pi has no permission prompts of its own. Below full access the gate extension, loaded from Harness Relay's own folder by its absolute path (never from the agent's home, and outside every folder the run may write: the run refuses to start otherwise), stops every tool call, MCP tools included, and asks over the RPC: an `input` dialog titled `harness-relay:tool_call` whose placeholder is the call as JSON; the adapter answers `{"allow":true}` or `{"allow":false,"reason":…}`. The decision is the same as the ACP agents' (`acpPermissionDecision` → `requestApproval` → `acpDeclined`): read-only runs reading tools and asks about the rest (MCP tools), edit runs everything but pushing and publishing, which ask. A refusal's reason, with the user's note, is the blocked call's result and names that exact call (`Bash npm publish`), so **the model sees why**, also when only one call of a batch was refused, and the turn goes on; the chat shows Harness Relay's label. An MCP tool's card shows its input (its usual fields, whole paths, else its JSON), and in read-only says that the sandbox still refuses writes the user allows. The gate fails closed: a cancelled dialog, an answer it cannot read, no client or an error block the call. It registers the command `harness-relay-gate`, which the adapter looks for before it sends the prompt: a run where the gate did not load does not start. Stopping a run sends `abort`; Pi then cancels a dialog still waiting, sends nothing about it, and the run's end expires the approval (its row keeps Pi's words, not a refusal). Read-only also limits Pi's tools to `read`, `grep`, `find`, `ls` (`grep` and `find` only when ripgrep and fd are on the PATH) and the tool library's MCP tools (`mcp__*`). Full access has no gate.

**Home.** `<agent home>/pi` keeps only the sessions, in the member's own state folder (`private/<key>/sessions/`, `PI_CODING_AGENT_SESSION_DIR`; one flat `<time>_<id>.jsonl` each). Everything Pi reads at start is written for each run into a fresh agent folder inside the run's temp folder (`PI_CODING_AGENT_DIR`): `settings.json` (no project trust, no telemetry, no cache warming), `models.json` (an endpoint, or a model Pi's catalog lacks), `mcp.json`, an empty `auth.json` and `models-store.json`, and the briefing. That folder stays writable (Pi makes `auth.json.lock` beside `auth.json` on every key lookup), while each of these files, and every other one Pi would load (`AGENTS.md`, `SYSTEM.md`, `APPEND_SYSTEM.md`, `keybindings.json`, `trust.json`, `extensions/`, `skills/`, `prompts/`, `themes/`, `bin/` where it looks for fd and ripgrep before the PATH, its package folders), is read-only in the relay sandbox. Parallel runs never share it, and nothing a run leaves there reaches the next. Every Pi process also gets `PI_OFFLINE=1` (no catalog refresh, no fd/ripgrep download), `PI_SKIP_VERSION_CHECK=1`, `PI_TELEMETRY=0`, and its code-loading caches turned off (`JITI_FS_CACHE=false` for the extension, `NODE_DISABLE_COMPILE_CACHE=1`). Outside a run (status, models) Pi points at `<agent home>/pi/agent`, never `~/.pi/agent`.

**Leaks closed with its flags.** `--no-skills`: Pi would read `$HOME/.agents/skills` whatever its home is (the tool library's skills reach it through the briefing). `--no-approve`: a project's `.pi/` folder (settings, MCP servers, extensions, skills, `SYSTEM.md`) and `.agents/skills` never load; the session folder is always set, since Pi reads a project's `sessionDir` before trust. `--no-extensions`, `--no-prompt-templates`, `--no-themes`.

**Model backends.** OpenAI, Anthropic and xAI by their keys' variables (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `XAI_API_KEY`); a model Pi's offline catalog lacks (such as a new xAI model) is added to `models.json` with its API's address, since Pi would otherwise copy its default model's settings. An endpoint is an `openai-completions` provider `relay-<id>` in `models.json` at its base URL, with its typed models, its key by variable (`$HARNESS_RELAY_ENDPOINT_API_KEY`, never in the file; a keyless endpoint gets a placeholder). The model is checked after start (`get_state`; Pi matches `--model` loosely and a resumed session keeps its own) and set again with `set_model` when it differs. **Effort** is Pi's thinking level (`off`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`), checked against `get_available_thinking_levels` before it is set, since Pi clamps a level it does not take silently (an unknown one becomes `off`). The model menu comes from Pi's catalog (`get_available_models`, offline), with each model's levels.

**Resume.** The session is found by its id in the sessions folder before Pi starts, and resumed by its file (`--session <file>`, which runs it in its own folder). A missing file (Pi would quietly start a new session) or a session of another working directory fails the resume, so the orchestrator starts afresh with the whole history; `--session <id>` is never used, since for a session of another folder Pi asks on stdin whether to fork it. After start, `get_state` must name the same session.

**What it loads by itself.** Its instruction files: `AGENTS.override.md`, `AGENTS.md` or `CLAUDE.md` (the first of them in each folder) from the working directory **up to `/`**, which may include files above the project (a parallel-mode worktree sits in Harness Relay's data folder, so Harness Relay's own `AGENTS.md` is among them). Settings lists them, and leaving out instructions passes `--no-context-files`, which leaves out all of them (Pi has no switch for one file). Nothing else of its own loads.

**Tool library.** MCP servers (stdio and streamable HTTP) go into `mcp.json` with `exposure: "direct"` (declared to the model), their secret values in variables (`${HARNESS_RELAY_MCP_<n>_<kind>_<m>}`), loaded with `-e builtin:mcp`. Only stdio servers were tried live.

**Sandbox needs.** None of the opt-ins: Pi's network goes through undici's `EnvHttpProxyAgent`, which reads the proxy variables the sandbox sets (no `NODE_USE_ENV_PROXY` needed), and a localhost or LAN endpoint goes through the proxy as the sandbox narrows `NO_PROXY`. No loopback ports of its own, PTY, Unix sockets or macOS trustd; no host to refuse quietly, since nothing Pi would fetch by itself is left on. Checked live on macOS in edit and read-only with every backend: writes outside the allowed folders, Harness Relay's database and port, its own config files and other hosts (asked about) are refused.

**Limitations.** No plan or to-do list; HTTP MCP servers not tried live; `find` needs fd and `grep` ripgrep; skills of Pi's own are never loaded (only the tool library's, through the briefing); instruction files can only be left out all together; the gate file must be shipped beside `pi.ts` (a bundled server needs it copied).
