# OS sandboxes by platform

Harness Relay starts the real `claude`, `codex`, `grok`, `cursor-agent`, `agy` (Antigravity), `copilot` (GitHub Copilot) and `muse` (Muse Code) CLIs, and each of them brings its own OS sandbox, or none (Cursor brings none to Harness Relay's runs, and Antigravity's would keep its commands from writing the working directory, so both run without one). The five open-source agents (OpenCode, Goose, Cline, OpenHands, Pi) bring none either, so Harness Relay sandboxes them itself, with [its own sandbox](#harness-relays-own-sandbox) (the same primitives: Seatbelt on macOS, bubblewrap on Linux, a filtering proxy for the network). This page says which of Harness Relay's runs use one today, on which platforms each sandbox works, what it needs there, what happens when it cannot start, and what it does not cover.

Checked on 10 November 2026, for Cursor on 11 November 2026, for Antigravity (with `agy` 1.5.6) on 12 November 2026, and for Copilot (with `copilot` 1.0.109) on 13 November 2026, and for Muse Code (with `muse` 1.4.18) on 13 November 2026. What was tried, on which systems and with which versions, is in [What was tested](#what-was-tested): a Mac (macOS 26.6) and an NVIDIA DGX Spark (Ubuntu 24.04, aarch64); Cursor on the Mac only; Antigravity and Copilot and Muse Code on both and on a Windows 11 virtual machine (arm64), Muse Code there without its sandbox's setup. Everything else, all of Windows and WSL included, comes from each CLI's own documentation (see [Sources](#sources)). The CLIs change quickly, so check again before you rely on a detail.

## What an OS sandbox is

An OS sandbox is a set of limits that the operating system's kernel enforces on a process and on every process it starts: which files it may write (and sometimes read), and whether it may use the network. macOS has Seatbelt (`/usr/bin/sandbox-exec`); Linux has Landlock, seccomp and bubblewrap (which uses user namespaces).

It works at a different point from approvals:

- An **approval** is decided *before* a command runs, from the command's text. Once a command is allowed, nothing checks what it does.
- A **sandbox** applies *while* the command runs. A write or a connection outside its limits fails (a write usually with `Operation not permitted`), also when it comes from code the agent wrote and a test then ran.

That is why the sandbox matters in edit mode too, where tests and builds run code the agent may have just changed; with Grok and Copilot that code can still reach the network, and Cursor and Antigravity have no sandbox at all in Harness Relay's runs, so there only asking keeps it in check (see [Architecture → Permission mapping](architecture.md#permission-mapping)).

Cursor runs in the first working directory: a write it asks about in another one goes to the user too, with a card that says where it is. In read-only mode its write tool can neither write nor delete (`Write(**)`, checked before Cursor would ask). Web fetch and web search run, a subagent's too. - **Antigravity** runs over ACP (`agy acp`). Its terminal sandbox lets commands write nowhere in the working directory over ACP in `agy` 1.5.6 (only in the temporary folder), so Harness Relay does not turn it on, on any platform, and relies on approvals for its commands, as for Cursor's: below full access none runs without asking, tests and builds included, and one the user allows runs outside any sandbox, with the user's full rights, network included (the card says so). - **Copilot** runs over ACP (`copilot --acp`), and below full access in its own sandbox (`--sandbox`: Seatbelt on macOS, bubblewrap on Linux, a process container on Windows). Its home (`COPILOT_HOME`, else `~/.copilot`) holds what decides what runs without asking: saved approvals (`permissions-config.json`), trusted folders (`config.json`), URL rules and the sandbox policy (`settings.json`). So each turn gets a home of its own, in Harness Relay's own temporary folder (`data/tmp/copilot-…`, owner-only, removed after the turn, and at the server's next start when the server stopped during one): a `settings.json` of Harness Relay's, which keeps of the account's own only its model and service, its proxy, whether it syncs its sessions to GitHub (`remoteExport`) and updates itself (`autoUpdate`, `autoUpdatesChannel`), and what it loads by itself (never its `sandbox`, `allowedUrls`, `defaultPermissionMode`, `statusLine` or `telemetry`), the account's sign-in state (`config.json` without its trusted folders, without the settings an older Copilot kept there, such as `trusted_folders`, `allowed_urls` or `allow_all`, in either spelling, and without its hooks' and plugins' keys when those are left out), the briefing, a link to the account's sessions, and links to what the account loads by itself; never its saved approvals. Below full access the run's `sandbox` setting has it on, with `allowBypass: false` (no command may leave it), the conversation's other working directories writable (`readwritePaths`), the skills folders, the attachments and the paths below read-only, the protected paths denied (`deniedPaths`, below), no credentials for git and `gh` through its proxy (`auth`), no keychain for its commands on macOS (`seatbelt.keychainAccess: false`), MCP servers outside it, as for every other CLI (`sandboxMcpServers: false`), its language servers and extensions inside it, and the network open (`allowOutbound`, `allowLocalNetwork`). A project's `.github/copilot/settings.json` cannot widen it (tried: its `allowBypass` and `readwritePaths` were ignored). Its commands then read system, `PATH` and dev-tool folders, the working directories and the temporary folder, not the home folder (so neither `~/.copilot` nor `~/.ssh`), and write only in the working directories and the temporary folder; its file tools keep to the same policy. Read-only besides (`copilotReadOnlyPaths()`), each only when it exists as the run starts (a path that does not exist when its sandbox starts is not protected by it, and bubblewrap refuses to start on one): your git config (`~/.gitconfig`, and the `config`, `ignore` and `attributes` files of `~/.config/git`, not the folder, so the credential store's file git may keep there stays unreadable), which git needs to run at all; the shared package and build caches its dev-tool access would let commands write besides the working directories (tried on a Mac in projects of each kind: Cargo's registry, git store and lock files, Go's build and module caches, npm, pnpm, Yarn, Bun, Deno, pip, uv, Poetry, virtualenv, Bundler, Maven, Gradle, ccache, sccache, node-gyp, Electron and Playwright), both where a variable moves one and in its default place, since Copilot grants both; some hold programs a later command runs outside any sandbox (npx's packages, Playwright's browsers, Gradle's wrapper), and this is the rule every CLI keeps (see [What the sandboxes do not cover](#what-the-sandboxes-do-not-cover)); and in each working directory what decides how agents run later (`.git/hooks`, `.git/config`, `.gitmodules`, `.vscode`, `.idea` and the agents' config that [Harness Relay's own sandbox](#harness-relays-own-sandbox) keeps read-only, see Git under [What the sandboxes do not cover](#what-the-sandboxes-do-not-cover); on macOS these are path rules, which a command can get around by renaming the folder above, as that bullet says). Only the flag fails closed: a sandbox turned on in its settings alone is dropped on a computer that cannot run it, and the flag is ignored while Copilot's own feature switch for its sandbox (`SANDBOX`) is off. So before each prompt Harness Relay sends `/sandbox policy`, a command Copilot answers itself (it never reaches the model, nor stays in the session); while it waits for the answer, any permission request is refused, and if the model answered after all (a tool call, its thinking, or usage in the result), the turn fails. Then it checks the answer: an effective policy, `Allow sandbox bypass: no`, `Allow keychain access`, `Authenticate git` and `Authenticate gh` off wherever it names them, and every protected path and other working directory named; otherwise the turn does not start, saying why. Anything else its "Dev tools" section lists as read-write, outside the temporary folders, makes the run start once more with that path read-only too (`copilotDevWrites()`); a command can still bring in more grants as it runs (Copilot: "run /sandbox policy <command> to resolve those"), and those are not seen in advance. A session that would run something by itself as it opens (a project's hooks, or the account's own hooks, plugins, extensions or language servers in the run's home) cannot be checked before that, so its sandbox is first checked in a start of its own: a home with only the sign-in state and the run's sandbox settings, everything left out, and an empty repository in the system's temporary folder as its working directory, so nothing runs there; its `/sandbox policy` must pass, then the run starts (one more short start, only then; tried with `copilot` 1.0.109 on macOS, Linux and Windows). Copilot asks (allow once, allow always, deny) before every command it does not take for read-only (`ls`, `cat`, `git status` and `echo` run without asking, in its sandbox), every file it creates or edits, every URL a command or its fetch tool names, and every read outside the working directory and the temporary folder; Harness Relay never answers allow always. In read-only, reads and URLs run, and commands, writes and MCP tool calls go to the user (or are refused); a command the user allows runs in the sandbox, which can write the working directories, so, as with Grok, the project is kept by asking. In edit mode commands run, except pushing and publishing; writes in the working directories run, except where a write could change how agents run later (the other CLIs' folders, `.git/hooks`, `.vscode`…, matched as for Antigravity, and Copilot's own in `.github`: `hooks`, `copilot`, `mcp.json`, `lsp.json`, `extensions` and `agents`, whose custom agents may name MCP servers of their own), which go to the user with a card that says why; and MCP tool calls and storing a memory go to the user too (Copilot's built-in GitHub MCP server can push files and open pull requests, outside any sandbox; a memory is kept on GitHub, for everyone who uses the repository's memories). A write outside the sandbox's writable paths is refused by Copilot itself, without asking (`Outside the sandbox's writable paths.`), and its turn goes on, so in edit mode the user cannot allow such a write; so is a detached command (`Detached commands cannot run inside the sandbox`). Any refusal from Harness Relay ends its turn (see [What an approval can do](#what-the-sandboxes-do-not-cover)). A project's own hooks, which Copilot runs without asking, are asked about before it starts, also when the account leaves hooks out (see [What the sandboxes do not cover](#what-the-sandboxes-do-not-cover)). Each turn also puts the session in Copilot's agent mode (its autopilot mode would turn allow-all on), below full access a session that does not report its allow-all option (one resumed from full access, say) does not run, and `COPILOT_ALLOW_ALL` and `COPILOT_ASSISTED_APPROVAL` are taken out of its environment. With full access Harness Relay passes `--allow-all`, turns the session's allow-all on and the sandbox off (`sandbox.enabled: false`): nothing asks. A stop cancels the session's prompt (`session/cancel`), and nothing it started stays running (checked: a `sleep 30` was gone).
- **Muse Code** runs over ACP (`muse acp`) and, below full access, in its own OS sandbox: Seatbelt on macOS, the bubblewrap it brings on Linux, and a Windows sandbox of its own once it is set up (see [Windows](#windows)). Its commands may write only in the workspace (the working directory and its `additionalDirectories`) and the system's temporary folder (`/tmp`, `/private/tmp`), while `.git`, `.muse` and `.agents` stay read-only; every host a command or its web fetch reaches is asked about (`--sandbox-network proxy-only`, its default). What runs without asking is its permission profile's and its session mode's, and a profile can be chosen only in its `settings.json`, so each turn gets a config folder of its own (`XDG_CONFIG_HOME`, a `run-…` folder in `muse-runs` in Harness Relay's data folder, owner-only and removed after the turn; not in `data/tmp`, which the profile denies, since git fails when it may not even look in its `XDG_CONFIG_HOME`) whose settings hold Harness Relay's profile `harness-relay`: Muse's `:ask-me` (a human reviewer) with a `"deny"` rule for each protected path (below). Muse's own `:read-only` cannot take deny rules ("deny cannot be enforced"), so read-only is that profile with Muse's file-writing tools taken away (`--disable-write`) and the session mode `promptUnmatched`, where every command asks; one the user allows runs in the sandbox, which lets it write in the working directories. Edit is the mode `onRequest`, where commands run in the sandbox and one that writes or reaches the network asks; Harness Relay allows one that writes, except pushing, publishing and a shell or interpreter running what it reads on standard input, which go to the user, and once allowed it still runs in the sandbox (tried: a command writing outside the workspace was asked about twice, allowed, and still failed with `Operation not permitted`). A command's network goes to the user in every mode below full access. Its file tools write in the working directories without asking in edit mode, but under `.git`, `.muse` and `.agents` (and `.envrc`), which Muse asks about and Harness Relay sends to the user when the write is into agents' config; Muse refuses a write outside the working directories by itself, and writes other agents' config in them (`.claude`, `.vscode`, `.mcp.json`…) without asking, as Claude Code, Codex and Grok do. The judge of Muse's default profile, a model that would decide calls, is off (`MUSE_DISABLE_APPROVAL_JUDGE=1`), and below full access the run's config folder has a `trust.json` of its own that marks the working directories untrusted (the account's is never used, nor is `--trust-workspace` given), so no workspace is trusted and a project's hooks (`.muse/hooks.json`, which Muse runs outside its sandbox in a trusted workspace) never load. On Linux its bubblewrap leaves an empty folder in each working directory for every path it mounts over (`.agents` and `.muse`, kept read-only; `.hg`, `.sl` and `.eden`, hidden); Harness Relay removes those that were not there before the turn once the last run in that folder ends, if they are empty or hold only the `.tbh-sandbox-mountpoint.<pid>` markers of sandbox processes no longer running (a stopped turn leaves them). With full access Harness Relay passes `--disable-sandbox` and `--trust-workspace`, with Muse's `:unrestricted` profile and the mode `allowAll`: nothing asks. Muse keeps the profile and the sandbox a session was made with (tried: a session made with full access, resumed with edit's settings, still read a denied file and wrote outside), so Harness Relay resumes a Muse session only when the same server process made it with the same permission and protected paths, and starts a fresh one otherwise.

## Harness Relay's own sandbox

The five open-source agents (OpenCode, Goose, Cline, OpenHands, Pi) have no OS sandbox of their own, so below full access Harness Relay runs each of them, and everything it starts, in a sandbox it builds with [`@anthropic-ai/sandbox-runtime`](https://github.com/anthropics/sandbox-runtime) (`srt`, Apache-2.0: Seatbelt on macOS, bubblewrap + seccomp on Linux, and a filtering HTTP/SOCKS proxy for the network). It is in `src/server/relaySandbox.ts`; the adapters ask for it through `sandboxCommand()`, and nothing below full access runs outside it.

**One sandbox per run.** Each run gets a host process of its own (`relaySandboxHost.ts`), started like any CLI through `src/server/process.ts` (tracked and killed with the whole process tree on shutdown), with a private control channel on its file descriptor 3. The host runs one sandbox-runtime for that run alone, so runs of different conversations — different working directories, permissions and hosts, at the same time — never see each other's rules: each has its own proxy, which only its own sandbox can reach (on macOS Seatbelt admits a connection to that proxy's port alone; on Linux the sandbox has no network of its own but that proxy's sockets), behind a token only its own sandbox is given. A host no rule decides is asked about over that run's channel, so the approval reaches the right run's **Ask me** and cannot be answered for another; the rules and the command never touch the command line or a shared file a sandboxed process could change. Inside the sandbox the agent starts through a fixed `/bin/sh` script (`SANDBOX_EXEC_SCRIPT`) that takes the program, its arguments and the run's own variables from its environment (`HARNESS_RELAY_SBX_*`, removed before the agent starts), so no value is ever part of a shell's text.

**The host's Node.** The host is a Node.js program. With `npm start` it runs on the server's own Node. The desktop app's Electron may not run as Node (its fuses turn that off), so there it runs on the Node.js 22.12 or later found on the login shell's `PATH` (`hostNode()`), bundled as `relaySandboxHost.mjs` with the sandbox runtime's packages beside it; without such a Node, the open agents are refused below full access with a message that says so.

**Filesystem.**

| | Read | Write |
| --- | --- | --- |
| Read-only | everything except the protected paths below | the run's own temp folder and the agent's state folders (its sessions, logs, caches) only — **not the working directory** |
| Edit | the same | the above plus the working directories and the conversation's attachments folder |

- Never readable **or** writable (`denyRead` + `denyWrite`): the protected paths (`protectedReads()`: the browsers' own folders and Harness Relay's database and temporary folder, and in a codespace its token files, the same as the other CLIs, see [What agents may not read or write](#what-agents-may-not-read-or-write)).
- Never writable (`denyWrite`), even where a folder above is: the agent's config paths (everything that changes what the CLI does when it starts — its config, plugins, extensions, hooks, MCP config, instructions files), so a run cannot widen its own next run; in edit mode, the other CLIs' and the open agents' own config inside the working directory (`.claude`, `.codex`, `.grok`, `.cursor` (Cursor, which runs without a sandbox, reads its rules, subagents, skills and MCP servers there), `.mcp.json`, `.opencode`, `opencode.json`, `opencode.jsonc`, `.goose`, `.cline`, `.clinerules` (Cline runs the hooks in `.clinerules/hooks` without asking), `.openhands`, `.pi`, `.agents`, and `.agent`, `_agents` and `_agent`, where Antigravity, which runs without a sandbox, also reads a project's hooks and MCP servers, and `.github/hooks`, `.github/copilot`, `.github/mcp.json`, `.github/lsp.json`, `.github/extensions` and `.github/agents` where a `.github` folder exists (so that one can still be made), since Copilot runs a project's `.github/hooks` without asking and reads its settings, MCP and language servers, extensions and custom agents, which may name MCP servers, there, and `.muse`, whose hooks Muse Code runs outside its sandbox in a trusted workspace), the folders of the programs the sandbox runs, and what sandbox-runtime would otherwise let any command write (`/tmp/claude`, `~/.npm/_logs`, `~/.claude/debug`). sandbox-runtime also keeps `.git/hooks`, `.git/config`, `.gitmodules` and the shell's dotfiles read-only by itself.
- **Each run writes its own, fresh temp folder** (in Harness Relay's data folder, removed when the run ends), not a shared one. sandbox-runtime gives every run the same `TMPDIR` (`/tmp/claude`) by default; Harness Relay overrides it so one run cannot leave a file — a transpile or compile cache, say — that the next run, perhaps in another conversation, loads and runs.
- **The host's own temp folder** (sandbox-runtime's sockets, its CA bundle) is in the data folder too, in `data/srt/<random>`, which no other run can read: never in the system's temporary folder, where another CLI's sandboxed command could replace or remove what is in it. A Unix socket's path must fit in 104 bytes on macOS and 108 on Linux, so a data folder whose path is too long for the sockets (more than 70 bytes on macOS, 61 on Linux, in UTF-8: a character outside ASCII takes 2 to 4) is refused below full access, with a message to set `RELAY_DATA_DIR` to a shorter folder. The desktop app's folder fits unless the user name is very long; a deep checkout (a worktree under `.claude/worktrees/`, say) may not.
- The run does not start when a protected path or a config path has `*`, `?` or `[` in its name (a sandbox would read it as a pattern and might not protect it), when a folder the run may write holds Harness Relay, the home folder or another CLI's own folder (it could then change what runs outside the sandbox), or, in edit mode, when the working directory itself is one of those (`relayFolderRefusal()`, as for the other CLIs).

**Network.** The run reaches the hosts of the model backends it uses (`api.openai.com`, `api.anthropic.com`, `api.x.ai`, and a custom endpoint's `host:port`) and no other without asking. Any other host is asked about through **Ask me** (an approval of kind `fetch`, for that host; "always allow" covers that host on that port only, or on 443 and 80 when the card names the host alone); declined, or in a conversation that refuses automatically, it is denied with a reason the model sees. A host the agent reaches every start but should never block a turn (Goose's `models.dev` catalogue) can be listed as **quietly denied** — refused with a reason, never asked. Harness Relay's own ports (`PORT`, or the one the server got when it is 0, 8787, 8789 and 5173: `npm start`'s and the desktop app's, and `npm run dev`'s API and Vite) are never allowed, directly or through the proxy, and neither is this computer's own address or a link-local or metadata address, however it is written (`127.1`, `2130706433`, `0x7f.0.0.1`, `localhost.` are read as the address the proxy dials). A host name is never looked up by Harness Relay before you allow it (its resolver is outside the sandbox, so looking up every name a command asks about would carry data out in the names): a name that leads to this computer (`localtest.me`, `127.0.0.1.nip.io`) is asked about like any other, and if you allow it, sandbox-runtime refuses it when it dials. A host still waiting to be asked about when the turn ends is refused, never put to the user afterwards. A model backend on this computer must name its port (`localhost:11434`; one on another computer of the local network, such as `192.168.1.20:8000`, need not), and both go through the proxy — Harness Relay keeps only loopback out of the proxy, never the private ranges, so a local backend still reaches the proxy and the allow-list decides (sandbox-runtime's own `NO_PROXY` covers the private ranges, which would send a local backend around the proxy and have it refused; Harness Relay narrows it). When a backend is on loopback itself (Ollama, a local vLLM), `NO_PROXY` lists only the agent's own ports (`localPorts`, below), so the backend and every other loopback port go through the proxy.

**The proxy, per client.** sandbox-runtime routes the network through a local proxy it names in `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY`. Harness Relay sets `NODE_USE_ENV_PROXY=1` so Node 22's `fetch` / `http` / `https` honour it (Node 22.21+); Bun, Python's `httpx` and `requests`, Rust's `reqwest`, Go and curl read the proxy variables by themselves. Checked on this Mac and in Docker on Linux: Node 22 `fetch`, Bun, Python `httpx` and `requests`, and curl (a stand-in for a Rust `reqwest` client) all reached an allowed host through the proxy and were refused a host that was not allowed. A client that never sends loopback to a proxy (Cline adds `localhost`, `127.0.0.1` and `::1` to `NO_PROXY` by itself) still reaches a model backend or a server on loopback that the run may reach: on macOS the run may connect to those loopback ports directly (never listen on them), and on Linux, where the sandbox's loopback is its own, `socat` relays each of those ports onto it through the proxy, with the run's own credentials, before the agent starts (`loopbackRelay`, `SANDBOX_EXEC_SCRIPT`). Either way it reaches only what the proxy's allowlist allows.

**Per-adapter opt-ins** (never on by default, each for one CLI that needs it, each documented where it is used):

- **A pseudo-terminal** (`allowPty`), for OpenHands, which runs its commands in one (never in tmux below full access). **What `allowPty` opens on macOS:** sandbox-runtime's rule lets the run open `/dev/ptmx` and **every** `/dev/ttys*` by path, read and write, so a program in the sandbox can open any terminal of the user's that is open at the time: print onto it, read what is typed into it and change its settings, such as turning echo off (the kernel still refuses to push input into a terminal that is not the program's own, `TIOCSTI`). Seatbelt cannot narrow it to the run's own terminals: its rules are fixed when the run starts and name devices by path, and a terminal's number is picked by the kernel only when it is opened (and reused). So on macOS OpenHands runs below full access only once the user turns on its switch in Settings (off by default), which says this. **On Linux** bubblewrap gives the sandbox a `/dev/pts` instance of its own (checked in Docker: only `ptmx` in it, no terminal from outside), so the option opens none of the user's terminals there and needs no switch. **The run's own Unix sockets** (`allowUnixSocketsInTmp`) stay available to adapters (macOS only, inside the run's own temp folder, fresh each run) but no adapter asks for them any more; on Linux sandbox-runtime cannot allow one socket path (its seccomp filter blocks every Unix socket unless all are allowed, which this sandbox never does).
- **Loopback ports the agent only connects to** (`connectPorts`): servers of the user's that the agent does not run itself (Goose's HTTP MCP servers on this computer). They are reached through the proxy, whose allow-list names `127.0.0.1`, `localhost` and `[::1]` at those ports; the sandbox may not listen on them (on macOS), so a command cannot take over the port of one that is down; on Linux it can only listen on its own loopback, which is not this computer's. Never one of Harness Relay's ports.
- **The agent's own loopback ports** (`localPorts`), for a CLI that runs an HTTP server of its own and talks to it (OpenCode's `opencode acp`). On macOS the sandbox may listen on and connect to exactly those ports and no other local port, directly or through the proxy (whose allow-list then has `127.0.0.1`, `localhost` and `[::1]` at those ports alone); on Linux it has a loopback of its own where any port works and none of this computer's is reachable, so the proxy, which is outside it, does not allow them. Next to a backend on loopback, `NO_PROXY` holds just `127.0.0.1:<port>` and `localhost:<port>` for these: Node, Bun and httpx honour a port there and reach the agent's server directly (checked on both platforms), while curl, and Python's requests for an address, ignore it and use the proxy, which reaches the agent's server on macOS only. Never one of Harness Relay's ports, nor the backend's. This is narrower than sandbox-runtime's `allowLocalBinding`, which would open every localhost port (Harness Relay's own API, other local services, other runs' servers).
- **The certificate-trust daemon** (`allowTlsTrustd`), for Goose, whose TLS verification (Rust, through rustls-platform-verifier → the macOS Security framework) needs `com.apple.trustd.agent`, which sandbox-runtime's Seatbelt profile blocks by default. This opens exactly that one mach service (the single service sandbox-runtime's own `enableWeakerNetworkIsolation` opens, named on its own so nothing else is), only on macOS. It is a possible way out of the sandbox, because trustd fetches a certificate's OCSP or CRL from the network itself, outside the proxy, so a program could carry a little data out in what it asks trustd to check; it is off for a CLI whose TLS already goes through the proxy (Node, Bun, Python).

**Fail closed.** When the sandbox cannot start — native Windows (sandbox-runtime's Windows support is alpha; the open agents refuse to run there below full access, as sandbox-runtime itself is refused below full isolation), another platform, a processor sandbox-runtime cannot block Unix sockets on (not x64 or arm64), `bubblewrap` / `socat` / `ripgrep` missing on Linux, or sandbox-runtime failing to apply the rules — the turn fails with a reason in the user's language and how to fix it per platform, unless the permission is full access. Harness Relay checks a real sandbox can start (it runs a trivial command in one) before each run, caching the result briefly; the host itself also fails closed before it starts anything, when sandbox-runtime cannot apply the rules or warns of a hole (no seccomp helper, its own copy writable).

**Leftovers.** When a run ends the host stops the sandbox's whole tree. A process that leaves the host's process group — a command the agent backgrounded, which some CLIs run detached so a double fork re-parents it to `launchd`, a daemon that called `setsid`, or a server such as a tmux — would be missed by a group kill, and macOS has no PID namespace to put the tree in. Two sweeps find such processes on macOS:
- **By their sandbox** (`src/server/sandboxProcs.ts`): every descendant keeps the Seatbelt profile it was started under and cannot drop it, whatever it closed or wherever it was re-parented. For each process of yours, the kernel tells whether its profile lets it write the run's own temporary folder (only that run's profile does) and not the folder around it (a process that may write that too has a wider sandbox, another tool's whose working directory holds Harness Relay's data, say, and is left alone). This reads no environment and no terminal, only the kernel's answer about the policy (libsandbox's `sandbox_check`, called through the system's Python, `/usr/bin/python3`, which comes with the Xcode command line tools). A run's profile lets it remove its own temporary folder or put a link in its place, so the server makes it a real folder again before it asks (the kernel answers by path). The server runs this sweep when it disposes of the run, before the run's folders are removed, and the next server start runs it for every run folder a killed server left.
- **By a marker**: every sandboxed process also inherits a read-only descriptor to a per-run marker file under `data/relay-sandbox/`, and whatever still holds it is found with `lsof` and killed, by the host when the run ends, by the server when it disposes of the run, and at the next start after a server kill. The CLIs close inherited descriptors when they start a command (Node, Bun and Python do; Goose keeps them), so this catches less, and it is all there is when the command line tools are missing. A start then cannot tell the folders of runs a killed server left free of what may still run in them, so it keeps them (below).

Only the run's own profile and its markers are looked at, so a shell of yours that merely has its working directory in the folder, or any process outside the run's sandbox, is left alone. A start removes what killed runs left only when its sweeps found nothing of them still running; otherwise it keeps their folders and markers for a later start, and gives no permission back anywhere (a process still running could swap a folder for a link). On Linux none of this is needed: bubblewrap puts the tree in its own PID namespace, which ends with the sandbox when the host (and so bubblewrap) dies, even on a server kill. What this does **not** catch: without the Xcode command line tools, a process that closed its inherited descriptors and left the host's group. Such a leftover keeps the filesystem rules frozen in its Seatbelt profile — in edit mode it can still write the working directory, the attachments and the run's state folder, and read everything outside the protected paths — but its proxy is gone, so it can reach **no** network host at all (Seatbelt allowed only the proxy's now-closed localhost port), Harness Relay's own API included. Its writes stop when the computer next restarts.

**What it needs installed.** Nothing on macOS (Seatbelt and `sandbox-exec` are part of it). On Linux: `bubblewrap`, `socat` and `ripgrep` (`sudo apt-get install bubblewrap socat ripgrep`, or `sudo dnf install …`), and, on Ubuntu 23.10 or later, the AppArmor profile for `/usr/bin/bwrap` from [On Linux](#on-linux) (bubblewrap needs unprivileged user namespaces). In a container, bubblewrap needs the container to allow user namespaces and a fresh `/proc` (for a throwaway container: `docker run --security-opt seccomp=unconfined --security-opt apparmor=unconfined --security-opt systempaths=unconfined`), or use full access and let the container be the sandbox.

**What it does not cover.** What a program in the sandbox may **read** (it reads almost the whole computer, `~/.ssh` and `~/.aws` included, except the protected paths); keeping secrets on the computer depends on the network block, which holds here on both platforms. A model backend you allow is reachable in full, so a determined agent could use it to carry data out (the allow-list is by host name, not by what the traffic is). On macOS, with `allowTlsTrustd` on, the trustd service as above. A Unix socket the agent needs on Linux (no path-based allow there). **On macOS, the start-up environment of every process above the command**: the agent process (`opencode`, …), the relay sandbox's host, the Harness Relay server, and the shell (or npm) that started the server — with the API keys any of them was started with and, for OpenCode, its local-server password. A command can read an ancestor's environment through the `kern.procargs2` sysctl (an unrelated process's is withheld by macOS, seen outside the sandbox). So keeping a key out of the agent's environment does not keep it from the agent's commands on macOS while the server holds it in its own start-up environment: start the server without API keys in its environment (Harness Relay keeps them in the OS credential store). On Linux the sandbox's PID namespace leaves only the sandboxed tree visible. Denying it would need a Seatbelt rule that also stops `ps` from running at all (procargs2 is the only channel for a process's command line too), which is too costly, so Harness Relay does not; instead an adapter keeps its secrets out of the environment of the commands the agent runs (OpenCode drops its server password there), and the network block stops a secret so read from being sent anywhere. Full access, which runs without a sandbox, as for the other CLIs.

**Checked** on 10 November 2026: on this Mac (macOS 26.6, arm64) with `scripts/sandbox-check.ts`, and on Linux in a throwaway Docker container (`node:22-bookworm`, bubblewrap 0.8, socat, ripgrep) with the same script. Again on 11 November 2026 on a DGX Spark (Ubuntu 24.04, arm64, bubblewrap 0.9) natively and in the same Docker container, with each open agent's real CLI run end to end there too (in read-only and edit, against a scripted endpoint and Ollama on loopback). In read-only and edit, a sandboxed process could not write outside the folders it is allowed (the working directory in read-only, the home folder, an ssh-like folder, the agent's config, any outside folder), could not read the protected paths (stand-ins for a browser folder, a secret file and the database), could not reach a host not allowed (and the approval path worked and was tied to the right run), reached an allowed host through the proxy with each client kind above, could not reach Harness Relay's port or this computer's own address, and could not escape through a child process, a symlink, a hard link, `git -c core.hooksPath` / config tricks, or by rewriting its own config path. Two concurrent runs with different rules stayed apart. A stopped run left no process or temporary folder behind, a detached command that tried to write after the turn ended (re-parented out of the host's group) was swept by the marker; background writers started from Node, Python and Perl that closed every descriptor and left the group were swept by their sandbox when the run ended (each wrote after the turn with that sweep turned off), while a process in a wider sandbox was left alone; and a process standing in for one left by a killed server was swept at the next startup. Every check ran with the private roots real runs have; a run read its own config inside them (Goose's layout), the network worked with the host's temp folder under the hidden folder (a short data path), a connect-only port was reached through the proxy and could not be listened on (macOS), a name that leads to this computer was asked about (never looked up by the server) and refused at dial time when allowed, and a shell whose working directory was in `data/relay-sandbox/` survived the startup sweep. `npm test` runs the offline unit tests (`test/relaySandbox.test.ts`, `test/sandboxProcs.test.ts`); it never starts a real sandbox. The real checks are the separate `scripts/sandbox-check.ts`.

## What agents may not read or write

Below full access, Harness Relay keeps every agent's sandbox (for Cursor and Antigravity, which have none, their own read and write tools, as far as Cursor's deny rules and the calls Antigravity asks about reach: see below) out of these places (`src/server/protect.ts`), on macOS and Linux:

- **The browsers' own folders**, where a signed-in browser keeps the key it sends to Harness Relay (and, in some browsers, its cookie) on disk: Chrome, Chromium, Edge, Brave, Arc, Vivaldi, Opera, Firefox, LibreWolf, Zen, Orion, Floorp, Waterfox, Helium, DuckDuckGo and GNOME Web, and Safari's and WebKit's folders (`~/Library/…` on macOS; `~/.config/…` and `$XDG_CONFIG_HOME/…`, `~/.mozilla`, snap and Flatpak folders on Linux). Only those that exist are listed, each also by its real path.
- **The desktop app's window's own folder** (`browser/` in the app's folder: `~/Library/Application Support/Harness Relay/browser` on macOS, `~/.config/Harness Relay/browser` on Linux), where its window keeps its cookie and key; the app names it to the server as `RELAY_APP_BROWSER_DIR`.
- **Harness Relay's database** (`relay.db` and the files SQLite keeps beside it, in `data/`, or with the desktop app in the `data` folder of its own folder), also when the working directory holds it.
- **Harness Relay's own temporary folder** (`data/tmp`, or `data/tmp` in the desktop app's folder), where a Claude Code turn's `--settings` and MCP config wait for it, and where each Cursor turn's config folder and each Copilot turn's home (its settings, which decide its sandbox, and a copy of the account's sign-in state) are. In the system's temporary folder, which every sandbox lets commands write in, another agent's command could change them before Claude Code (or Copilot) reads them (turning its sandbox off, or starting a command of its own as an MCP server, outside any sandbox), or read the MCP servers' secret values. A turn removes its folder when it ends; what a turn the server was stopped during left (a Claude Code turn's settings hold an endpoint's key when it runs on one) is removed when the server starts again (`clearRunTmp()`).
- **In a GitHub codespace** ([Try it in GitHub Codespaces](codespaces.md)), the files that hold GitHub tokens in plain text: `/workspaces/.codespaces`, where Codespaces keeps the codespace's token, its registry sign-ins and the user's Codespaces secrets, readable by every program in the codespace, and gh's own folder (`~/.config/gh`, or where `GH_CONFIG_DIR` or `XDG_CONFIG_HOME` puts it), which keeps the sign-in made for sharing in a file, without a keyring. Agents keep the token Codespaces gives every program there (`GITHUB_TOKEN`) for their own `gh` and `git`. Only where `CODESPACES=true` (`codespaceSecretDirs()`): anywhere else gh's folder is how the agents' own `gh` signs in.

How each CLI takes them:

- **Claude Code**: `sandbox.filesystem.denyRead` and `denyWrite`, and `Read` deny rules for its own file tools, which are outside its sandbox. The turn's `--settings` also set `filesystem.disabled: false`, over a user setting that turns file isolation off. `allowRead` / `allowWrite` lists add up across settings files, so a run does not start when your own Claude Code settings (`settings.json` in its home) or managed settings on the computer (`managed-settings.json` and `managed-settings.d`) allow a path that reaches a protected one, a relative entry taken from the settings file's folder; the message names the entry to remove. (Claude Code itself, 2.1.322, ignores a project's `allowRead` entries that would open a path the turn's `--settings` deny.)
- **Codex**: a `deny` entry for each in the thread's `harness-relay-…` permission profile (not on Windows, whose legacy sandbox cannot deny reading everywhere). Its name changes with each run: Codex merges a profile of the same name from its other config files, such as a trusted project's `.codex/config.toml`, into it, and a more specific entry there (`read` for a folder inside a denied one) opens the path again (tried with `codex sandbox`). Codex 0.167 on the DGX Spark could not use a profile of its own: the thread started, but every turn failed sending its request (`failed to load workspace requirements: invalid input parameter`; Codex's built-in `:workspace` worked). A run that hits this runs again in Codex's legacy sandbox mode, kept for the rest of the server's run: its writes and network as before, without the deny list, so there Codex's commands can read the browsers' folders and the database (they still cannot reach the network, Harness Relay's API included).
- **Grok**: the `deny` list of its custom profile `harness-relay`, which Harness Relay writes into `sandbox.toml` in Grok's home (`~/.grok`, or `grok` in the CLIs' own folder) before each run, between `# >>> harness-relay` and `# <<< harness-relay`, leaving the rest of the file as it is. A custom profile Grok cannot apply makes it refuse to start; on Linux, its `deny` list needs bubblewrap. Grok's `workspace` lets its commands write all of Grok's home, where its own program is (`downloads`, `bin`): the list also denies those, and the folder of the program Harness Relay starts. Grok reads its settings there after its sandbox is on (`sandbox.toml` outside Harness Relay's block, `config.toml`, `managed_config.toml`, `requirements.toml`, `trusted_folders.toml`, `permission.toml`, `hooks-paths`), so they cannot be denied: Harness Relay reads them before each turn (a link as a link; an empty file counts as none, since Grok's sandbox makes them empty when they are missing) and, when a turn changed one, moves the changed one aside (`….changed-<time>`, renamed, not followed), puts it back and fails the turn saying so; a changed `skills` folder is reported the same way, not put back. Grok turns running at the same time share the settings as they were before the first of them, and a turn that starts while another runs first puts back what that one's commands changed. Changes that Grok itself, or you, make to these files during such a turn are put back the same way. Trusting a folder in Harness Relay during one first puts back what its commands changed, then records the trust in the store as the turn found it, and the turn keeps that. (`read_only` in a Grok profile grants reading; it does not stop writing.) On Linux, Grok starts its sandbox by running its own program again through bubblewrap, so a denied program could not start at all (tried): there its program is not denied but checked instead, the links in `~/.grok/bin` and the program file, with a copy kept in `data/tmp`; a change is put back from the copy before another sandboxed turn starts it and after each turn, and fails the turn.
- **Cursor**: deny rules in the turn's own `cli-config.json`, for each path `Read(<path>)`, `Read(<path>/**)`, `Write(<path>)` and `Write(<path>/**)` (the path itself, for the database's files, and everything under it), beside your own deny rules from the account's `cli-config.json`. They bind Cursor's own read and write tools only, and Cursor matches them against the path as written, case-sensitively and without resolving links: another spelling of a protected path (other letter case, on macOS's usual case-insensitive disk) or a link inside the project that leads to one is not denied, and its read tool reads it without asking. Its shell commands have no sandbox, so they are kept from these paths only by asking: a command the user allows (or one on a Cursor team's allowlist) can read and write them.
- **Antigravity**: Harness Relay refuses, without asking, each call agy asks about that reads or writes one of these paths (matched with the links on the way resolved; the chat shows why), and since a refusal ends its turn, the turn ends there. agy asks about reads only outside the workspace, a read through a link that leads out of it included (it resolves the link; checked with `agy` 1.5.6), so such a read of a protected path is refused too; a read whose path the adapter cannot tell asks. What Harness Relay cannot see are the reads agy does without asking, inside the workspace. Its shell commands have no sandbox, so they are kept from these paths only by asking: a command the user allows can read and write them.
- **Copilot**: the `deniedPaths` of the run's sandbox policy (`sandbox.userPolicy.filesystem` in the `settings.json` of the turn's own home), which its commands and its own file tools keep to (its file tools refuse such a path by themselves, without asking: `Is a sandbox denied path.`); the policy check before each turn makes sure every one of them is named. Harness Relay also refuses, without asking, each call Copilot asks about that names one (matched with the links on the way resolved), and since a refusal ends its turn, the turn ends there.
- **Muse Code**: a `"deny"` entry for each path in the `filesystem` of Harness Relay's permission profile (`harness-relay`, from `:ask-me`) in the turn's own `settings.json`, for files and folders, there or not. It binds Muse's own file tools and its sandbox alike (tried on macOS and Linux: `read_file` of a protected file was refused, and `cat` of it in the sandbox failed with `Operation not permitted`). A `"read"` or `"write"` rule for a missing path would make Muse refuse the run ("cannot be enforced"), so only `deny` is used, and a profile Muse cannot apply fails closed. Harness Relay also refuses, without asking, a call Muse asks about that names a protected path. Muse reads `*`, `?` and `[` in a rule as a pattern (see below).
- **The open agents** (OpenCode, Goose, Cline, OpenHands, Pi): `denyRead` + `denyWrite` for the same paths, as literal names, in [Harness Relay's own sandbox](#harness-relays-own-sandbox); the agent's config paths are `denyWrite` too, so a run cannot widen its next one.

Tried on a Mac in edit mode with Claude Code, Codex and Grok: listing `~/Library/Application Support/Firefox` and reading `data/relay.db` with the shell failed with `Operation not permitted`, reading the database with Claude Code's Read tool or Grok's file tool was refused, and writing in the working directory worked. Claude Code's Read tool was also refused a file in the Firefox folder (a path with spaces). Grok's commands could not write `~/.grok/downloads` nor rename `~/.grok/bin` (before this, they could), and appending to `~/.grok/config.toml` was refused by Grok itself; its sessions stayed writable. Copilot's commands could not read a protected path on the Mac, and its file tools refused one by themselves.

What this does not cover: Codex where it cannot use a profile of its own (see above); Cursor's and Antigravity's commands, which have no sandbox, and their hooks and MCP servers; Cursor's read and write tools given another spelling of a protected path, or a link to one; Antigravity's reads inside the workspace, which it does not ask about (of a protected path inside a working directory, say); Muse Code's own hooks and MCP servers (whether they run in its sandbox was not checked); a browser whose folder is not on the list (a new one, a portable one, or Chrome with `--user-data-dir` somewhere else); a command the user allows to run outside the sandbox; what a CLI runs outside its sandbox, such as Claude Code's hooks and local MCP servers, and Copilot's MCP servers (see [What the sandboxes do not cover](#what-the-sandboxes-do-not-cover)); a project's own Claude Code settings (`.claude/settings.json`, `.claude/settings.local.json`), which another agent in edit mode can write, and whose hooks, `sandbox.excludedCommands` and `network.allowUnixSockets` the next Claude Code turn takes; the plugin folders Grok keeps up itself in its home (`marketplace-cache`, `installed-plugins`, `bundles`, `bundled`), which its commands can change for a later run with full access; a change to Grok's settings made by a process a command left running after its turn, which the next turn takes as it finds it; full access; native Windows. A protected path whose name holds `*`, `?` or `[`, which the sandboxes would read as a pattern, makes runs below full access refuse to start, saying which.

Edit mode is also refused in a working directory that holds Harness Relay itself (its folder, or its data folder; the worktrees of parallel mode, inside the data folder, are fine) or voice input's folder (`data/voice`, or where `RELAY_VOICE_DIR` puts it, also a folder inside it: Harness Relay runs the engine there outside any sandbox), or what decides how the agents run: your home folder (a project inside it is fine), a CLI's own folder (`~/.claude`, `~/.claude.json`, `~/.codex`, `~/.grok`, `~/.cursor`, `~/.gemini` (Antigravity's, or an account's `.gemini`), `~/.copilot` (Copilot's), Muse Code's config and data folders (`~/.config/muse`, `~/.local/share/muse`, or an account's), or where their variables move them — Cursor's also under `$XDG_CONFIG_HOME/cursor` when that is where it keeps its settings — with `~/.cursor` refused even then, and so are `$XDG_CONFIG_HOME/cursor` (else `~/.config/cursor`) and `%APPDATA%\Cursor`, where Cursor keeps its sign-in on Linux and Windows, wherever its settings are), the CLIs' own folder Harness Relay gives them, or the folder of a CLI's program; holding it or inside it. Agents there change files without asking, and could change Harness Relay's code, a CLI's settings or program, or your shell's. A conversation is refused when it is created, scheduled or changed so (before a missing folder is created), and a turn when it starts. Read-only stays allowed there, since it asks before writing (and Codex cannot write at all). To work on Harness Relay itself, run the copy you use from another folder.

### macOS

- Claude Code, Codex and Grok use Seatbelt, which is part of macOS: there is nothing to install.
- **Cursor** applies no sandbox in Harness Relay's runs (tried with `cursor-agent` 2026.11.11): below full access every command it runs asks (except those on a Cursor team's allowlist), and one the user allows runs with the user's full rights, network included.
- **Antigravity** has a terminal sandbox of its own, which on macOS also blocks the network, but Harness Relay does not turn it on: over ACP in `agy` 1.5.6 it let sandboxed commands write only in the temporary folder, nowhere in the working directory. Below full access every command it runs asks, and one the user allows runs with the user's full rights, network included.
- **Copilot** uses Seatbelt as well, through its own sandbox, which Harness Relay turns on below full access: nothing to install. Tried with `copilot` 1.0.109: a command's write outside the working directories failed with `Operation not permitted`, and a protected path could not be read. The policy Harness Relay gives it lets commands reach the network, this computer's loopback included (tried: `curl http://127.0.0.1:…` from a Copilot command in edit mode got its answer).
- **Muse Code** uses Seatbelt, with nothing to install: below full access its commands write only in the working directories and the temporary folder, and every host they reach is asked about (tried with `muse` 1.4.18).
- **Grok cannot block the network on macOS.** Its docs say that blocking the network of the commands it runs is enforced on Linux only (through seccomp) and does nothing on macOS, for every profile, `read-only` and `strict` included. On every platform, what Grok does itself (web search, web fetch, the model's API) is never blocked.
- A runtime socket that is a symlink can stop Grok's `read-only` and `strict` profiles from starting (see above; both tried).
- Claude Code's docs list what fails under its Seatbelt sandbox: `gh`, `gcloud` and `terraform` may fail TLS verification; `open`, `osascript` and sign-ins in the browser are blocked (Apple Events); git over SSH fails (its tunnel through the sandbox's proxy cannot authenticate on macOS); and a command can listen on or connect to a localhost port only with `network.allowLocalBinding`.

### Linux

- **Claude Code** needs `bubblewrap` and `socat` (`sudo apt-get install bubblewrap socat`, or `sudo dnf install bubblewrap socat`). To block Unix sockets as well, it needs the seccomp filter from `npm install -g @anthropic-ai/sandbox-runtime`. Each command gets a localhost of its own, so it cannot reach a server on the computer's localhost.
- **Codex** uses bubblewrap and seccomp. It takes the first `bwrap` on the `PATH` (outside the working directory), or else one it ships with, and warns at start. Its older Landlock code (`features.use_legacy_landlock`) is rejected for policies that restrict files.
- **Grok** uses Landlock and needs kernel 5.13 or later. Before kernel 6.2 (Landlock ABI 3; the default kernels of Ubuntu 22.04 and Debian 12 are older), a command can still shorten a file outside the paths it may write with `truncate`. A custom profile with a `deny` list also needs bubblewrap, so Harness Relay's runs below full access do (theirs always holds its database). Its docs also say that `workspace`, `read-only` and `strict` refuse to start on Linux "without verified read-only mounts" (the mounts that keep Grok's own settings and hooks from being written). Network blocking (`restrict_network`) uses seccomp and works on Linux.
- bubblewrap needs unprivileged user namespaces. Since 23.10, Ubuntu restricts them with AppArmor, which can stop bubblewrap; Claude Code's docs then say to add an AppArmor profile for `/usr/bin/bwrap`, or to lift the restriction with `sysctl` for a `bwrap` anywhere else.
- **Cursor** needs nothing here, since its ACP mode applies no sandbox on Linux either (from its code; not tried on Linux). Its commands are kept in check by asking alone.
- **Antigravity** needs nothing here either: Harness Relay does not turn its sandbox on (tried on Linux: every command asks). Its commands are kept in check by asking alone.
- **Copilot**'s sandbox uses bubblewrap 0.5 or later, and needs besides it slirp4netns, util-linux 2.35 or later (`unshare`, `nsenter`), iproute2, `iptables` and `ip6tables` (with `iptables-restore` and `ip6tables-restore`), `/dev/net/tun`, and unprivileged user and network namespaces, which Ubuntu 24.04 blocks with `kernel.apparmor_restrict_unprivileged_userns=1` (whether the AppArmor profile for `/usr/bin/bwrap` in [On Linux](#on-linux) is enough for it was not checked). Without them every command Copilot runs in its sandbox fails, closed, with Copilot's own reason (`Cannot start sandboxed command: Bubblewrap … private network is unavailable … requires 'slirp4netns'`): its turn goes on, nothing runs outside the sandbox, and its file tools still keep to the policy (tried on the DGX Spark). With all of them in place (tried there with slirp4netns 1.2.1 and the sysctl set to 0) it works in Harness Relay's runs as on macOS: commands write only in the working directories and the temporary folder (a folder outside them is not even there inside bubblewrap: `No such file or directory`), and protected paths are refused. Its commands reach the internet but not services on this computer's own loopback (`127.0.0.1`), since their network is slirp4netns' own: a test against a local database or a dev server started outside the sandbox fails there unless it uses this computer's LAN address (and the server listens there), and Harness Relay's own server, which listens on loopback only, is out of their reach too. The read-only paths Harness Relay gives it are only those that exist when the run starts, since bubblewrap refuses to start on a path that does not exist.
- **Muse Code** brings its own bubblewrap, so nothing needs installing (tried on the DGX Spark, Ubuntu 24.04). It leaves empty `.agents`, `.muse`, `.hg`, `.sl` and `.eden` folders in the working directory, for what it mounts over, and a turn stopped while its sandbox ran also leaves `.tbh-sandbox-mountpoint.<pid>` markers in them. Harness Relay removes those a turn made once the last run in that folder ends, when they are empty or hold only markers of sandbox processes no longer running; anything else in them stays.

### Docker and dev containers

Containers often keep bubblewrap from working: they may block the user namespaces it needs, or mounting a fresh `/proc`.

- **Claude Code**: `sandbox.enableWeakerNestedSandbox: true` makes it work in an unprivileged container (it reuses the container's `/proc`), with weaker isolation.
- **Codex** warns at start when bubblewrap cannot create user namespaces. Its docs suggest giving the container what bubblewrap needs, or running `codex` with `--sandbox danger-full-access` inside it and letting the container be the sandbox.
- **Grok**: Landlock itself needs no user namespace, but a `deny` list needs bubblewrap, and the read-only mounts of its built-in profiles (see Linux above) may need a mount namespace too (not verified). Not tried in a container.
- **Cursor** has no sandbox to break: the container itself is the only isolation its commands get there (not tried).
- **Antigravity**: the same, since Harness Relay does not turn its sandbox on (not tried).
- **Copilot**: its bubblewrap sandbox needs what Linux above lists inside the container too: user and network namespaces and `/dev/net/tun` among them (not tried).
- **Muse Code**: its bubblewrap needs what bubblewrap needs (not tried).

**This repository's dev container** (`.devcontainer/`, for [GitHub Codespaces](codespaces.md)) gives bubblewrap what it needs: `securityOpt` `seccomp=unconfined`, `apparmor=unconfined` and `systempaths=unconfined`, and a TUN device (`--device=/dev/net/tun`) for Copilot's sandbox; not `privileged`. Tried on 14 November 2026 in a codespace (Debian 12, kernel 6.8, x86_64, 2 cores):

- Without those options, `bwrap` stopped with `No permissions to create new namespace` (Docker's seccomp profile), so every command below full access would have failed.
- With them, `scripts/sandbox-check.ts` passed all 51 checks; Codex's sandbox (`codex sandbox`, workspace-write) wrote the working directory and neither the home folder nor the network; and Copilot's, in a Harness Relay turn in edit mode, could not read the database (`Permission denied`), while what it wrote in the home folder and Harness Relay's folder stayed inside the sandbox, not on disk.
- Claude Code's sandbox (the same sandbox runtime as Harness Relay's own) was not run with a sign-in.

### Windows

- **Codex** has a sandbox of its own, in three implementations (`[windows] sandbox = "…"` in `config.toml`):
  - `mxc`, the one its docs recommend: no administrator setup, no extra accounts or firewall rules. It needs Windows 11 24H2 (build 26100.9278) or 25H2 (build 26200.9278) or later. Commands can reach services on loopback, and when a command ends, the processes it left running stop too (so a dev server started in the background stops with it).
  - `elevated`, the legacy fallback its docs prefer when `mxc` is not available: an administrator sets it up once (a UAC prompt, local users and groups, firewall rules, logon rights for those users); commands then run as those lower-privilege users, without administrator rights. IT can run `codex sandbox setup --elevated` from an elevated process ahead of time.
  - `unelevated`, a second legacy fallback: a restricted token derived from your account, with file permissions as the boundary, for when the elevated setup is not possible. Its network isolation is weaker, and it cannot deny reading a path.
  - Windows 11 is recommended; Windows 10 is best effort and needs version 1809 or later. Its log is `CODEX_HOME/.sandbox/sandbox.log`.
- **Claude Code** has no sandbox on native Windows: commands run without one. Use WSL2.
- **Grok**: its docs list only macOS and Linux. Whether Grok then runs without a sandbox on Windows (its docs say a built-in profile that cannot be applied only warns, see below) or refuses to start was not verified.
- **Cursor** has none there either. Harness Relay keeps no protected paths on Windows, so its read and write tools get no deny rules for them there (not tried with the real CLI).
- **Antigravity**: none either, and with no protected paths on Windows Harness Relay refuses none of its reads or writes for them there (tried with the real CLI: every command asks, and runs in PowerShell).
- **Copilot** has a sandbox of its own there, a process container, which Harness Relay turns on below full access, as on macOS. Tried with `copilot` 1.0.109 on Windows 11 Pro (arm64, build 26200): a command's write outside the working directories failed with `Access to the path … is denied`, a second working directory was writable, and a file given to it as a protected path was refused. Harness Relay keeps no protected paths on Windows, as for every CLI, so its policy denies none there; the sandbox's own read policy still keeps commands to the working directories, the tools and the system folders. Its shell there is PowerShell. Installed with npm, Copilot is npm's `copilot.cmd` there, which Harness Relay starts as the program it runs (`winLaunch.ts`; tried: a turn, a refusal, a stop). Other Windows versions were not tried.
- **Muse Code** has a sandbox of its own on Windows, which needs a one-time setup run elevated, by the user (a UAC prompt; run as SYSTEM it refuses, "runtime user SID is not a supported account SID"): `muse sandbox windows setup` creates two local accounts (`muse-sbx-r1`, `muse-sbx-u1`) in a `MuseSandboxUsers` group, their capabilities, firewall (WFP) filters that keep them from connecting, listening and accepting, and `C:\ProgramData\muse` (with the accounts' passwords), once per computer; `muse sandbox windows check` says whether it is done (`setup_required`, "sandbox users are not ready", before; `ready` after). Muse has no command that removes them. But muse 1.4.18's ACP mode, which Harness Relay uses, does not use that sandbox: with it set up (tried on Windows 11, arm64), every command below full access still fails before it starts ("sandbox enforcement unavailable: windows_elevated setup_required…"; its trace says `sandbox.prepare … platform="none"`), with every network mode, also when `muse acp` is driven directly with Muse's default settings. Commands fail closed, so none runs outside a sandbox. Its file tools, web fetch and full access work. Its shell tool there is PowerShell. Harness Relay keeps no protected paths on Windows, so Muse gets no deny rules there (it would refuse a Windows path in one anyway). Muse finds `C:\ProgramData` through `SystemDrive`, which Harness Relay passes on with the rest of its environment; without it `check` itself says `setup_required`.

### WSL

- **WSL2**: Codex and Claude Code use their Linux sandbox, with the same requirements (bubblewrap; and `socat` for Claude Code). Whether Grok's Landlock works depends on the WSL2 kernel (not verified). Cursor and Antigravity have no sandbox there either. Copilot's Linux sandbox was not tried in WSL2. Muse Code was not tried there.
- **WSL1** cannot create user namespaces. Claude Code's sandbox needs WSL2, and Codex (since 0.115) refuses the sandboxed commands that need bubblewrap.

Grok keeps the profile a session started with for the life of that session, and refuses to resume it with a different one (its docs). Harness Relay resumes each agent's session from turn to turn, and starts a fresh one, with the conversation so far, when a resume fails. Read-only and edit share a profile, so only a change to or from full access, or a change to the profile you set, makes that happen (Grok sessions from before `harness-relay` also start fresh once).

### On macOS

There is nothing to install for any of them.

**Claude Code.** In `~/.claude/settings.json`:

```json
{
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "allowUnsandboxedCommands": false,
    "network": {
      "allowedDomains": ["github.com", "*.npmjs.org"],
      "allowLocalBinding": true
    }
  }
}
```

- `failIfUnavailable` makes Claude Code stop at start instead of running commands without a sandbox; `allowUnsandboxedCommands: false` takes away the retry outside the sandbox.
- `network.allowedDomains` lists the hosts commands may reach; any other host is asked about or refused (see [What an approval can do](#what-the-sandboxes-do-not-cover)). `network.allowLocalBinding` lets commands listen on and connect to localhost ports, for dev servers and tests.
- For one session only: `claude --settings '{"sandbox": {"enabled": true, "allowUnsandboxedCommands": false}}'`. In a session, `/sandbox` shows and changes it, and saves the change in the project's `.claude/settings.local.json`.
- To check, ask Claude (not the `!` prompt) to run `touch ~/sandbox-probe`, which should fail with `Operation not permitted`, and `curl --noproxy '*' https://example.com`, which should fail with `Could not resolve host`; turn down any retry outside the sandbox.

**Codex.**

```sh
codex --sandbox workspace-write    # this session: read-only, workspace-write or danger-full-access
codex sandbox --permission-profile :workspace -- touch ~/sandbox-probe    # check: Operation not permitted
```

In `~/.codex/config.toml`:

```toml
sandbox_mode = "workspace-write"

[sandbox_workspace_write]
network_access = false
writable_roots = ["/absolute/path/to/another/folder"]
```

- `codex sandbox` runs one command in the sandbox of a built-in profile: `:read-only`, `:workspace` or `:danger-full-access`. In 0.167 it takes no platform name; Codex's docs still write `codex sandbox macos …` (tried: 0.167 takes `macos` as the command to run).

**Grok.**

```sh
grok --sandbox workspace    # this session: workspace, read-only, strict, devbox or a custom profile
GROK_SANDBOX=workspace grok    # the same, from the environment
tail -n 1 ~/.grok/sessions/sandbox-events.jsonl    # check: "enforced": true
```

In `~/.grok/config.toml`:

```toml
[sandbox]
profile = "workspace"
```

A custom profile goes in `~/.grok/sandbox.toml`, or a project's `.grok/sandbox.toml`, and is used with `grok --sandbox project`:

```toml
[profiles.project]
extends = "workspace"
read_only = ["/data"]
deny = ["~/.ssh", "**/.env", "**/*.pem"]
```

- `devbox` is for disposable machines: it writes almost everywhere, the home folder included. `restrict_network = true` does nothing on macOS (see [macOS](#macos)).
- Harness Relay already runs Grok in its own profile `harness-relay`, based on `workspace`, below full access; a `GROK_SANDBOX` it was started with applies to its full-access Grok runs only.

**Cursor.** Nothing to turn on for Harness Relay's runs: its ACP mode ignores `--sandbox` and `sandbox.mode`. What keeps its commands in check there is asking; for code you do not trust, use read-only, or set **Actions beyond the permission** to refuse.

**Antigravity.** Nothing to turn on for Harness Relay's runs: `enableTerminalSandbox` (or `--sandbox`) would keep its commands from writing the working directory over ACP (`agy` 1.5.6). What keeps its commands in check there is asking, as for Cursor.

**Copilot.**

```sh
copilot --sandbox    # this session: in its sandbox, or not at all
```

- In a session, `/sandbox policy` shows the policy in force (`Effective sandbox policy`, `Allow sandbox bypass: …`, the paths it names), or `Command sandboxing is disabled, so no policy is in force…` when it is off.
- A sandbox turned on only in `~/.copilot/settings.json` (`sandbox.enabled`) is dropped on a computer that cannot run it; only `--sandbox` fails closed.
- Harness Relay already runs Copilot in its sandbox below full access, with a policy of its own for each turn; your own `sandbox` settings do not reach those runs.

**Muse Code.** Nothing to turn on: Seatbelt is part of macOS, and Muse runs its commands in its sandbox unless it is given `--disable-sandbox` (Harness Relay gives that with full access only).

### On Linux

First check what the sandboxes need (these checks are not from the CLIs' docs and were not tried):

```sh
bwrap --ro-bind / / true && echo "bubblewrap works"    # Claude Code, Codex, Grok's deny lists
uname -r    # Grok: 5.13 or later (6.2 or later to stop truncate)
cat /sys/kernel/security/lsm    # Grok: the list includes landlock
sysctl kernel.apparmor_restrict_unprivileged_userns    # Ubuntu 23.10 and later: 1 = restricted
bwrap --version    # Copilot: 0.5 or later
unshare --version    # Copilot: util-linux 2.35 or later
command -v slirp4netns ip iptables ip6tables iptables-restore ip6tables-restore    # Copilot: each found
ls -l /dev/net/tun    # Copilot: present
```

When bubblewrap fails on Ubuntu 23.10 or later, Claude Code's docs give an AppArmor profile for `/usr/bin/bwrap`:

```sh
sudo tee /etc/apparmor.d/bwrap > /dev/null <<'EOF'
abi <abi/4.0>,
include <tunables/global>

profile bwrap /usr/bin/bwrap flags=(unconfined) {
  userns,
  include if exists <local/bwrap>
}
EOF
sudo systemctl reload apparmor
```

It covers only `/usr/bin/bwrap` (see `which bwrap`), not the copy Codex ships with. For a `bwrap` anywhere else, `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0` lifts the restriction for every program until the next restart.

**Claude Code.**

```sh
sudo apt-get install bubblewrap socat    # Fedora: sudo dnf install bubblewrap socat
npm install -g @anthropic-ai/sandbox-runtime    # optional: blocks Unix sockets as well
```

Then the same `settings.json` as on macOS; `allowLocalBinding` has no effect on Linux. Restart Claude Code after installing, since it checks at start. To check, the same two commands as on macOS: `touch ~/sandbox-probe` fails with `Read-only file system` here, and `/sandbox` shows whether anything is missing.

**Codex.**

```sh
sudo apt-get install bubblewrap    # Fedora: sudo dnf install bubblewrap
```

Without it, Codex uses the `bwrap` it ships with and warns at start. Then the same `config.toml` and commands as on macOS (`codex sandbox` was tried on a Mac only).

**Grok.** After the checks above, the same `config.toml`, `--sandbox` and `GROK_SANDBOX` as on macOS. On Linux a custom profile can also block the network of the commands Grok runs:

```toml
[profiles.offline]
extends = "workspace"
restrict_network = true
```

A `deny` list needs bubblewrap: `sudo apt-get install bubblewrap`.

**Cursor.** Nothing to install: Harness Relay's runs have no sandbox on Linux either.

**Antigravity.** Nothing to install either: Harness Relay does not turn its sandbox on (tried on Linux).

**Copilot.** Its sandbox needs the programs the checks above name, and unprivileged user and network namespaces. On Debian and Ubuntu (package names; not tried on a fresh system):

```sh
sudo apt-get install bubblewrap slirp4netns iproute2 iptables
```

On Ubuntu 23.10 or later the namespaces are restricted (`kernel.apparmor_restrict_unprivileged_userns=1`, as on Ubuntu 24.04); whether the AppArmor profile above is enough for Copilot was not checked: on the DGX Spark the restriction was lifted instead (`sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`, until the next restart). Without all of this, every command Copilot runs in its sandbox fails with Copilot's own reason. With it, its sandbox works in Harness Relay's runs (tried on the DGX Spark), but its commands cannot reach services on this computer's loopback, such as a local database or dev server: `127.0.0.1` in their network namespace is not the host's, so use the host's LAN address.

**Muse Code.** Nothing to install: it brings its own bubblewrap (tried on Ubuntu 24.04).


**Claude Code and Grok** have no sandbox on native Windows: run them, and Harness Relay, in WSL2. **Cursor** and **Antigravity** have none in Harness Relay's runs on any system, so WSL2 does not change that for them. **Copilot** needs nothing to be installed for its sandbox there: Harness Relay passes `--sandbox` (tried on Windows 11 Pro, arm64, build 26200).

## When the sandbox cannot start

Some of these failures are silent: the CLI runs on without a sandbox, and Harness Relay does not show any warning the CLI prints.

| | What happens |
| --- | --- |
| Claude Code | Commands run without a sandbox, unless `sandbox.failIfUnavailable` is `true`; then it exits at start. Harness Relay sets it below full access, so the turn fails with Claude Code's reason and how to fix it. |
| Codex | On WSL1, sandboxed commands are refused. Elsewhere it warns at start (for example bubblewrap without user namespaces); its Linux README calls the alternative "a runtime sandbox failure", so sandboxed commands most likely fail then rather than run without a sandbox (not verified). |
| Grok | A built-in profile: its docs say it warns and carries on without enforcement, but some failures (such as the symlinked socket above, or Linux without the read-only mounts) make it refuse to start instead. A custom profile (`sandbox.toml`) always refuses to start. `"enforced": true` in `sandbox-events.jsonl` in Grok's `sessions` folder (`~/.grok/sessions`, or `grok/sessions` in the CLIs' own folder) shows that a profile was applied. |
| Cursor | Its ACP mode never starts one, so nothing fails and nothing warns: below full access every command asks instead (except those on a Cursor team's allowlist). |
| Antigravity | Harness Relay does not turn its sandbox on, so nothing fails and nothing warns: below full access every command asks instead. One you turned on yourself (`enableTerminalSandbox: true` in its settings) does not reach Harness Relay's runs, whose settings keep only your model and service. |
| Copilot | Only `--sandbox` fails closed: a sandbox turned on in its settings alone is dropped where it cannot run, and the flag is ignored while Copilot's own feature switch for its sandbox is off. Harness Relay passes the flag and, before each prompt, checks `/sandbox policy`: an effective policy, no bypass, no keychain access and no git or gh authentication where it names them, every protected path and other working directory named, and an answer from Copilot itself, not its model (no tool call, thinking or usage; any permission request meanwhile is refused). Otherwise the turn does not start, saying why (*Copilot's sandbox is not as Harness Relay set it up (…)*). A session that would run something by itself as it opens (hooks, plugins, extensions, language servers) is checked first in a start of its own, where nothing runs. On Linux without what its sandbox needs, the policy is in force but every command it runs in the sandbox fails with Copilot's own reason, and the turn goes on: nothing runs outside the sandbox. |
| Muse Code | A profile it cannot apply fails closed: `session/new` refuses to open, and the turn fails with Muse's message. On Windows every command fails before it starts ("sandbox enforcement unavailable: windows_elevated setup_required…"), also after its own sandbox setup, and the model sees that as the command's failure; its file tools still work. A sandbox that could not start on macOS or Linux was not seen. |

When Grok refuses to start because of its sandbox, the turn fails with Grok's reason. Apart from Copilot's policy, Harness Relay does not check whether a sandbox was actually applied.

## What the sandboxes do not cover

- **Reading.** By default all let commands read almost the whole computer, `~/.ssh` and `~/.aws` included; only Grok's `strict` profile limits reading (to the working directory, system paths and `~/.grok`), and so does Copilot's sandbox (to system, tool and working folders and the temporary folder: not the home folder). Harness Relay keeps every sandbox, [its own](#harness-relays-own-sandbox) included, out of the browsers' folders (the desktop app's window's included) and its own database (see [What agents may not read or write](#what-agents-may-not-read-or-write)), not out of anything else. A Cursor command the user allows (or one on a Cursor team's allowlist), or an Antigravity command the user allows, with no sandbox, can read and write anything the user can. Keeping secrets from leaving the computer depends on blocking the network, which Grok cannot do on macOS, Copilot's sandbox does not do in Harness Relay's runs (its policy lets commands reach the network), Muse Code's sandbox does by asking about a command's network, which Harness Relay sends to the user, and Cursor and Antigravity cannot do anywhere in Harness Relay's runs; Harness Relay's own sandbox blocks it on both platforms, but a model backend it allows is reachable in full, so a determined agent could still carry data out through one (the allow-list is by host, not by what the traffic is).
- **Harness Relay's own API.** Grok's sandbox lets commands reach localhost (tried on a Mac: `curl http://127.0.0.1:…` from a Grok command in edit mode got its answer), but Harness Relay's API at `127.0.0.1:8787` takes only signed-in browsers: a program without the browser's cookie and key gets 401 (tried with `curl`), so such a command cannot start a turn (see [Architecture → Signing in](architecture.md#signing-in) for what it does not stop). Claude Code's and Codex's sandboxes, and Harness Relay's own, refused localhost in the same test — Harness Relay's own denies its port by name as well, so even an agent granted a loopback port of its own (OpenCode) cannot reach it. A Cursor command the user allows reaches localhost too, with no sandbox, and gets the same 401 (so would an Antigravity one: not tried). On macOS a Copilot command reaches localhost too (tried: `curl http://127.0.0.1:…` from a Copilot command in edit mode got its answer), so there only Harness Relay's sign-in keeps it out of the API. On Linux it cannot reach this computer's loopback at all: bubblewrap gives it a network namespace of its own (through slirp4netns), where `127.0.0.1` is not the host's (`Couldn't connect`), and it reaches this computer only at its LAN address, where Harness Relay does not listen. On Windows that was not tried.
- **What the open agents run outside their own tools.** Harness Relay's own sandbox covers everything the agent and its subprocesses do; there is no part of the agent that runs outside it (unlike Claude Code's hooks and MCP servers). On Linux it cannot allow a single Unix socket (so a CLI that needs one there must do without), and on macOS a CLI that verifies TLS through the system (Goose) is given the `trustd` service, which is a possible way out (see [Harness Relay's own sandbox](#harness-relays-own-sandbox)).
- **Claude Code's own tools.** Its sandbox covers Bash commands and what they start, not its Read, Edit, Write, WebFetch and WebSearch tools (its permission rules govern those), its hooks, local MCP servers (the tool library's included) or LSP servers.
- **Cursor's own tools.** Its deny rules bind its read and write tools only, not its commands, and only for the path as written: Cursor matches them case-sensitively and without resolving links, so another spelling of a protected path (other letter case, on macOS's usual case-insensitive disk) or a link inside the project that leads to one is not denied, and its read tool reads it without asking. Its hooks (`~/.cursor/hooks.json`, an organisation's, and Claude Code's in `~/.claude/settings.json`, which Cursor loads too, whatever is left out of Claude Code's own runs) run on its tool calls in every run, with no switch to turn them off for one, and the MCP servers it starts run outside any sandbox.
- **Antigravity's own tools.** Harness Relay decides only the calls agy asks about: reads inside the workspace never come to it (a read through a link that leads out of the workspace does, and is refused when it leads to a protected path). Its hooks and MCP servers in `~/.gemini/config/` (or an account's `.gemini`) load in Harness Relay's runs and run outside any sandbox: agy has no switch to leave them out of one run. A project's own MCP servers, hooks and plugins (`mcp_config.json`, `hooks.json`, `plugins/` and `plugins.json` in `.agents`, `.agent`, `_agents` or `_agent`, from each working directory up to its repository's root) agy starts as soon as its session opens, outside any sandbox and without a permission request, in read-only too (checked with `agy` 1.5.6). Other agents in edit mode can write those files (Claude Code, Codex, Grok and Cursor all write the working directory; only Harness Relay's own sandbox keeps them read-only, for the open agents), and so can whoever made the repository. So below full access, when the working directories hold any of them, Harness Relay asks the user before agy starts, with a card that lists them; "always allow" holds while their contents stay the same. Refused, or refused automatically, the turn does not start. With full access nothing asks.
- **Copilot's own tools and a project's hooks.** Its MCP servers (the account's and the tool library's) run outside its sandbox, as every CLI's do; its language servers and extensions run inside it. A project's hooks (`.github/hooks/*.json`, from each working directory up to its repository's root) run when Copilot's session opens and before its tool calls, without a permission request, in read-only too (inside its sandbox below full access; checked with `copilot` 1.0.109). They run also when the account leaves Copilot's hooks out (`disableAllHooks`), which turns off only the account's own hooks (tried with `copilot` 1.0.109). Copilot's help says it also runs the hooks a project's `.github/copilot/settings.json` or `settings.local.json`, or Claude Code's `.claude/settings.json` or `settings.local.json`, defines; those did not run in Harness Relay's runs, which trust no folder, but are asked about all the same. Other agents in edit mode can write those files (Harness Relay's own sandbox keeps `.claude` read-only for the open agents, and `.github/hooks`, `.github/copilot` and `.github/agents` where a `.github` folder exists; Antigravity's edit mode asks before writing them; Copilot's own writes there ask, and its commands cannot write them where they existed as its run started), and so can whoever made the repository. So below full access, when the working directories hold any, Harness Relay asks the user before Copilot starts, with a card that lists them; "always allow" holds while the contents of each whole `.github/hooks` folder (the scripts beside its JSON files too) and of the hook settings files stay the same (a 16-digit fingerprint; a script elsewhere that a hook runs is not covered). Refused, or refused automatically, the turn does not start; so Copilot as the lead agent or the group sorter, which cannot ask, does not start in such a project (as Antigravity does not in one with a project setup of its own). Allowed, its sandbox is checked first in a start where nothing runs, and the hooks then run inside it (tried with `copilot` 1.0.109 on macOS, Linux and Windows: a `sessionStart` hook's file was written in the working directory). It is asked also when the account leaves Copilot's hooks out; with full access it is not. Copilot does not start a project's `.mcp.json` or `.github/mcp.json` (only in a folder it trusts, and Harness Relay's runs trust none), `.github/extensions` (experimental only) or `.github/lsp.json` (it did not start).
- **Muse Code's own tools.** Its file tools follow its profile, deny rules included; its web fetches and searches are asked about and allowed below full access. In read-only a command the user allows runs in its sandbox, which lets it write in the working directories: Muse's `:read-only` profile, which would not, cannot take deny rules. In edit mode its file tools write other agents' config in the working directories (`.claude`, `.vscode`, `.mcp.json`, `.codex`, `.cursor`…) without asking, as Claude Code, Codex and Grok write the working directory: Muse asks only about writes under `.git`, `.muse` and `.agents` (and `.envrc`). Its skills and instruction files, its own and those it takes from Claude Code and Codex, load in every run. A trusted workspace's hooks (`.muse/hooks.json`) run outside its sandbox (one wrote outside the workspace in a test): below full access no workspace is trusted, so they do not load.
- **A Cursor team's allowlist.** Commands on a Cursor team's auto-run allowlist (set by a team admin in Cursor's dashboard, read from Cursor's servers) may run without asking, outside any sandbox. Harness Relay cannot clear it.
- **Writing outside the working directory and the temp folders fails**, package caches included (`~/.npm`, pip, cargo, Go's build cache). With the network off as well, installing dependencies fails. Copilot's dev-tool access would let commands write many of these caches, so below full access Harness Relay makes them read-only for it (see Copilot above): installing dependencies that write them fails there too (tried: writes to a Cargo registry, a go-build cache and a module cache refused on macOS and Linux, a Cargo registry write on Windows).
- **Git.** Codex's `workspace-write` keeps `.git` read-only: `git add` and `git commit` fail with `.git/index.lock: Operation not permitted` (tried on a Mac). Claude Code keeps `.git/config` and `.git/hooks` from being written. Copilot's sandbox lets commands write anywhere in the working directory, `.git/hooks` and `.git/config` included, so Harness Relay gives those to Copilot's sandbox as read-only paths, with `.gitmodules`, `.vscode`, `.idea` and the agents' config files Harness Relay's own sandbox keeps read-only (`PROJECT_AGENT_CONFIG` in `relaySandbox.ts`), but only those that exist when the run starts: a path that does not exist then is not protected by Copilot's sandbox (and bubblewrap refuses to start on one), so a command can still make one that was missing (a `.vscode` folder, say). On macOS these read-only paths are path rules, so a command can rename the folder above one, write inside and rename it back (tried with `copilot` 1.0.109: `mv .git .g; touch .g/hooks/planted; mv .g .git` worked on macOS; on Linux the bind mount held, `Read-only file system`): Harness Relay's own git commands never run a repository's hooks or the commands its config names (`repoDriverGuards()`, below), but your own git later would. Its commands can read your own git config (`~/.gitconfig`, and the `config`, `ignore` and `attributes` files of `~/.config/git`), which git needs to run, but not write it, and not read the rest of that folder, where git's credential store may keep a file, and Muse Code's sandbox all of `.git`. In parallel mode, a worktree's git data lives in the main repository's `.git/worktrees/<name>`, outside the working directory. Harness Relay's snapshots and the commits of worktree results run in the server, outside any sandbox, so they still work. Grok's sandbox lets commands write `.git/config`, `.git/info` and `.git/hooks` (tried on a Mac: `git config core.fsmonitor …` worked), and so can a Cursor or Antigravity command the user allows, or a write to them that the user allows Cursor or Antigravity, so Harness Relay's own git commands, outside any sandbox, never run what a repository's own config names: its hooks and fsmonitor are off, each filter, diff and merge driver its config (or what that includes) defines is emptied, and a diff runs no external diff or textconv (`repoDriverGuards()`). The same goes for the repositories at its submodules, which `git add` runs `git status` in: an agent can write their config, and in a worktree make one where a submodule's folder is empty. Git fetches no missing object (`GIT_NO_LAZY_FETCH`, git 2.44 or later), since a partial clone's remote would be reached through a command the config names, and a `core.worktree` naming a folder other than the repository's own is refused, since a snapshot would take that folder's files in and applying would write there. The user's own drivers, such as git-lfs's in `~/.gitconfig`, still run.
- **Tools that often break in a sandbox** (from Claude Code's docs): Docker and ssh-agent (Unix sockets), git over SSH and `open` and `osascript` (on macOS), watchman (use `jest --no-watchman`), Chromium on Linux (Playwright, which starts it, was not tried).
- **What an approval can do.** In a sandbox, asking the user means asking whether a command may leave it:
  - Claude Code: the model may run the command again outside the sandbox with `dangerouslyDisableSandbox` (`sandbox.allowUnsandboxedCommands: false` takes that way out away). That retry, and a connection to a host that is not on its network allowlist, are asked about in `manual` and `acceptEdits` and refused in `dontAsk`. In a headless `-p` run they come as `can_use_tool` requests (tried on a Mac): a host as `SandboxNetworkAccess`, which Harness Relay shows as reading a web page from that host; and a command Claude Code asks about because of a path (`blocked_path`) the sandbox cannot write, which would fail in the sandbox even once allowed, so Harness Relay runs it outside the sandbox when the user allows it, and the card says so. With refusing, `acceptEdits` still sends the host request, which Harness Relay refuses.
  - Codex: it asks only when the model requests more than the sandbox allows, as today.
  - Grok: a profile cannot be lifted once applied, so approving a call does not let it write outside the profile's paths.
  - Cursor: there is no sandbox to leave, so allowing a command runs it with the user's full rights.
  - Muse Code: allowing a command lets it run, still in the sandbox: a write outside the working directories still fails (tried). A command's network is asked of the user on its own, in every mode below full access. The model gets no note with a refusal, only Muse's own words, and the turn carries on.
  - Antigravity: the same as Cursor, and any refusal (the user's, an automatic one, or a protected path) ends its turn at once: agy stops (`stopReason: "end_turn"`) and tells the model nothing, so no note passes with a refusal.
  - Copilot: its sandbox cannot be left (`allowBypass: false`), so a command the user allows runs in it; Harness Relay never answers "allow always", which Copilot would save. Any refusal (the user's, an automatic one, or a protected path) ends its turn at once: Copilot tells the model only "The user rejected this tool call." and stops (`stopReason: "end_turn"`), so no note passes with a refusal.
  - The open agents: only a host no rule decides is asked about (an approval of kind `fetch`), and allowing it lets the run reach that host through the proxy; the file rules cannot be lifted, so approving nothing lets the agent write outside the folders its permission allows. A host on this computer, or Harness Relay's own port, is refused without asking.

## What is still missing

Read-only and edit now run in a sandbox with Claude Code, Codex, Grok, Copilot, Muse Code and the open agents (in Harness Relay's own) where the platform has one; Cursor's and Antigravity's commands run in none, on any platform, and are kept in check by asking alone. Full access is meant to run without one: Docker, pushing, installing and writing outside the folder are what it is for. Still missing:

1. **Not taking a setting for a sandbox.** Claude Code and Grok on native Windows, and Grok's network on macOS, can be set but are not enforced, Cursor's ACP mode applies no sandbox at all, Antigravity's terminal sandbox cannot be used over ACP (`agy` 1.5.6: its commands could not write the working directory), and Copilot's sandbox turned on in its settings alone is dropped where it cannot run (Harness Relay's runs pass the flag and check the policy). The UI should say whether each agent is really sandboxed on this computer, or refuse a sandboxed mode there.
2. **Checking the requirements on Linux before a run.** When Claude Code's sandbox cannot run, its turn fails and says to install `bubblewrap` and `socat`; Codex's and Grok's requirements (`bwrap`, the kernel version, user namespaces inside a container) are not checked, and nothing says in the user's language what to install for them. Neither are Copilot's (slirp4netns, network namespaces…): without them each of its commands fails with Copilot's own reason, in English.
3. **Codex's `elevated` sandbox on Windows** needs its one-time setup, with a UAC prompt; whether a `codex app-server` started in the background can show it was not verified. An administrator can run `codex sandbox setup --elevated` first, or the user can use `mxc` where Windows supports it.
4. **Muse Code's Windows sandbox** needs its one-time setup, run elevated. Harness Relay neither runs it nor checks that it was run before a turn (its commands fail until then), and commands in that sandbox were not tried.
