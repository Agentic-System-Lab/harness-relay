# Developer guide

How the code is organized, how to run and test it, and how to extend it. Read [Architecture](architecture.md) first for the big picture.

## Stack

| Layer | Tech |
| --- | --- |
| Language | TypeScript (strict), ES modules |
| Server | Node.js ≥ 22.13, [Hono](https://hono.dev) on `@hono/node-server`, run with `tsx` (no build step) |
| Database | SQLite via the built-in `node:sqlite` (`DatabaseSync`) |
| API keys | OS credential store via [`@napi-rs/keyring`](https://github.com/Brooooooklyn/keyring-node) (prebuilt binaries, no compiler needed) |
| Client | React 19, Vite, `react-markdown` + `remark-gfm` + `rehype-highlight` |
| Tests | Vitest |

## Running

```bash
npm install
npm run dev        # tsx watch (API :8789) + vite (UI :5173, proxies /api/ to the API); prints a sign-in link for :5173
npm run typecheck
npm test
npm run test:e2e   # end-to-end tests in a browser, with fake CLIs (npm run test:e2e:install once)
npm run build      # UI → dist/web
npm start          # one process: API + built UI on :8787; prints a sign-in link
npm run login      # another one-time sign-in link (ten minutes)

npm install --prefix desktop   # once, for the desktop app only: Electron and electron-builder
npm run desktop                # build the UI and the desktop app, and run it without installing it
npm run desktop:dist           # …and make the installer for this system in desktop/release/
npm run desktop:dist -- --output <folder>   # …elsewhere (the `--` hands the option to the script)
npx tsx desktop/scripts/check-package.ts    # check the packaged app, as a release is checked
npm run desktop:typecheck
```

`npm run build` puts the libraries the page loads at startup in their own chunks (`react`, `highlight`, `vendor`), so a browser keeps them across app updates; Mermaid stays lazy. It warns when a chunk loaded at startup passes 500 kB (`vite.config.ts`); Mermaid's lazy chunks are larger and only load when a diagram needs them.

The web app manifest and the icons a phone puts on its home screen (or a browser shows for the installed app) are in `src/web/public/`. They are drawn by `npm run icons` (`scripts/app-icons.ts`) from the same three circles as the favicon and `Logo.tsx`, without an image library; run it again after changing the mark, the icons' sizes or the manifest, and commit what it writes.

`npm run dev` restarts the server on every file change. A restart aborts any running agent turn (its message is marked aborted), so avoid editing server files while a long turn is running.

### Environment variables

| Variable | Default | Purpose |
| --- | --- | --- |
| `PORT` | `8787` (`8789` with `npm run dev`) | API port (the Vite proxy uses it too). `npm run dev` has a port of its own so that it runs beside the desktop app, or an `npm start` of another checkout, which use 8787 (`src/server/ports.ts`); beside an `npm start` of the same checkout it refuses to start, since the two would share its data folder |
| `HOST` | `127.0.0.1` | Bind address |
| `RELAY_DATA_DIR` | `./data` | Where `relay.db` lives. One server holds it while it runs (`server.lock`): a second one with the same folder refuses to start |
| `RELAY_DEFAULT_CWD` | process cwd | Initial default working directory (until changed in Settings) |
| `RELAY_ALLOWED_HOSTS` | — | Extra comma-separated host names accepted by the Host/Origin check, such as the machine's Tailscale name (see [Use it from your phone](remote-access.md)) |
| `RELAY_KEYRING` | — | `off` keeps API keys in the database instead of the OS credential store (e.g. for a throwaway data directory) |
| `RELAY_WEB_DIR` | `./dist/web` | Where the built UI is (the desktop app points it at its own copy) |
| `RELAY_KEYRING_SERVICE` | `harness-relay` | The name API keys are filed under in the credential store (the desktop app's own: `harness-relay-desktop`) |
| `RELAY_APP_BROWSER_DIR` | — | Set by the desktop app: its window's browser folder (cookies, localStorage: its sign-in), which agents below full access may not read (`protectedReads()`) |
| `RELAY_UPDATES` | — | Read by the desktop app, not the server: `off` keeps it from asking GitHub for new releases |
| `RELAY_MAX_ACCOUNTS` | `10` | Accounts per CLI, the default one included (1–100) |
| `RELAY_MAX_TEAM_AGENTS` | `8` | Most members a team may have, set by hand or by the lead agent (1–32). A team the lead agent designs by itself keeps to 5, or fewer when this is lower |
| `RELAY_TURN_TIMEOUT_MIN` | `45` | Each agent turn's safety timeout in minutes, a turn waiting for the user's answer included (1–1440) |
| `RELAY_VOICE_MODEL_BASE_URL` | Hugging Face, pinned to one commit | The http(s) folder voice input downloads its models from (`<url>/ggml-<model>.bin`), such as a mirror. Each file is still checked against its pinned size and SHA-256 |
| `RELAY_VOICE_ENGINE_BASE_URL` | whisper.cpp's release on GitHub | The http(s) folder voice input downloads its engine from on Linux and Windows (`<url>/<archive>`, the names of `ENGINE_BUILDS`), checked the same way |
| `RELAY_VOICE_DIR` | `<data folder>/voice` | Where voice input keeps its models and engine: an absolute path, or one starting with `~/`. Not in a temp folder (the server refuses to start), and edit mode is refused in a working directory that holds it or is inside it, since the engine runs outside any sandbox (so is it in the default folder). The engine's empty static folder stays in the data folder (`voice-public`). Removing voice input there removes the files Harness Relay downloads, by their names (the models, this version's engine), and the folders it made once they are empty; nothing else |

The server passes its own environment to the CLIs, minus Claude Code's nesting variables, plus stored API keys (`SettingsStore.env()`).

### The desktop app

`desktop/` is the desktop app ([user guide](user-guide.md#desktop-app)). It is a package of its own, with its own `package.json` and lockfile, so `npm install` at the root never downloads Electron (about 100 MB) for people who use `npm start`. Install it once with `npm install --prefix desktop`; it uses the root's `tsx` and `typescript`, so install the root first. Its code is plain TypeScript checked by `npm run desktop:typecheck`. The parts without Electron (`env.ts`, `supervisor.ts`, `tailscale.ts`, `autostart.ts`, `prefs.ts`, `profile.ts`, `log.ts`, `update.ts`, `traymenu.ts`, `selftest.ts`, `i18n.ts`, `icons.ts`, `manifest.ts`, `lifecycle.ts`, and `scripts/packaged.ts`) are tested from the root `test/` like the rest; only `main.ts` imports `electron`.

How it runs:

- **The server** is `src/server/index.ts`, bundled by esbuild into one ES module (`desktop/build/server/server.mjs`). It runs in an Electron utility process: Electron's own Node (Electron 45: Node 24, with `node:sqlite`), so the app needs no Node.js. The built UI (`server/web`, given as `RELAY_WEB_DIR`) and the keyring module (`server/node_modules/@napi-rs/`, native code, so it is copied, not bundled) sit next to it. In the installed app they are in the app's resources (`Resources/server` on macOS), outside the app archive, so `protect.ts`'s `RELAY_ROOT` is the app itself (`Harness Relay.app/Contents` on macOS, the install folder on Windows).
- **Messages** (`DesktopToServer` and `ServerToDesktop` in `src/shared/types.ts`, through `process.parentPort`; see `src/server/parent.ts`). The server says when it listens, or why it cannot. The app asks for a sign-in link (a new one-time code, one minute: `CODE_TTL_MS.desktop`) each time it opens the chat, how many conversations have agents at work (`busy`: `Orchestrator.busy()`, which counts runs and runs being set up, changes being made to a conversation such as a parallel reply applied, the lead agent changing a team or sorting a conversation into a group, and branches being made; an update waits for none), and for a shutdown, which runs the same shutdown as SIGTERM: agents are stopped and their process groups killed first. Windows has no signal to send, so this is how it stops there. A server the app started prints no sign-in code: its output goes to the app's log, which agents may read. It also tells the sign-in page so (`createApp({ desktopApp })`: `GET /api/auth` adds `desktop: true`, and the 401 message changes), which then points at the app's menu instead of a terminal: at **Open Harness Relay** in the app's window (Electron names itself in the user agent), at **Open in browser** in a browser (`src/web/signin.ts`). Started by `npm start` or `npm run dev`, the server has no parent and none of this happens.
- **The environment.** On macOS and Linux the app runs the user's login shell (`$SHELL -i -l -c`, printing `/usr/bin/env -0` between two marks) before it starts the server, at launch and again on **Restart server…** and **Start server**, and gives the server that environment, as a terminal would have it. On Windows it takes its own environment at launch; a restart or a start reads PATH and the user's variables again with PowerShell (`windowsEnv()`, `mergeWindowsEnv()`): PATH as Windows makes it for a new program (the system's, then the user's), followed by the app's own other entries; the system's other variables are left alone (some, such as `USERNAME`, are defaults the session replaces). If that fails it adds the usual install folders to PATH instead (`withCommonPaths`). `serverEnv()` then sets `RELAY_DATA_DIR` (the app's data folder, unless the user set one), `RELAY_KEYRING_SERVICE` (`harness-relay-desktop`, with the app's own data folder), `RELAY_DEFAULT_CWD` (the home folder, unless set), `RELAY_WEB_DIR`, `RELAY_APP_BROWSER_DIR` (the window's browser folder, below), `PORT` (from `desktop.json`), `HOST=127.0.0.1`, and `RELAY_ALLOWED_HOSTS` with this computer's tailnet name: as Tailscale reports it (also before it has connected, when it knows it), else the last one seen (`tailnetName` in `desktop.json`), so that a start at login before Tailscale connects still lets the phone in. It drops `ELECTRON_*` variables.
- **The supervisor** (`supervisor.ts`) checks that the port is free, starts the server, waits for it to listen (three minutes at most: after an update macOS may ask for the keychain first), and keeps the end of its output for the error dialog. It asks for sign-in links and how many conversations have agents at work (each in order; no answer after 5 s). On a stop it asks the server to shut down and kills it if it has not exited in 20 seconds. A stop while the server starts kills it at once instead: it has not listened, so it runs no agent, and quitting while macOS asks for the keychain does not wait for the three minutes. Each server process has its own queues of questions, so one that exits late cannot cancel the next one's. An exit nobody asked for, after the server ran, is reported as a crash.
- **Quitting** (from the menu, on SIGINT or SIGTERM, or when macOS or Linux shuts down) waits for the server to stop before the app exits.
- **The window** shows the chat: a `BrowserWindow` (sandboxed, context isolation, no Node) that loads a sign-in link from the server, so it is signed in at once (as a browser of its own). `guardContents()` (`lifecycle.ts`) keeps its pages on the server, for new windows, navigations and redirects: `linkAction()` sends other web pages and mail to the default browser, opens the server's own pages (files, attachments, which need the window's sign-in) in windows of the app, and goes nowhere for anything else (`file:`, `javascript:`). `permissionAllowed()` lets the server's pages use the microphone (audio only, for voice input), write to the clipboard and go full screen (a video's own button), and nothing else; Electron's permission check for media without a kind counts as one for the microphone (`permissionChecked()`). Its browser data (cookies, localStorage: its sign-in) is in `browser/` of the user-data folder (`profile.ts`, Electron's `sessionData`), which the server is told as `RELAY_APP_BROWSER_DIR` and `protectedReads()` adds to what agents below full access may not read; the rest of the user-data folder holds the data folder, which parallel mode's worktrees are in, so it cannot be kept from them as a whole. A sign-in an earlier build kept in the user-data folder itself is removed at start. **Open Harness Relay** on a window that shows the sign-in page (it has `data-signin`) loads it again with a new link. Downloads use Electron's save dialog. The window's size is kept in `desktop.json`. Closing it leaves the app in the tray (`window-all-closed` is handled); on macOS the Dock icon shows while a window is open (the app is `LSUIElement`). The app menu (Edit, View, Window, in the user's language) gives the window the usual shortcuts, copy and paste included, which macOS only routes through a menu; on Windows and Linux it shows with Alt. **Open in browser** in the tray menu opens the same in the default browser.
- **The tray menu** is rebuilt on every state change, always with the same items (by id), shown or hidden. On macOS and Windows an open menu keeps showing what it showed when it opened: changing an item, or setting a new menu, changes nothing on screen until it opens again (tried with Electron 45 on macOS). So while it is open (`menu-will-show` to `menu-will-close`, and a moment after, since the click on an item comes after the menu closed), its items are changed in place (`patchMenu()`, `traymenu.ts`) and no new menu is set, and `LiveMenu` closes it and opens it again (`closeContextMenu()`, `popUpContextMenu()`; on Windows where the user opened it) when what it shows changed, such as an update's progress, at most once a second. It opens it again 50 ms after closing it (`REOPEN_DELAY_MS`), outside the closing menu's own loop: opened from inside it, each menu runs inside the one before on macOS, and after a few the app takes seconds to quit, or never does. The old menu's close is expected before or after the new one says it opened. Linux's menus (D-Bus) are set anew as before. Opening the app again (`second-instance` on Windows and Linux, `activate` on macOS, the Dock icon) shows the window (`reopenAction()`). Open at login uses Electron's login items on macOS and Windows, and an XDG autostart entry on Linux (`autostart.ts`), started with `--hidden` (macOS reports `wasOpenedAtLogin` instead) so that it does not open the window. On Linux, an autostart entry that is on is written again at each start, so that it starts the AppImage the app runs from.
- **Sharing with the tailnet** runs `tailscale serve --bg`, on HTTPS 443 unless another service, or Funnel, uses that port (then 8443 or 10000: `sharePlan()`, `freeHttpsPort()`; sharing a funneled port for the tailnet would turn Funnel off). When `tailscale serve status --json` cannot be read, nothing is shared.
- **The log** (`log.ts`) is the server's output: started over, the previous one kept as `.old`, past 5 MB, at a start and while the server runs. A log that cannot be written is given up on quietly, never an uncaught error.
- **Updates** (`update.ts`). About 30 seconds after the first start, then every hour (`CHECK_EVERY_MS`; at most every five minutes when the chat asks, `mayAskGitHub()`), a packaged app (unless `RELAY_UPDATES=off`) asks `GET /repos/…/releases?per_page=20` when it is a release candidate or a build of your own (`releases/latest` would leave out pre-releases), and `GET /repos/…/releases/latest` when it is a release (`LATEST_RELEASE_API`: found however many release candidates came out since); `checkNow()` says whether a check asks at all, and a question is given up on after 30 s (`CHECK_TIMEOUT_MS`). `parseRelease()` takes a release that is not a draft and whose tag is a version of ours, a release candidate too, with each system's installer by the endings of `site/assets/downloads.js` (`INSTALLERS`, `isInstallerUrl()`), fetched from its copy for updates when the release has one (`UPDATE_INSTALLERS`: `-update` before the extension, so that GitHub's download counts tell updates of an installed app from new installs; still named as the installer, which the AppImage takes), a plain file name and GitHub's `digest` (SHA-256); `newestRelease()` takes the newest by version (`compareSemver()`), not by when it was published, and leaves release candidates out for an app that is a release (`takesCandidates()`: an app whose semver has no `-rc` or `-dev`). When it is newer (`compareSemver()` against `app.getVersion()`) and has this system's installer, the tray menu offers it, and so does the chat: `main.ts` sends the server an `update` message (`DesktopUpdate`: a newer version, an update under way, the last check) each time that changes and once the server listens (`Supervisor.tell()`), the server keeps it (`src/server/updates.ts`, `Updates`) for `GET /api/update`, and passes the chat's asks back (`update-check` with an id, `update-install`, which the supervisor emits as `request`); the app answers each check by its id (`answered`, `CheckAnswers`) in the first state it tells once no check is under way, so a state already on its way never ends a newer check. `installPlan()` says how this copy updates. `download()` streams the installer through `.part` and checks its SHA-256, and gives up after a minute without a byte (`DOWNLOAD_STALL_MS`), so a dropped connection does not hold the update and every check after it. `updateSystem()` picks the installer: the Apple Silicon one on macOS (none on an Intel Mac), the running app's processor's on Windows and Linux (`process.arch`: an x64 app emulated on Windows on Arm stays x64). Once the new version is downloaded and checked, `whenIdle()` waits until the server says no conversation has agents at work (`Supervisor.busy()` every 2 s; one that does not answer is asked again), the menu saying *Update ready: switches once replies finish*, or until the user chooses **Switch to the new version now…** (after a dialog). `busyWithoutAsking()` says what the app knows without asking: a server that stopped by itself (a crash) runs nothing, but one that starts or stops (a restart from the menu) gives no answer yet, and once the app quits (also as the system shuts down) there is never one, so quitting never switches. The running app is not touched until then: after the wait, an app that is quitting puts nothing in place and keeps this version, and the next start removes what was downloaded. On macOS `stageMacApp()` mounts the `.dmg` (`hdiutil`), copies the app next to the running one (`ditto`) and checks it (`codesign --verify --deep --strict`, its bundle id and version) before the wait, and after it `swapMacApp()` renames the two while the server still runs, so that a failed swap changes nothing; a shell started with `spawnDetached()` (`src/server/process.ts`) waits for the app to exit and `open`s the new one. Its script is fixed text: the app's pid and the new version's path reach it in its environment (`HARNESS_RELAY_RELAUNCH_PID`, `HARNESS_RELAY_RELAUNCH_TARGET`, removed before the new version starts), never in its text or its arguments. On Windows the installer runs with `--updated /S --force-run` once the app has quit. On Linux the new AppImage downloads hidden next to the running one (`appImageDownload()`; one left by a quit during the wait is removed at start, `removeAppImageLeftovers()`), is put in place after the wait (`appImageTarget()`, `placeAppImage()`), the autostart entry follows, and it is started once the app has exited. A copy that cannot update itself (`not-packaged`, `no-installer`, `no-checksum`, `read-only`, `not-appimage`) gets the release's page.
- **Its own check.** Started with `--smoke-test[=<report>]`, the app checks itself and exits with 0 or 1, without the single-instance lock and with a temporary user-data folder, so it runs beside a Harness Relay in use: the keyring module loads, the server starts in a utility process (port 0, `RELAY_KEYRING=off`), passes the checks of `selftest.ts`, says no conversation has agents at work, a hidden sandboxed window signs in with a link and shows the chat, and the server stops. `desktop/scripts/check-package.ts` runs it.

Building: `npm run desktop` and `npm run desktop:dist` build the UI (`npm run build`), then run `desktop/scripts/build.ts`, which writes `desktop/build/`:

- `app/` holds what Electron runs: `main.cjs`, its `package.json` (from `src/manifest.ts`; `productName` names the user-data folder `Harness Relay`) and the tray icons.
- `server/` holds the server, the UI and the keyring module.
- `resources/icon.png` is the app icon, for electron-builder.

`RELAY_VERSION` (set by the [Release workflow](#releasing)) builds the app as a release's version: its semver in `package.json` (see `semverOf()` in `scripts/release.ts`), the version itself in the menu, the log and a problem report (the server's bundle gets it as `__RELAY_VERSION__`, read by `src/server/about.ts`). Without it, the app is a build of the day in Taiwan, with `-dev` and the commit (`devVersion()`): `2026-11-10-dev (30f3d4f)`, as semver `2026.1110.0-dev`, which sorts before every release and release candidate of that day, so that one of that day or later is offered as an update.

`npm run desktop` then starts Electron on `build/app`. `npm run desktop:dist` runs `desktop/scripts/dist.ts`, which runs electron-builder (`desktop/electron-builder.yml`) and ends by naming the installer and the app to double-click: the installer for the system it runs on (`.dmg`, NSIS `.exe`, `.AppImage`) in `desktop/release/`, and the app itself next to it (`desktop/release/mac-arm64/Harness Relay.app`, say). `npm run desktop:dist -- --output <folder>` puts them elsewhere, to try a build without replacing an app in use. It refuses to start while a Harness Relay runs from the output folder (macOS and Linux, from `ps`; on Windows a running app keeps its files locked anyway), and at the end says when one runs from elsewhere: opening the new build would bring the running one forward instead. Building for another system or processor is not set up: build on each (the Release workflow builds the Arm64 installers on GitHub's Arm runners).

`npx tsx desktop/scripts/smoke.ts` runs the bundled server the way the app does, with plain Node standing in for Electron (`desktop/scripts/parent-port.mjs` gives it a `process.parentPort` over Node's IPC): the keyring module must load from next to the server, and the server must listen on 127.0.0.1, serve the UI, refuse the API until a browser signs in, give a sign-in link whose code works, print no code, say that no conversation has agents at work, and exit with code 0 when asked to shut down. CI runs it after building the desktop app, the Release workflow on each system, and `test/parent.test.ts` runs the same checks on `src/server/index.ts`.

`npx tsx desktop/scripts/check-package.ts [--dir <folder>]` checks the packaged app electron-builder left next to the installer (`desktop/release/` by default: `mac-universal/` or `mac-arm64/`, `win-unpacked/` or `win-arm64-unpacked/`, `linux-unpacked/` or `linux-arm64-unpacked/`): its fuses as `electron-builder.yml` sets them (read back with `@electron/fuses`), the server, the web app and the keyring module in its resources (both processors' native parts in a universal Mac app), and the app's own `--smoke-test`. On Linux it needs a display (`xvfb-run`) and runs the app with `--no-sandbox`. The Release workflow runs it on each system after making the installer, and CI on a Linux package (`electron-builder --linux dir`).

A few things to know:

- **electron-builder leaves out a `node_modules` folder** at the top of a folder it copies, whatever the filter says. So the keyring module is copied as an entry of its own in `extraResources`.
- **Fuses.** The packaged app turns off Electron's run-as-Node mode and `NODE_OPTIONS` / `--inspect` (`electronFuses`). Otherwise any program could run code as the app and use the privacy permissions macOS gave it. This is also why the shell's environment is read with `env -0` and not by running the app as Node. It loads its code only from its archive, and checks the archive (`enableEmbeddedAsarIntegrityValidation`, on macOS and Windows), and `file:` pages get no extra privileges (`grantFileProtocolExtraPrivileges: false`; the window shows only the server's pages). Cookie encryption stays off: the window's sign-in is in a folder agents below full access may not read, its key is in localStorage, which it would not encrypt, and on an app signed ad hoc macOS would ask for the keychain after every update. `check-package.ts` reads all of them back.
- **Signing.** On macOS the app is signed ad hoc (`mac.identity: '-'`, and `dist.ts` turns off electron-builder's search of the keychain), on every computer the same: never with a certificate electron-builder would otherwise find in your keychain. Its entitlements (`desktop/entitlements.mac.plist`) are electron-builder's defaults plus the microphone, which the hardened runtime refuses otherwise; Info.plist says why it asks (`NSMicrophoneUsageDescription`, translated in `desktop/macos/*.lproj/InfoPlist.strings`). Apple Silicon runs no unsigned code, and the fuses change the Electron binary after it was linked: an unsigned build is killed at launch (exit code 137). The ad-hoc signature is not trusted by Gatekeeper, so a downloaded app needs **Open Anyway**, and macOS asks again for the keychain after each update. Signing with a Developer ID and notarizing, and signing for Windows, are not set up yet. Updates are the app's own (`update.ts`), not electron-updater's, and rest on GitHub's checksums over HTTPS.
- **The Mac app is for Apple Silicon only** in a release (`--mac dmg --arm64`, the macOS runner's own processor): there is no app for Intel Macs, which run Harness Relay from the source. The website counts a Mac as one with Apple Silicon unless Chromium's hints say Intel (Safari and Firefox say "Intel" on every Mac); the app offers no update on an Intel Mac. The Mac apps of 2026-11-11 and its release candidate were universal and look for `-mac-universal.dmg`, so they do not find the releases after them. `npm run desktop:dist` builds for the Mac it runs on.
- **Windows and Linux have an installer per processor** in a release: x64 (`win-x64.exe`, `linux-x86_64.AppImage`) and Arm64 (`win-arm64.exe`, `linux-arm64.AppImage`). The Arm64 ones are built on GitHub's Arm runners (`windows-11-arm`, `ubuntu-24.04-arm`, free for public repositories), not cross-built, so that npm installs the keyring module's native part for Arm and the packaged app's own check runs there.
- **Linux AppImages** may need `--no-sandbox` where unprivileged user namespaces are restricted (Ubuntu 24.04). electron-builder's `executableArgs` only reach a `.desktop` file, not an AppImage started directly; the app passes the flag on to its autostart entry when it was started with it.
- **To try it apart from your own data**, run the built app with a user-data folder of its own and without opening its window, and give that folder a `desktop.json` with another port if a Harness Relay already listens on 8787: `desktop/node_modules/.bin/electron desktop/build/app --user-data-dir="$HOME/relay-desktop-try" --hidden` (not under `/tmp`: the server warns about a data folder in a temporary folder, which sandboxes let agents write in). The server's log is `~/Library/Logs/Harness Relay/server.log` on macOS, and `logs/server.log` in the user-data folder on Windows and Linux.

## Request flow

1. The client posts `POST /api/conversations/:id/messages` → `Orchestrator.send()` prepares the workspace (for edit / full access: `git init` if needed, and the directory lock unless the mode is parallel), appends the user message and starts `execute()` in the background (the request returns `202`).
2. In an auto-team conversation, a run for a new question only lets the lead agent design the team (`designTeam()`, see [Architecture → Auto team](architecture.md#auto-team)); the team answers in a run of its own once the design is confirmed. Otherwise `execute()` chooses speakers by mode (creating per-agent worktrees first in parallel mode) and calls `turn()` for each.
3. `turn()` creates a streaming agent message, records the starting state (worktree `HEAD` or a snapshot), computes the messages the agent hasn't seen, builds the prompt (`prompt.ts`), and calls `runners[provider].run()` in the right directory, passing `requestApproval` unless the conversation refuses automatically.
4. The adapter spawns the CLI (`process.ts`), parses each stdout line and emits `AgentEvent`s.
5. `turn()` applies events to the message (text, thinking, plan, tool rows and output), emits SSE events through the `Hub`, and saves through the `Store`. An approval request adds an approval part and waits for `POST …/approvals/:approvalId`. When the CLI exits it records the files changed (commit in the worktree, or a second snapshot) on the message.

## HTTP API

All write requests must send `Content-Type: application/json` (CSRF guard). Errors are `{ "error": string }` with status 400/404/409/415/500. Send `X-Relay-Lang: zh-TW | en` to get errors, system notes and built-in templates in that language (the web app always does).

Every request but `GET /api/auth` and `POST /api/auth/login` must come from a signed-in browser ([Architecture → Signing in](architecture.md#signing-in)): the `relay_session` cookie and the `X-Relay-Key` header. The routes the browser loads by itself (`BROWSER_LOADS` in `app.ts`: replies' media and downloads, attachments, `files/raw`, `files/download`, `files/zip`) take the cookie alone, and `…/events` takes the key as `?key=`. Otherwise the answer is 401 with `code: "signed-out"`. Tests that are not about signing in pass `auth: null` to `createApp()`.

## Adding a new agent CLI

1. **Types** — add the id to `Provider`, `PROVIDERS` and `PROVIDER_LABEL` in `src/shared/types.ts`.
2. **Adapter** — create `src/server/agents/<name>.ts`:
   - a `create<Name>Parser(emit)` (or update handler) that turns the CLI's output into `AgentEvent`s (`session`, `text`, `text_end`, `thinking`, `plan`, `tool_start`, `tool_end` with `output` / `error`, and `detail` when the CLI only says what a call was about once it is done) and remembers the final result/error;
   - an `AgentRunner` whose `run()` builds the arguments (prompt, system prompt, session new/resume, permission, model, effort), calls `runProcess()` and throws `AgentRunError` on failure (`aborted = true` when stopped);
   - approvals: when the CLI asks to do something the permission does not cover, call `o.requestApproval({ kind, detail, reason, tool })` and answer the CLI with the result (when `requestApproval` is absent, refuse).
   Keep the parser pure so it can be tested with recorded output lines.
3. **Register** it in `src/server/agents/index.ts`.
4. **Settings** — default binary name in `DEFAULT_BIN` and, if the CLI reads an API key from the environment, `API_KEY_ENV` (`src/server/settings.ts`).
5. **Status & login** — `checkAuth()` and `LOGIN_METHODS` in `src/server/providers.ts`; the logout command in `logout()`.
6. **Models** — a discovery function in `src/server/models.ts` (or a static list).
7. **UI** — a color variable in `styles.css` (`--<name>`), `PROVIDER_COLOR` and `newAgent()` in `src/web/util.ts`, API-key help text in both locale files (`settings.apiKeyHelp`).
8. **Messages** — login method labels in `src/server/i18n.ts` (`login`), in both languages.
9. **Bug report form** — the CLI's name among the `agents` options of `.github/ISSUE_TEMPLATE/bug_report.yml` (`test/community.test.ts` checks them against `PROVIDER_LABEL`).

## Database changes

The schema lives in the `MIGRATIONS` array in `src/server/db.ts`; `PRAGMA user_version` records how many have been applied. To change the schema:

1. **Append** a new SQL string to `MIGRATIONS` (never edit a released one).
2. Update the row types and queries in `store.ts` / `settings.ts`.
3. Add or update tests in `test/store.test.ts`.

Each migration runs in its own transaction at startup. node:sqlite cannot bind `undefined`; use `nul()` for optional values, and `transaction(db, fn)` for multi-statement writes (it doesn't nest).

To inspect data:

```bash
sqlite3 data/relay.db '.tables'
sqlite3 data/relay.db 'select seq, author_kind, agent_name, status from messages order by conversation_id, seq'
```

## Changing prompts

- `buildBriefing()` — the system-level briefing (role, team, mode rules, workspace). Rebuilt every turn. `scheduleRules()` explains messages a schedule sent (`via="schedule"`), and with `unattended` (the run refuses approvals) says so.
- `buildTurnPrompt()` — the per-turn message with `<chat>` and the cue line.
- `forwardText()` — how a reply is shown to other agents (text + `<actions>` log).
- `parseMentions()` — mention parsing; text may follow a name directly, and code spans and fenced blocks of any kind (also unclosed ones) are ignored.
- `buildPlannerPrompt()` / `PLANNER_BRIEFING` (`planner.ts`) — what the lead agent is asked in auto-team mode, and the JSON it must return. For a schedule's message (`schedule`) it says the team gets it on a schedule, unattended, and asks for members named after the names it @mentions.
- `buildRevisePrompt()` / `REVISER_BRIEFING` (`planner.ts`) — what the lead agent is asked when the user wants the team in the team drawer changed: the request, the team, the conversation so far, a waiting design (for a question or the schedule), the schedule's message; it must return the whole team, naming a renamed or moved member as `was` (never a new member) and giving a role only for a new member or one it rewrites. It also says when the schedule is off or was deleted, and which saved folder the lead works in when the drawer names another one.
- `buildGroupPrompt()` / `GROUPER_BRIEFING` (`grouping.ts`) — how the lead agent is asked to sort a new conversation into the user's groups.

Prompts are in English on purpose (agents reply in the user's language). User-facing text is translated — see [Translations](#translations).

## Translations

The UI and the server's user-facing text come in Traditional Chinese (`zh-TW`) and English (`en`).

- **UI strings** — add the key to `src/web/locales/zh-TW.ts` first: its shape is the `Messages` type. `en.ts` is typed `Messages`, so TypeScript reports a missing or mistyped English entry; text with values is a function (`(n: number) => …`). In components use `const t = useT()` (or `useI18n()` for the language and `setLang`). Code outside React gets the messages passed in (`relativeTime(ts, t)`, `conversationMarkdown(conv, t)`).
- **Server strings** — `src/server/i18n.ts` has both dictionaries; call `t()` where the text is produced. The language comes from the request (`X-Relay-Lang`) through AsyncLocalStorage and follows the runs the request starts, so do not cache translated text in long-lived objects.
- **Built-in templates** — `src/server/presets.ts` keeps names, descriptions and roles in both languages.
- **Another language** — add it to `Lang` / `LANGS` in `src/shared/types.ts`, add a locale file and a server dictionary, the template texts, and its detection rule in `browserLang()`.

`test/i18n.test.ts` checks that both UI dictionaries have the same shape (including list lengths, which types don't check).

The guided tour's steps are `tour.steps` in the locales; the element each step points at (its `data-tour` attribute) is `TOUR_TARGETS` in `src/web/components/Onboarding.tsx`, by step index. When you add, remove or reorder steps, change both locales and `TOUR_TARGETS` together. When you change the steps in a way worth seeing, raise `TOUR_VERSION` in the same file: the browser remembers which version was finished (`localStorage` key `relay:onboarded`), so people who finished an earlier one see the tour again once. `test/tour.test.ts` checks the target count and fails when the steps change, as a reminder: update the version and the fingerprint it prints (only the fingerprint for a typo fix).

## Testing

```bash
npm test               # all tests
npx vitest test/store.test.ts
```

The tests run on macOS, Linux and Windows (CI runs them on Linux and Windows). For a test to pass on each:

- Build paths with `join()` and `resolve()`, not as text with `/`: on Windows `/repo` resolves to `C:\repo`, or to the drive of the folder it is resolved from (GitHub's runners check the repository out on `D:`, with the temporary folder and the home folder on `C:`). A function that takes a `platform` builds that platform's paths (`posix` or `win32` from `node:path`), whichever system it runs on.
- Split a PATH with `delimiter` (`;` on Windows), and write a path into a git config file with `/`: the file reads `\` as an escape.
- Skip what only macOS or Linux have with `it.skipIf(process.platform === 'win32')` (or `describe.skipIf`): permission bits, POSIX signals and process groups, `/bin/sh`, and stand-in CLIs run by their `#!` line, which Windows cannot start.
- Leave time limits to `test/timeouts.ts` and `test/setup.ts`: `vi.waitFor` waits up to 5 s unless a test says otherwise (Vitest's own 1 s is too short for a run that records its changes with git while all the test files run at once), and on Windows, which starts processes and runs git several times slower, every test's limit and every wait is six times longer; a test that sets its own limit uses `slow(ms)`.
- Wait for what a test needs (`vi.waitFor`), not for a fixed time: Windows' timers tick every 15.6 ms.
- Windows' temporary folder may be named by its short 8.3 name (`C:\Users\RUNNER~1\…` on GitHub's runners), which `realpathSync` keeps and git and the system's own real path (`realpathSync.native`, `fs.promises.realpath`) spell out. `test/setup.ts` sets `TEMP` to the name spelled out, so the tests' folders are named as the folder dialog would name them.

`test/setup.ts` also removes every `RELAY_*` variable before a test file loads its modules, so a limit or a voice folder you set for your own Harness Relay does not change what the tests see; a test that needs one sets it itself. The end-to-end servers leave them out too (`e2e/support/relay.ts`), and a spec gives its own with `serverEnv`.

## End-to-end tests

```bash
npm run test:e2e:install                  # once: the Chromium Playwright drives (Linux: npx playwright install --with-deps chromium)
npm run test:e2e                          # every spec in e2e/specs/, in Chromium
npx playwright test e2e/specs/chat.spec.ts
npx playwright test -g approvals          # by title
npx playwright test --ui                  # pick and watch tests in Playwright's window
npx playwright show-report                # the last run's report, with the traces of failed tests
E2E_BROWSERS=chromium,firefox,webkit npm run test:e2e   # after npx playwright install firefox webkit
```

They drive the UI in a real browser ([Playwright](https://playwright.dev), [`playwright.config.ts`](../playwright.config.ts)) against the real server, `src/server/index.ts` with the built UI, so the routes, sign-in, SSE, the orchestrator, the adapters and the workspace's git are tried together, as a person uses them. The agents are fake CLIs, so the tests stay offline and cost nothing, and they run the same on macOS, Linux and Windows.

- **Each test has a server of its own** (`e2e/support/relay.ts`, the `relay` fixture in [`e2e/fixtures.ts`](../e2e/fixtures.ts)): on a free port (`PORT=0`), with a temporary folder for its data (`RELAY_DATA_DIR`), a home (`HOME`, `USERPROFILE`), the CLIs' homes (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `GROK_HOME`) and the default working directory (a small project, `seedProject()`), and `RELAY_KEYRING=off`: nothing of your own Harness Relay, CLIs or keychain is read or changed. The fixture reads the sign-in link the server prints. The `page` fixture opens the link of a new code, so it starts signed in, with the tour done and the UI in English; `test.use()` changes that (`lang: 'zh-TW'`, `signIn: false`, `tour: true`) or adds environment for the server (`serverEnv`). `relay.api()` calls the API as a signed-in browser, to set things up or check what was stored, and `relay.fakeLog()` returns what the fake CLIs were started with and given. A failed test gets the server's output and the fake CLIs' log attached, besides its trace, screenshot and video.
- **The fake CLIs** ([`e2e/fake-cli/fake-cli.cjs`](../e2e/fake-cli/fake-cli.cjs), one CommonJS file using only Node's built-ins) speak each CLI's protocol as the adapters drive it: Claude Code's stream-json with its control requests and `can_use_tool`, `codex app-server`, and Grok's ACP; and they answer the probes (`--version`, the sign-in status, the models, `grok inspect --json`). The server finds them first on its PATH, by name, as it finds the real ones. On macOS and Linux each one is the script with a `#!` line for the Node that runs the tests. Windows starts only real programs (`.exe`) without a shell, so there `e2e/support/fake-cli.ts` makes the script a Node single executable application (`node --experimental-sea-config`, then `postject`), copied under the three names. That takes a few seconds and about 100 MB, so it is kept in `node_modules/.cache/harness-relay-e2e/` until the script or Node changes. `E2E_FAKE_SEA=1` builds them that way on macOS and Linux too. On Windows postject warns `The signature seems corrupted!`: injecting the script breaks `node.exe`'s Authenticode signature, which the copy does not need.
- **What the fakes answer** depends on the prompt, as a model's would. The lead agent's prompts get a team (`e2e:team=claude,codex,grok`, `e2e:mode=relay`, `e2e:rounds=2`, `e2e:name=Some_name`, `e2e:template=<id>`, `e2e:badplan` for an answer that is not JSON; one Claude member by default), a group (the first group that the first message names) and a changed team (`e2e:add=<cli>` adds a member). A turn gets `Hello from <name> (<CLI>). You said: “<the user's latest message>”.`, with the images and the tool library's MCP servers it got, streamed in pieces and changed by directives in that message: `e2e:think`, `e2e:tool`, `e2e:todo`, `e2e:approve` (a command that needs approval), `e2e:write=<path>` and `e2e:writeother=<path>` (in the first other working directory the CLI was given), `e2e:ask`, `e2e:handoff=<Name>`, `e2e:slow`, `e2e:fail` (exits with an error), `e2e:error` (fails inside the protocol), `e2e:flaky` (fails once, answers the retry) and `e2e:markdown` (`DIRECTIVES` in the script). `@<cli>` after a directive keeps it to that CLI: `e2e:write=a.txt@codex`. A later round with nothing new from the user is `[PASS]`. Like a model that ignores its briefing, a fake always tries what a directive asks, and whether it happens depends only on what Harness Relay gave the CLI: Claude Code's `--permission-mode`, `--disallowedTools` and `--add-dir` folders, Codex's sandbox or permission profile (with its `write` entries; `writable_roots`) and approval policy, Grok's yolo mode and the `read_write` folders of its sandbox profile (without a sandbox, in yolo mode and on Windows, the other working directories its briefing names), and the answers to each one's approval requests (a decline's note is passed on). So a test that writes in a read-only chat or in another folder tells whether the adapter set the CLI up right. The fakes keep their sessions in their homes and refuse to resume one they never started, as the real CLIs do. `E2E_FAKE_SIGNED_OUT=codex,grok` (through `serverEnv`) signs those CLIs out.
- **The fake folder dialog** ([`e2e/fake-cli/fake-dialog.cjs`](../e2e/fake-cli/fake-dialog.cjs)) is installed with them as `zenity` on macOS and Linux. Linux looks for its dialog on the PATH in a graphical session, so a test that sets `DISPLAY` (through `serverEnv`) gets the box's folder button, and the fake answers with the folders `E2E_FAKE_PICK` lists (JSON, each resolved from the folder it opens at), or is cancelled when it lists none. Its arguments and character set go to `relay.fakeLog()` (`cli: 'zenity'`). macOS and Windows open their own dialogs by their full paths, so those tests run on Linux only.
- **Before the tests**, [`e2e/global-setup.ts`](../e2e/global-setup.ts) builds the UI when a file it is built from is newer than `dist/web` (`E2E_BUILD=always` builds it every run, `E2E_BUILD=never` never does) and installs the fakes.
- **Writing a test**: in `e2e/specs/<area>.spec.ts`, import `test` and `expect` from `../fixtures`, and the steps from [`e2e/support/app.ts`](../e2e/support/app.ts) (`startChat`, `send`, `confirmTeam`, `finishedReply`, `openTeamChat` for a chat with a team of its own, made through the API, and so on). Find elements by their role and visible text where the UI gives them (English unless the test changes the language), CSS classes only otherwise. Something new an agent should do goes in the fake as a new directive.

Current specs:

- `e2e/specs/chat.spec.ts` — a new chat: the lead agent's team card, confirming it and the reply; teams used without asking; a team of all three CLIs answering in order; a follow-up question with a team of its own.
- `e2e/specs/activity.spec.ts` — each CLI's thinking, tool call (with its output) and to-do list; a reply in Markdown (heading, list, table, code).
- `e2e/specs/approvals.spec.ts` — each CLI asking before a command: allowed (it runs), declined with a note (shown on the card, and passed on to Claude Code and Grok); "Always allow" answering the next request by itself; stopping while a request waits; full access running and writing anywhere without asking; a chat that refuses automatically.
- `e2e/specs/files.spec.ts` — edit mode: a file written, `git init`, the changes card and the turn's diff; each CLI in a read-only chat writing nothing (Claude Code without its file tools, Codex and Grok asking and declined), and Grok's reason when refused automatically; each CLI's turn recording its own change; parallel mode's worktrees and applying one result; the file browser and a file's preview.
- `e2e/specs/folders.spec.ts` — in edit mode, a folder the chat was not given staying out of each CLI's reach when refused automatically, and Claude Code and Codex writing there once the user allows it; several working directories: folders added and removed in the box, each CLI writing in each folder with the changes card listing them by folder (Grok on Windows told them by its briefing alone), the file browser's folders, parallel mode's worktree of each folder applied together, and Settings' default working directories. On Linux, the folder dialog (the fake zenity): the folders chosen in it added to the box and the chat starting in them, the dialog opened inside the last folder with several allowed, and in Chinese on a server without a UTF-8 locale its Chinese title and `LC_CTYPE=C.UTF-8`, with Cancel adding nothing.

- `e2e/specs/team.spec.ts` — the lead agent adding a member when asked in Team settings, and the new member answering once saved; a template standing in when the lead agent's answer cannot be read; a team proposed for a new question declined, and the current team answering.

- `e2e/specs/sidebar.spec.ts` — a group and the lead agent sorting a new conversation into it, renaming and deleting, search by what an agent wrote, a title given at the start.
- `e2e/specs/templates.spec.ts` — the built-in templates and their members, the lead agent using one as it is, saving a designed team as a template.

- `e2e/specs/settings.spec.ts` — each CLI's version and sign-in, an executable path (a wrong one shows the CLI missing), the language kept after a reload, another CLI chosen as the lead agent; a CLI that is not signed in (Settings, the sidebar, and its reply's error).

## Continuous integration

[`.github/workflows/ci.yml`](../.github/workflows/ci.yml) runs on every pull request and every push to `main`: `npm ci`, `npm run typecheck`, `npm test` and `npm run build`, on Ubuntu with Node 22 (the oldest supported) and Node 24, and on Windows (`windows-latest`) with Node 24. On Ubuntu it also installs the desktop app's tools (without the Electron binary), typechecks the desktop app, builds it (`desktop/scripts/build.ts`) and runs its bundled server as the app does (`desktop/scripts/smoke.ts`). A second job (`desktop-package`) packages the desktop app for Linux without an installer (`electron-builder --linux dir`), for x64 and on GitHub's Arm runner for Arm64 as a release does, and checks it as a release is checked (`desktop/scripts/check-package.ts`, on a virtual display, with Electron's own libraries installed where the runner lacks them). Releases have a workflow of their own: see [Releasing](#releasing). A new push to a pull request cancels its previous run. Run the same commands locally before pushing.

[`.github/workflows/e2e.yml`](../.github/workflows/e2e.yml) runs the [end-to-end tests](#end-to-end-tests) (`npm run test:e2e`, Chromium) on Ubuntu, macOS and Windows with Node 24, and on Ubuntu with Node 22 too, for every pull request and every push to `main`; run it by hand (**Actions → End-to-end tests → Run workflow**) to choose other browsers. Each run uploads the HTML report, with the trace, screenshot, video and logs of each failed test (`e2e-report-<os>-node<version>`).

To block merging until the checks pass, add a branch protection rule (or ruleset) for `main` in the repository settings and require the `Typecheck, test, build` checks (and `End-to-end` ones, if you want them too).

### Website

The landing page at https://agentic-system-lab.github.io/harness-relay/ is plain HTML, CSS and JavaScript in [`site/`](../site/): `index.html` (English), `zh-TW/index.html` (繁體中文) and shared `assets/`. There is no build step. [`.github/workflows/pages.yml`](../.github/workflows/pages.yml) runs on pushes to `main` that touch `site/`, `docs/media/` or the workflow itself: it copies `site/` and the demo videos from `docs/media/` into one folder, leaves out Markdown files, and deploys it to GitHub Pages (repository settings → Pages → Source: GitHub Actions). Preview it with `npm run site:preview` ([`scripts/preview-site.ts`](../scripts/preview-site.ts)): it serves `site/` on http://127.0.0.1:4180 (`SITE_PORT` changes the port) with the videos read from `docs/media/`, the way Pages will. Read [`site/DESIGN-GUIDELINES.md`](../site/DESIGN-GUIDELINES.md) before changing the page; it also says what to update when the demo is re-recorded.

### Recording the demo

The demo in the READMEs and on the landing page (`docs/media/demo-*.mp4` and `.webp`) is a real run, recorded by `npm run demo` ([`scripts/demo/`](../scripts/demo/)). Record it again when the UI it passes through changes. It needs the three CLIs installed and signed in, FFmpeg and libwebp (`brew install ffmpeg webp` on macOS), and the Chromium that `playwright-core` drives (`npx playwright-core install chromium-headless-shell` once, or `DEMO_CHROME` set to a Chrome or Chromium binary).

```bash
npm run demo                          # record both languages, cut them and publish them
npm run demo -- record --dry          # check the UI flow up to the open chat, no agents (under a minute)
npm run demo -- record --lang en      # one step, one language
npm run demo -- cut publish           # cut and publish the last recordings again
```

1. **record** builds the UI and starts Harness Relay on its own port (8791, and 8792 for the second language) with an empty data folder in `data/demo/<lang>/`, so your own conversations and settings are left alone; this repository is the chat's working directory, read-only. A headless browser then does what a person would, with a drawn cursor: a new group, the Three-way debate template, a new chat and a question that names all three CLIs, the lead agent's team (confirmed), the answers (a request beyond read-only is shown and declined, a question the agents ask is skipped), a follow-up question with a team of its own, Files at relay mode's hand-off in `orchestrator.ts`, and a search. Both languages record at once, about half an hour with the real CLIs. Each step leaves a mark in `marks.json`.
2. **cut** speeds the agents' work up so the video lasts about two minutes (`--length`), and writes `video.mp4` (1600×1000, 24 fps), `animation.webp` (880×550, 8 fps) and `timeline.json`. If the recorder waited for nothing, add a `skip-start` / `skip-end` pair to `marks.json` and cut again.
3. **publish** copies the video and the animation into `docs/media/`, re-cuts the posters, the screenshots and the social cards from the frame where the first team's card shows (the `poster` mark), re-times the chapter rails in `site/index.html` and `site/zh-TW/index.html` and the frame times in `site/DESIGN-GUIDELINES.md`, and writes `data/demo/<lang>/review.md`: the chapters as written, the teams, any approval, the search term and the replies.

Then read `review.md` and watch the videos. The chapter sentences are in `scripts/demo/chapters.ts`; the teams, names, rounds, the group and the search term are filled in from the recording, but when the agents did something the sentences don't describe, change them there and run `npm run demo -- publish`. Check the READMEs' captions and the rail notes too, then commit the media, `site/` and the scripts together.

## Releasing

A release is the desktop app's installers for macOS (a `.dmg` for Apple Silicon), Windows (x64 and Arm64 `.exe`) and Linux (x64 and Arm64 `.AppImage`), published together as one GitHub release by the Release workflow ([`.github/workflows/release.yml`](../.github/workflows/release.yml)). It is run by hand; nothing else makes releases or tags.

**Versions** are the day of the release in Taiwan (`RELEASE_TIME_ZONE`, Asia/Taipei), and the git tag is the version itself:

| Version | Is |
| --- | --- |
| `YYYY-MM-DD-rc` | a release candidate of the day's release, published as a pre-release |
| `YYYY-MM-DD-rc.1`, `.2`, … | that day's patches of it |
| `YYYY-MM-DD` | a release |
| `YYYY-MM-DD.1`, `.2`, … | that day's patches of it |
| `YYYY-MM-DD.1-rc`, `YYYY-MM-DD.2-rc`, … | a release candidate of that patch, published as a pre-release |
| `YYYY-MM-DD.1-rc.1`, `.2`, … | that day's patches of it |

A fix on a later day is that day's release, not a patch. A release candidate is optional, and is always one of the day's next release: the release itself until it is out, then its next patch (`npm run release:next` prints both). One of a release that is out is refused: it would sort before that release (`2026.1110.0-rc.2` < `2026.1110.0`), and the download page, which offers the newest release by publish time, would show it instead (the app, which goes by version, would never offer it). A release candidate of a patch sorts between the release before it and the patch (`2026.1110.0` < `2026.1110.1-rc` < `2026.1110.1-rc.1` < `2026.1110.1`), so both find the same newest one.

**To release:**

1. On `main`, see today's next versions: `npm run release:next` (it reads the tags on GitHub).
2. In GitHub, open **Actions → Release → Run workflow**, keep **Use workflow from: main**, enter the version, and run it.

`npm run release:check -- <version>` checks a version locally the same way (against your local tags; `npm run release:check -- <version> --remote` for GitHub's: without the `--`, npm keeps `--remote` for itself).

**What the workflow checks** (`scripts/release.ts`, tested in `test/release.test.ts`), before it builds anything:

- the version follows the rules, with a precise reason when it does not: a `v` in front, `-RC` in capitals, `-rc1` without the dot, `.0`, `.01`, one-digit months or days, a day that is not in the calendar (`2026-02-30`), spaces, or a character that only looks like one (a full-width digit, an en dash, a non-breaking hyphen);
- its date is today in Taiwan, not yesterday or tomorrow (also around midnight UTC, when the two days differ);
- it is the next one: not released already, no patch before the release it patches, no skipped number, a release candidate only of the day's next release (none of a release that is out or of a later patch than the next). The error says which versions today takes;
- the run is on `main`.

Then it runs the typecheck and the tests, builds the five installers in parallel, the Arm64 ones on GitHub's Arm runners (each runs `desktop/scripts/smoke.ts` on its bundled server first, and `desktop/scripts/check-package.ts` on the packaged app after: fuses, resources and the app's own `--smoke-test`, under `xvfb-run` on Linux), checks the version again against the tags as they are now (a run that started before midnight keeps its day), checks that there is exactly one installer for each end of name in `INSTALLERS` (`site/assets/downloads.js`, which the website and the app's updates look for) and nothing else, copies each one for the app's updates (`updateCopyName()`: `…-mac-arm64-update.dmg` and so on, which the app downloads instead, so that the download counts tell updates from new installs; the website never offers them. Apps released before the copies still download the installers, so their updates count as installs until their users have updated once), and publishes the release on the commit it built, with the installers named `Harness-Relay-<version>-<os>-<arch>.<ext>`, notes generated from the merged pull requests, and the install notes (the systems each installer needs, the first-run warning on each system, `--no-sandbox` on Ubuntu 24.04, who is offered it: an installed Harness Relay, in its menu and its chat, a release candidate only to release candidates and builds of your own; and what the `-update` files are). Only one release runs at a time, and only the publishing job may write to the repository. The version reaches the scripts through the environment, never in a command line.

**Download counts.** GitHub counts each installer's downloads (not installs, and repeated downloads count again):

```bash
gh api repos/Agentic-System-Lab/harness-relay/releases --paginate --jq '.[] | .tag_name as $t | .assets[] | "\($t)\t\(.name)\t\(.download_count)"'
```

## Debugging tips

- **Server logs** — the `[server]` lines in the `npm run dev` output; adapter failures include the CLI's stderr tail in the message's error.
- **SSE** — `curl -N -b 'relay_session=<cookie>' 'http://127.0.0.1:8789/api/conversations/<id>/events?key=<key>'` shows the raw event stream under `npm run dev` (8787 under `npm start`). Take the `relay_session` cookie and the key (`relay:key` in localStorage) from a signed-in browser's developer tools.
- **Language** — add `-H 'X-Relay-Lang: en'` to a `curl` call to see the English errors and templates.
- **Auto team** — the lead agent's run is a normal CLI session in the conversation's working directory; its reply and its cost are on the plan message (`messages.plan`, `cost_usd`).
- **Reproduce a CLI call** — the adapters' argument lists in `src/server/agents/*.ts` can be run by hand; add `--debug` (Claude, Grok) to see more.
- **Worktrees** — `git -C <working dir> worktree list` and `git branch --list 'relay/*'` show what parallel conversations created; `data/worktrees/<conversation>/` holds the checkouts.
- **Voice input** — `GET /api/voice` shows what is installed and the last install's log; the engine runs as `whisper-server` (see `ps`) and stops after 10 idle minutes. Downloads go to `data/voice/` (`models/`, and `engine/` on Linux and Windows), or to the folder `RELAY_VOICE_DIR` names; the log shows the address of each download.
- **Stale session** — with the server stopped, delete the agent's row in `agent_sessions` to force a fresh session with full history (open conversations are cached in memory, so edit the database only while the server is down).

## Conventions

- Strict TypeScript; shared types only in `src/shared/types.ts`.
- Never send secrets to the client (`SettingsView` returns masked keys only).
- New write endpoints automatically get the JSON content-type and Host/Origin checks from the `/api/*` middleware — keep it that way.
- Spawned processes go through `process.ts` so they are tracked and killed on shutdown.
