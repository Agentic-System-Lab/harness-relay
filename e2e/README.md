# End-to-end test scenarios

What the end-to-end tests (`npm run test:e2e`) try today, area by area. They drive the built UI in a real browser ([Playwright](https://playwright.dev)) against the real server, with a fake for each of the twelve agent CLIs (Claude Code, Codex, Grok, Cursor, Antigravity, Copilot, Muse Code, and the five open agents: OpenCode, Goose, Cline, OpenHands and Pi), so they run offline, cost nothing and run on macOS, Linux and Windows alike, but for what each system's sandboxes allow ([Platforms and browsers](#platforms-and-browsers)).

How they work, how to run one and how to write one is in the developer guide, [End-to-end tests](../docs/developer-guide.md#end-to-end-tests). This page is the list of scenarios: when you add, change or remove an end-to-end test, change this page and [its Chinese copy](README.zh-TW.md) in the same commit ([AGENTS.md](../AGENTS.md), "Documentation").

There are 640 tests in 54 spec files, in each browser that runs them (Chromium by default). Some run only on some systems, or only where Harness Relay's own sandbox works: see [Platforms and browsers](#platforms-and-browsers).

## Running them

```bash
npm run test:e2e:install                      # once: the Chromium Playwright drives
npm run test:e2e                              # every spec, in Chromium (builds the UI first when it is out of date)
npx playwright test e2e/specs/approvals.spec.ts
npx playwright test -g "relay mode"           # by title
npx playwright test --ui                      # pick and watch tests in Playwright's window
```

The developer guide has the rest (other browsers, the report, the variables they read).

## What every test starts with

- **A server of its own** on a free port, with temporary data, a temporary home, the CLIs' homes (`.claude`, `.codex`, `.grok`, `.gemini`, `.copilot`, `.config/cursor`, and Muse Code's `.config/muse` and `.local/share/muse` in that home, the open agents' in the data folder) and the OS keyring off: nothing of your own Harness Relay, CLIs or keychain is read or changed, your credentials (Cursor's, Antigravity's and Google's too) are left out of its environment, and git looks for a repository no further up than the test's folder ([`support/relay.ts`](support/relay.ts)). On macOS and Linux its folder is in `/tmp` (or `E2E_TMP_DIR`), whose path is short enough for the sockets of Harness Relay's own sandbox.
- **A fake model endpoint** of its own: a small HTTP server set up as the model backend `e2e` (**Settings → Model connections**) with the models `e2e-model` and `e2e-model-mini`, and `e2e/e2e-model` as each open agent's default model, so the open agents a test installs are ready (OpenHands with its terminal switch on). The server lists those two models, serves `unlisted-model` by ID, and collects the log lines from sandboxed fakes. A test can start without it (`openBackend: false`), with OpenHands' switch off (`sandboxTerminal: false`), or with CLIs not installed (`missingClis`).
- **A working directory** with a small project in it: `README.md`, `src/hello.ts` and `src/lib/math.ts` (`seedProject()`). A test that needs other folders adds them next to it (`relay.addProject()`).
- **A browser page signed in** with a new one-time code, the guided tour done, the sandboxes' setup answered (so New chat asks nothing, whatever the computer lacks) and the UI in English ([`fixtures.ts`](fixtures.ts)). A test changes that with `test.use()`: `lang: 'zh-TW'`, `signIn: false`, `tour: true`, `sandboxAsk: true`, or more environment for the server (`serverEnv`).
- **Fake CLIs** ([`fake-cli/`](fake-cli/)), one for each of the twelve. A test server has Claude Code, Codex and Grok installed, and the CLIs the test is about (a test of each CLI its own, a test of the two teams its team's, `withClis()` in [`support/clis.ts`](support/clis.ts) any other): the others are not installed there, as the server asks every installed CLI for its version, sign-in, models and what it loads by itself whenever a page opens, some six starts each. They speak each CLI's protocol and answer `Hello from <name> (<CLI>). You said: “<the user's latest message>”.` The test steers them with `e2e:` directives in the message (`e2e:write=notes.md`, `e2e:approve`, `e2e:slow`…). A fake always tries what a directive asks, and whether it happens depends only on what Harness Relay gave the CLI (its permission, flags and settings, sandbox, folders and the answers to its approval requests), so a test that writes where it may not tells whether the adapter set the CLI up right. The fakes of Claude Code, Codex, Grok, Copilot and Muse Code work out what their CLI's own sandbox would allow; Cursor's and Antigravity's, which have no sandbox, ask as the real ones do; the open agents' fakes write and reach hosts for real, so below full access what is not theirs is refused by Harness Relay's own sandbox itself (on macOS and Linux). A fake inside it cannot write the fakes' log, so it sends its lines to the fake endpoint.
- **A fake `gh`** ([`fake-cli/fake-gh.cjs`](fake-cli/fake-gh.cjs)) for sharing, a problem report's screenshots and an automation that waits for GitHub: it keeps its gists in the test's own folder (`fake-github/`), never on GitHub, lists the pull requests and runs a test writes there (`fake-github/repos/<owner>/<name>/pulls.json`, `runs.json`), and `E2E_FAKE_SIGNED_OUT=gh` signs it out, until its own sign-in (`auth login --web`) is approved by the test. On Linux, a fake folder dialog (`zenity`) too. AgentsView is a small HTTP server inside [`specs/sessions.spec.ts`](specs/sessions.spec.ts), as Harness Relay only sends it requests.
- **A fake PowerShell** ([fake-pwsh.cjs](fake-cli/fake-pwsh.cjs)) gives Teams tests isolated Graph device sign-in, channel reads and posting in each test’s process and folder.

In the tables below, the CLI column says which CLIs a test runs with: **each** means once for each of the twelve; **each with a sign-in** once for each of Claude Code, Codex, Grok, Cursor, Antigravity, Copilot and Muse Code; **each open agent** once for each of OpenCode, Goose, Cline, OpenHands and Pi; and **two teams** that the test runs twice, with a team of the seven with a sign-in and with a team of the five open agents (its title then starts with `open agents:`). Where a CLI runs only with full access (the open agents on Windows, OpenCode on Linux), a test about permissions skips it, saying why, and any other test runs it with full access. On CI, a CLI's own tests (each, and its place in the two teams) run on macOS and Windows only for the CLIs Harness Relay runs differently there than on Linux: see [Platforms and browsers](#platforms-and-browsers).

## Documentation contents

The website’s own files exercise deep links and keyboard disclosure in the Chinese tools guide, active subsections while scrolling the English phone guide, and opening a Google setup guide with JavaScript disabled. Scrolling collapses the previous automatic branch without moving the article text on a phone. Manual choices and branches containing keyboard focus stay open. Phone and tablet checks cover the sticky contents row, keyboard focus at the destination, long lists with their own scrolling, switching between contents, search and the page list, and resizing to desktop. A delayed breakpoint notification checks that resizing preserves focus in search or the article and moves it only when a focused contents control disappears. The page menu is tested at 390, 1024 and 1366 CSS pixels with pointer hit tests across the whole covered row and keyboard focus checks.

## Signing in

[`signin.spec.ts`](specs/signin.spec.ts): a browser that has not signed in (`signIn: false`). The last four also in a development build of the UI (React's StrictMode, which runs each effect twice), which `global-setup.ts` builds next to the usual one.

| Scenario | What is checked |
| --- | --- |
| A browser that is not signed in gets the sign-in page, and a code signs it in | The sign-in page shows and the API answers 401; a wrong code says it is wrong or has expired; a new code opens the app on its home page, and the session outlives a reload. |
| A sign-in link signs in once; the code cannot be used again | `/#code=…` signs in and the code leaves the address bar; the same link in another page shows its error. |
| A link opened in a tab that shows the sign-in page already signs it in | The tab goes from the sign-in page into the app. |
| A link's error does not come back after signing in with a code and being signed out | Once signed out again, the sign-in page has no stale error. |
| A sign-in link opened in a tab signed in already keeps it signed in, with requests still on their way | Requests sent with the old key that answer "signed out" arrive with the sign-in's answer, and the page never signs out. |
| A tab that shows the sign-in page follows a sign-in in another tab of the browser | It opens the app without a code of its own. |
| A sign-in link opened in another tab keeps every tab signed in, with requests still on their way | The first tab stays in the app. |
| A tab still on its first check follows a sign-in in another tab | Its first answer is stale by then, and it signs in anyway. |
| A sign-in that gets no answer is given up after 30 seconds, with a message | With the page's clock run forward, the sign-in page says why. |
| A browser signs itself out in Settings | **Settings → Signed-in browsers** lists "this browser"; **Sign out** goes back to the sign-in page. |
| In a development build: a sign-in link opens the app on the first load, asking once whether the browser is signed in | StrictMode's second run of the effect does not ask again or lose the code. |
| In a development build: a link opened in a tab signed in already, or in another tab | As above, with StrictMode. |
| In a development build: a link that does not work shows its error on the first load | The error is on the sign-in page. |

## The home page

[`home.spec.ts`](specs/home.spec.ts)

| Scenario | What is checked |
| --- | --- |
| New chat and New automation keep their actions visible (2 scenarios) | The submit button stays at the card’s bottom. The controls have equal space above and below, with and without the scroll arrow. The team choices and lead review scroll with the fields. Short cards fit their contents. A long description scrolls inside its text box. The form scrolls independently. Its arrow scrolls the form, disappears when the last field is visible, even with a little blank padding still below, and stays still, centred in its circle, with reduced motion. |
| Start a question from the collapsed home page | An empty, whitespace-only or cleared question keeps Send question disabled, even with a file attached. At phone width, Tab moves from the question to Common apps, the first button below it. Enter opens the inline chooser. Checking and unchecking apps changes the requested-apps line. Visiting connection settings keeps the choices, question and attachment without starting a chat or changing any assistant grants. The selected app is included in the sent message. A visit to lead settings also preserves the title, folders, permission and team confirmation. Sending posts one message with the file, the home page links to the waiting team, and the next chat shows the saved confirmation preference. |
| A slow creation from New chat or New automation (one scenario per form) | A rejected request keeps the draft, its visible lead review choice and error across Settings. A successful retry leaves Settings in front. At phone width the link there opens the created item, including the automation’s one-time webhook token. |
| The app opens on it, and the logo and name lead back to it | The home page shows the logo and its tagline; the sidebar's logo and **Harness Relay** (marked as the current page there) go back to it from the New chat page and from a chat (`#/`). |

## Platforms and browsers

- [Installing Git](#installing-git) exercises the missing-Git and Windows Git Bash flows on every tested platform through simulated API responses.
- [`.github/workflows/e2e.yml`](../.github/workflows/e2e.yml) runs every spec in Chromium on Ubuntu, macOS and Windows with Node 24, and on Ubuntu with Node 22, for each push to `main`, and for each pull request that touches a file they depend on (`scripts/ci-scope.ts`: not for one that changes the docs, the unit tests, the desktop app or the landing page alone; a run by hand always runs them): each in two jobs, half the tests each (Playwright's `--shard=1/2` and `2/2`), so that no job runs much over seven minutes. Run it by hand to choose other browsers; locally, `E2E_BROWSERS=chromium,firefox,webkit` ([`playwright.config.ts`](../playwright.config.ts)). On Ubuntu it installs what Harness Relay's own sandbox needs (bubblewrap, socat and ripgrep, and the AppArmor profile that lets `/usr/bin/bwrap` make its namespaces), on Ubuntu it runs the sandbox's own checks (`scripts/sandbox-check.ts`) first, and it sets `E2E_REQUIRE_RELAY_SANDBOX=1` there, so a test that needs the sandbox fails rather than skips.
- The open agents run below full access on macOS and Linux only (Linux with bubblewrap, socat and ripgrep): on Windows, which Harness Relay's own sandbox does not cover, they run with full access only, and so does OpenCode on Linux. There the tests about permissions skip them, saying why, the others run them with full access, and [Harness Relay's own sandbox](#harness-relays-own-sandbox) checks that a chat below full access does not start them. Without the sandbox on a Mac or Linux computer, the tests that need it are skipped, saying why (`E2E_RELAY_SANDBOX`, which `global-setup.ts` works out once).
- On CI (`E2E_SYSTEM_CLIS=1`) each CLI's own tests run on Linux for all twelve, and on macOS and Windows only for the CLIs Harness Relay runs differently there than on Linux in a way their fakes can tell (`testedOn` in `support/clis/<cli>.ts`, which says why); elsewhere they are skipped, saying where they run. **macOS**: the five open agents (Harness Relay's own sandbox as Seatbelt makes it, OpenCode below full access there only, OpenHands' terminal switch) and Claude Code, for the seven with a sign-in, whose fakes do there what they do on Linux. **Windows**: the seven with a sign-in (Claude Code without sandbox settings, Codex without a permission profile, Grok's `workspace` profile, Cursor's sessions linked as a junction, Antigravity's home given as `USERPROFILE`, Copilot's folders linked as junctions, Muse Code's sign-in copied and its PowerShell), OpenCode and Goose (their own shell) and OpenHands (its PowerShell terminal); not Cline or Pi, which run there with full access only, as on Linux with full access ([CLIs that are scripts on Windows](#clis-that-are-scripts-on-windows) still starts them there). ## What they do not cover

- **A hand-over's window, and its screencast below full access.** No spec opens the window on the computer Harness Relay runs on (it would open on the developer's screen): its launch arguments and environment, where it is offered and the hand-over's ticket are in `test/handover.test.ts`, and it was tried by hand on a Mac (the window at the page, a `chrome://` page and a file sent back, a new tab closed, a sign-in's session cookie kept after the window closed). Nor do the specs answer a question about a new host from the panel, a real input method's composition (they insert its text), a paste, or a site that takes the browser for an automated one; nor, in the browser for the user alone, a page on another host here (refused) or a selection in a field (both in `test/browser.test.ts`), or **Drag to select** on a phone.
- **Most of long-term memory.** End-to-end tests save, recall, set aside, restore, pin and tidy notes, and switch memory off. The following cases are covered offline (`test/memory.test.ts`, `test/orchestrator-memory.test.ts`): corrections and forgets, notes waiting for the user (review), the user's own notes kept from agents, a note of one folder, recall once per session, automatic tidying and the rules its changes follow.
- **Most of secrets and fixed commands.** End-to-end tests give a secret, save, try and share a fixed command and send one run from the outbox, with Claude Code's fake only: the blocks are plain text the server reads, so every CLI's reply is read the same way. - **Most of team checks.** End-to-end tests exercise the editor, protected paths, commands and hooks with Claude Code's fake where a CLI is needed. The following cases are covered offline: the commit format, a member's worktree in parallel mode, a run that stopped to ask, the lead review reading the result, an automation's run nobody watched, a template's list copied into a chat, commands held back by changed settings, Check again running them in the background and the commands run in a check tree when a parallel result is applied (its dependencies linked in) (`test/orchestrator-checks.test.ts`, `test/checks.test.ts`, `test/checkCommands.test.ts`), as is each CLI writing a protected file (the checks read the disk, whatever wrote it). The two openings a command can have (every local port on macOS, every Unix socket on Linux) are tried only by hand, as `scripts/sandbox-check.ts` does not run a check's command.
- **Two chats in one folder with every CLI, and what comes after.** The end-to-end test runs Codex in the team's own worktree; that each CLI writes in a worktree is [parallel mode](#files-and-changes)'s. Its team checks, its lead review, a rewind dropping it, several folders, nested repositories and an automation's run there are covered offline (`test/orchestrator-workspace.test.ts`, `orchestrator-folders`, `orchestrator-checks`, `orchestrator-review`, `orchestrator-schedule`).
- **Native Git installation.** The Git dialog tests simulate missing Git and installer responses. `test/git-install.test.ts` checks platform-specific installer choices with fake processes.
- **Steering with the other CLIs.** Only the fakes of Claude Code and Codex take a message into a running turn; Grok's `x.ai/interject`, Antigravity's further `session/prompt`, Goose's `_goose/unstable/session/steer` and Pi's `steer` are tried offline only, in `test/steer.test.ts` (and the generic ACP turn's hook in `test/acp-turn.test.ts`), and the orchestrator's rules per mode (parallel mode's all or none among them) with its fake runner in `test/orchestrator-steer.test.ts`. No real CLI has taken one in a test yet, live or not.
- **Most of the interactive commands.** End-to-end tests start one from its card, type into it hidden, answer its password helper, cancel it and send its output. Covered offline instead (`test/interactive.test.ts`, `test/orchestrator-handoffs.test.ts`, `test/handoffs-api.test.ts`): the block's rules, the working directory (its configuration files listed, and a start refused when others appeared), a card an automation's run proposed and another chat's, the time limit, the folder's secrets masked, a refused helper question, and a run a stopped server left. Real sign-ins (`gcloud`, `npm login`), `sudo -A`, ssh and git through the helper were not tried end to end.
- **A real lead agent's judgement of what is safe ("Approve for me").** The fake lead agent approves or flags as a directive says; what the review reads, when it is skipped, its time limit, how many run at once and an automation's runs are covered offline (`test/approvalReview.test.ts`, `test/orchestrator-approve.test.ts`, `orchestrator-schedule`). What a real model decides is not tested.
- **The CLIs themselves.** The fakes check Harness Relay's side of each protocol; the [live tests](#the-live-tests) try the real ones, by hand. A CLI that changes what it writes is caught by the adapter tests' recorded messages (`test/claude.test.ts`, `test/codex.test.ts`, `test/grok.test.ts`, `test/cursor.test.ts`, `test/antigravity.test.ts`, `test/copilot.test.ts`, `test/muse.test.ts` and the open agents', the last ones replaying messages recorded from the real CLIs) and by trying the real CLI in the app; those recordings are of the versions the adapters were written against, so a new version of a CLI is checked by hand with `scripts/cli-check.ts`, against the real CLI ([developer guide, "Checking a CLI's new version"](../docs/developer-guide.md#checking-a-clis-new-version)). Whether a real CLI keeps the gateway's token, an HTTP MCP server's header, in memory only is checked by hand with `scripts/mcp-headers-check.ts`, not here: the fakes only show that Harness Relay gives it in the header and in no argument.
- **The CLIs' own sandboxes.** The fakes of Claude Code, Codex, Grok, Copilot and Muse Code work out from what Harness Relay gave them what their CLI's sandbox would allow (Copilot's from its run's settings, and it answers `/sandbox policy` with the policy they give, as Copilot prints it); only Harness Relay's own sandbox, around the open agents, is the real one. That the real CLIs below full access write nowhere outside the chat's folders is tried by the live tests (`live/sandbox.spec.ts`).
- **AgentsView itself.** It is a stand-in server in [`sessions.spec.ts`](specs/sessions.spec.ts) that answers Harness Relay's requests and never reads a session file. That the real AgentsView reads each CLI's own sessions where Harness Relay's runs leave them, under the ids Harness Relay links (Copilot's `session-state` and Muse Code's data folder among them, in the CLIs' usual homes and through the user guide's `config.toml` for an AgentsView of its own), and files them under the thread, was tried by hand, with AgentsView 0.46.1 (for Copilot and Muse Code also on the sessions copilot 1.0.109 and muse 1.4.18 wrote on Linux and Windows through their adapters).
- **GitHub's own sign-in for gh.** The share dialog's sign-in runs the fake `gh`, which prints a code and waits for the test's approval; gh's real device sign-in was checked by hand (that it prints its code and `github.com/login/device` without a terminal, and opens no browser), not GitHub approving it.
- **A shared page on GitHub and the website themselves.** The tests open the viewer from the repository's `site/` and gists of the test's, at their real addresses but routed: GitHub's raw host and API themselves (their caching, their limits, an account renamed) and the published site are not tried, nor a download in WebKit; the viewer was tried by hand against GitHub, with the use cases' shares, in Chromium, Firefox and WebKit. A link on gistpreview.github.io (shares made before the viewer) is not opened.
- **A tracked goal over time.** Its retries after a failed run (5, 30 and 120 minutes), a run a restart cut off and the schedule's own times are tried in the unit tests with a fake clock (`test/orchestrator-tracking.test.ts`); the end-to-end tests run a tracked schedule once, by **Run once now**.
- **Live OAuth provider accounts.** Common apps uses service stand-ins for consent and token exchanges. The Teams browser tests exercise direct reading and confirmed sending against a local Graph PowerShell stand-in. The unit tests also exercise the Drive and Teams read tools and renewal of saved Slack grants. The browser uses stand-ins for Microsoft’s sign-in and Graph, and for Google’s OAuth page and Docs API ([Accounts that sign in with OAuth](#accounts-that-sign-in-with-oauth)); the device code, a pasted address, a refused or expired sign-in, the broker's refreshes, a refresh that comes back after its account was removed, and the calendar tools over Graph and over Google's CalDAV with a token (against stand-ins for Google's sign-in and CalDAV) are in `test/oauth.test.ts`; the mail tools, the mail trigger and IDLE over XOAUTH2, a refused token renewed, the scopes of a sign-in for mail, Google's incremental consent and Gmail are in `test/oauth-mail.test.ts`. In the browser, mail over a sign-in is only signed in for and tested (no agent reads or sends it), and over plain TCP to stand-ins. No real account signs in in these tests: a real Google account (its calendars, and Gmail taking its token) was tried by hand, as the architecture's limitations say; Microsoft's has not been.
- **Real MCP servers that sign in, and the other ways of their sign-in.** [MCP servers that sign in](#mcp-servers-that-sign-in) signs in against a stand-in only, and gives the token to Claude Code's fake alone (each CLI's own way of taking an HTTP server's headers is [What reaches each CLI besides the prompt](#what-reaches-each-cli-besides-the-prompt)'s). Discovery's other forms (the well-known addresses, OpenID's metadata, a challenge's scope) and its failures, the refusals (no PKCE S256, no registration, another resource's metadata or one above the server's path, another issuer, plain http elsewhere, a server that asks for none), a server elsewhere (only addresses on the internet, through a stand-in lookup, pinned), RFC 9207's `iss`, the mix-up attack against two stand-ins (a hostile server's metadata naming another authorization server's page: confirmed first, and its code never sent to the hostile token endpoint), registering again for another redirect address or once a refresh refused the client, a client secret (Basic or in the form, to sign in, refresh and revoke), a pasted address, a sign-in with no refresh token, a refresh that fails otherwise, tokens of ten minutes or less, a member not given the server or on Antigravity, the host rule, answers too large or with a token too long, revocation's failures, the old refresh token revoked when a sign-in replaces it, removing the server or changing its URL, the waiting limit with discoveries under way, and a restart are tried in the unit tests (`test/mcp-oauth.test.ts`, `test/orchestrator-mcp-oauth.test.ts`).
- **The triggers' cadence, the calendar source, CI runs and the team's own writes.** [Automations](#automations) checks with **Check now**, and GitHub only through the fake `gh` (its pull requests; the real gh and GitHub are never reached); the checks every 2 minutes, slower after errors, what a restart keeps, files the team writes in the folder (never starting another run), and several things to wait for apart from the two file patterns (other sources together, each one's errors and slower checks, two messages from one check, IMAP IDLE asking for one of them) are tried with a fake clock in `test/orchestrator-watch.test.ts`, the IMAP side (UIDVALIDITY, conditions, many mails at once) in `test/watch.test.ts`, and an event about to begin (against a stand-in CalDAV calendar, also one that expands recurring events, and over OAuth), a failed CI run (against a stand-in for gh) and a file still being written in `test/watch-sources.test.ts`, and IMAP IDLE (a connection waiting in the folder, renewed and opened again) in `test/idle.test.ts`, not end to end.
- **Real service accounts and mail server TLS.** Unit tests use local IMAP, SMTP and CalDAV servers without TLS. They reject a STARTTLS reply that contains extra data before starting TLS (`test/connectors.test.ts`). Browser tool tests use real Chromium when available (`test/browser.test.ts`). End-to-end tests call `mail_send` through the fake Claude Code CLI over stdio and through Codex, Copilot and OpenCode over loopback HTTP. The fake Claude Code CLI also reads through the mail, calendar, browser, Google Drive, GitHub, Obsidian, Notion and Heptabase tools. The Google Docs and Slack cases exercise confirmed writes. Their confirmation tests use local fixtures or temporary vaults. These checks use no live cloud accounts.
- **What Cursor does without asking in a temporary folder.** The real Cursor writes in a temporary folder (`/tmp`, macOS' `/private/var/folders`) without asking; its fake does not, as the tests' folders are all in one and every write outside the workspace would then go through unasked. Nor does a spec try a Cursor team's auto-run allowlist (the fake has one, `E2E_FAKE_CURSOR_TEAM_ALLOW`). The real Muse Code's sandbox lets its commands write in the temporary folder too; its fake's does not, for the same reason.
- **The CLIs' real plan usage.** [Plan usage](#plan-usage) checks Harness Relay's side with the fakes' answers; the real CLIs' answers are covered by the answers recorded from them in `test/usage.test.ts` (Antigravity's only as agy 1.5.8 types them: no real Google account's was seen), and no live test asks a real CLI. The fake agy answers a signed-out `/usage` at once with an error, where the real one asks for a sign-in on stderr and waits (the unit tests' stand-in does that). Error messages and the zh-TW wording of the panel are covered by `test/usage-web.test.ts`, not here.
- **The smooth scroll to the end of the chat.** [Scrolling the chat](#scrolling-the-chat) checks where the arrow takes the chat and that it goes there at once with reduced motion, not how the smooth scroll looks on its way. The arrow after more came in under part of a message opened at the end is covered by `test/chat.test.ts` only, and on a phone the chat is scrolled by script, not by a finger.
- **How the guided tour's welcome picture looks.** [The guided tour and the theme](#the-guided-tour-and-the-theme) checks its parts, its size, its animations and its end state; how it looks, in light and dark, in both languages, on a desktop and a phone, and its animation frame by frame, was checked by eye.
- **How smoothly the home logo's animation runs.** [The home page](#the-home-page) checks that it animates `transform` and `opacity` alone, once; that Chrome runs it on the compositor, with no layout or paint after the page is drawn, was checked by hand in a Chrome trace. The same for the team design card's mark, which turns until the design is in ([A new chat and the lead agent's team](#a-new-chat-and-the-lead-agents-team) checks that no element of it has two `transform` animations, which Chrome would not composite): that its style is no longer recalculated each frame was measured by hand (Chrome's `RecalcStyleCount`, about 60 a second with both turns on one element). The same for the app's loader (`LogoSpinner`): [What an agent does on its way to a reply](#what-an-agent-does-on-its-way-to-a-reply) checks that only its orbit's turn animates; that ten at once keep the page's style recalculations near those of none and lay nothing out was measured by hand (`RecalcStyleCount` and `LayoutCount` over two seconds).
- **Push notifications and the system's own notifications.** [Notifications and sound](#notifications-and-sound) records them with stand-ins; push needs a real push service (Google's, Apple's…), so the server's side (subscriptions, encryption, signing, what it sends and holds) is covered by unit tests (`test/push.test.ts`, `test/alerts.test.ts`, `test/push-api.test.ts`) the page's side by `test/alerts-web.test.ts`, and the service worker's handlers, with a stand-in `self`, by `test/sw.test.ts`; a browser subscribing with its push service and a real push reaching a phone are not tried by any test.
- **OpenCode's and Goose's tokens and cost.** Harness Relay reads them from those CLIs' own SQLite databases (`opencode.db`, `sessions.db`), which their fakes do not keep, so their replies show none here; the adapters' tests (`test/opencode.test.ts`, `test/goose.test.ts`) run whole turns against databases written as the real CLIs write them.
- **What a real lead agent points out.** The fake lead agent's review always flags the first words of the first reply; whether a real model's highlights and next steps are worth reading is not tried here. Its prompt, and how its answer is checked (a quote the reply does not have dropped, unknown kinds, the limits), are in the unit tests (`test/reviewer.test.ts`, `test/orchestrator-review.test.ts`).
- **A real phone's swipe.** [On a phone](#on-a-phone) sends most of the swipe's touch events from the page itself, so the browser does not scroll with them; one test sends Chromium's own touches, which it hit-tests and scrolls with, but no test has a phone's own gestures or touch handling: a swipe from the screen's very edge, which a phone may keep for going back, and the point from which Android's Chrome sends a finger's moves (about 8dp, where the scrolling boxes under the finger are measured at its first move) are not tried.
- **A real install of what the sandboxes need.** [What the sandboxes need](#what-the-sandboxes-need) answers for the server: no package manager, sudo, pkexec or AppArmor is run. `test/sandbox-setup.test.ts` covers what Harness Relay runs (the fixed script, its environment, the way it gets administrator rights) and runs the script itself against stand-ins of apt-get and apparmor_parser; the packages and the desktop app's Node.js were installed for real through the dialog, in the packaged desktop app and with `npm start`, on Linux and macOS ([OS sandboxes by platform](../docs/sandboxing.md#installing-what-they-need-from-harness-relay)).
- **A real install from Settings.** [Installing a CLI](#installing-a-cli) installs with the fake npm; npm's registry, the makers' scripts and uv are not reached, nor is nodejs.org: installing Claude Code, Codex or Copilot without npm on the PATH, with Node.js's own build in the CLI's folder, is covered by `test/cli-install.test.ts` and the start of its programs on that Node by `test/winLaunch.test.ts` and `test/process.test.ts`, and was tried by hand on macOS, Linux and Windows. `test/cli-install.test.ts` covers what Harness Relay gives each of them (their arguments, their environment, the folder, on Windows too), with a fake computer, and each CLI's real install was tried by hand on Linux (the Windows installers not yet on a Windows computer).
- **The desktop app's own menus.** [Languages](#languages) checks that the page in the app's window (Electron in its user agent) tells the server its language; the app itself (Electron) does not run here. What the server passes on and what the app keeps are in `test/app.test.ts`, `test/desktop-supervisor.test.ts` and `test/desktop-app.test.ts`, and the menus changing language was checked by hand in the app.
- **An endpoint model's context window in a run.** [Settings](#settings) checks that Save reads it and keeps the user's over it; what each adapter writes from it (OpenCode's `limit` and pruning, Goose's `context_limit` and variables, Pi's `contextWindow` and compaction, OpenHands' condenser, Codex's and Claude Code's settings) is checked by the adapters' own tests, since the fake CLIs do not compact. The test server's default endpoint `e2e` is set up without a check of its models, so its runs get no context window.
- **A member's own limit in a run, the lead agent's answers in a shape, and stopping Claude Code with an interrupt.** The team editor's limit field is checked through the template and team tests, but no fake CLI acts on a limit or a JSON shape: what each adapter passes (`--max-budget-usd`, `--max-ai-credits`, `GOOSE_MAX_TURNS`, `steps`, `--json-schema`, `outputSchema`) and Claude Code's interrupt before the kill are unit-tested (`test/orchestrator-budgets.test.ts`, each adapter's test). Steering through Grok, Antigravity, Goose and Pi is unit-tested too (`test/steer.test.ts`); only Claude Code's and Codex's fakes take a message into a turn.
- **Publishing to the real Render and Neon**: the specs use stand-ins of their APIs; and publishing a backend, a `Dockerfile` or a compose file with PostgreSQL through the UI (Neon's project, its init scripts with `psql`, the variables rewritten), which `test/publish.test.ts` covers with stand-ins and real git, and `test/publish-initdb.test.ts` with a fake Docker (the real `psql` was tried by hand).
- **Most of the Files panel's refusals.** The specs try a save over a newer version and while a run writes in the folder, and a bad name for a new file; the others are covered offline (`test/fileEdit.test.ts` in real folders, `test/files-edit-api.test.ts` over HTTP): a link on the way, `.git`, a file the server withholds or Harness Relay's data folder, an agent's worktree and a folder where edit mode is refused (the listing's `writable`), a read-only file, names no system takes, a file over the limits, and a request that is not the UI's. Neither tries another program changing the folder in the instant between a save's last check and its rename, nor a file that another program holds open on Windows.
- **The lead agent's drafts beyond their fixed answers**: the fake lead agent answers a template, team checks, a schedule and group suggestions with fixed drafts, so what each prompt tells it (the project to read, the time in the user's zone, the accounts, the families of branches) and the drafts it can get wrong (a rule that cannot be used, an account that is not set up, a time that passed, a name a group has) are in `test/checksDraft.test.ts`, `test/scheduleDraft.test.ts`, `test/grouping.test.ts`, `test/planner.test.ts` and `test/orchestrator-drafts.test.ts`; naming a chat in the same run as sorting it into a group, and a title the user typed meanwhile, are there too.
- **Features no spec goes through yet**: an agent calling `run_code` from Settings → Labs, and its RLM mode's sub-model (no fake CLI calls it: `test/runCode.test.ts` runs its real runner and its calls through a real gateway, `test/llmQuery.test.ts` the sub-model's requests, `test/cliSubModel.test.ts` a question through a CLI, `scripts/cli-check.ts`'s `toolless` scenario the real CLIs' toolless runs, and `scripts/sandbox-check.ts --only run-code` the runner in the real sandbox); the notification inbox in a second browser at once (the server's side is in `test/inbox.test.ts` and `test/inbox-api.test.ts`, the page's in `test/inbox-web.test.ts`); voice transcription with a physical microphone and the downloaded engine (the automation browser test uses a synthetic microphone and a fixed transcript); the files a shared reply links to, and uploading a report's screenshots (both push to a gist with git, which the fake `gh` does not stand in for); API keys in the OS credential store (the tests keep it off, so they go to the database, encrypted); signing Codex, Grok, Cursor, Antigravity, Copilot and Muse Code in from Settings (their own flows; Copilot's device sign-in is tried by `test/providers.test.ts`), and what the real Codex does with a key `codex login --with-api-key` was given; Copilot refusing to start below full access when its sandbox's policy is not the one its run set up (`test/copilot.test.ts` covers it); Muse Code asking about a command's network (its fake asks, in its sandbox, for `e2e:approve=publish`, which no spec sends it), and a Muse Code member starting a fresh session after its chat's permission changed or the server restarted (`test/muse.test.ts` covers it); AgentsView's links to the lead agent's and the group sorter's sessions, conversations sent once an address is set, and the members' sessions Harness Relay records for the open agents (`test/agentsview.test.ts` covers them, and Cursor's, which a spec tries too); the subagents of every CLI but Claude Code, and the notes Codex, Grok, Copilot and Pi send about their own runs (only Claude Code's fake sends them: each adapter's test plays its CLI's messages, `test/codex.test.ts`, `test/grok.test.ts` with a stand-in that waits for a background subagent and the turn it wakes Grok for, `test/cursor.test.ts`, `test/copilot.test.ts`, `test/pi.test.ts`); ## The live tests

[`live/`](live/) holds a second suite, `npm run test:e2e:live` with [`playwright.live.config.ts`](../playwright.live.config.ts): the real CLIs, signed in as you are, on real models, so it costs a little and never runs on CI. It is not counted above. It tries all twelve CLIs by default, each test skipped unless the environment names what it needs (an endpoint, `E2E_LIVE_CLOUD=1` for the CLIs' own cloud models): on a Mac, 48 tests in three files with one endpoint, and 58 with the cloud models too (one more for each `E2E_LIVE_MODEL_<CLI>`; with nothing set, 21 tests are listed, all skipped). They try each CLI on an endpoint's model picked in Team settings, a CLI's default model set to an endpoint's in Settings, the seven CLIs' own cloud models (Claude Code's, Codex's, Grok's, Cursor's, Antigravity's, Copilot's and Muse Code's), a member on a deleted endpoint's model, a model typed for an endpoint, the open agents on native Windows below full access, a team on cloud and local models together, each CLI writing a file in each of a chat's two working directories through its shell (on an endpoint's model, and the seven with a sign-in on their own too), Cursor's own file tool in the second one, Antigravity ending its turn at a refused command and asking about a project's own MCP server before it starts, Copilot doing the same with a refused command and a project's own hook, and every CLI below full access writing nothing outside the chat's folders. How to run them: the developer guide's [Live tests](../docs/developer-guide.md#live-tests).
