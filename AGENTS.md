# AGENTS.md

Guidance for coding agents (Claude Code, Codex, Grok and others) working in this repository. People should start with the [README](README.md), [CONTRIBUTING.md](CONTRIBUTING.md) and the [developer guide](docs/developer-guide.md).

## What this is

Harness Relay is a local web app: a group chat where the real `claude`, `codex`, `grok`, `cursor-agent` (Cursor), `agy` (Antigravity) and `copilot` (GitHub Copilot CLI) and `muse` (Muse Code) CLIs, and five open-source coding-agent CLIs (OpenCode, Goose, Cline, OpenHands, Pi: the "open agents"), work with the user and with each other. The open agents have no sign-in in Harness Relay: they run on the model backends the user sets up (OpenAI, Anthropic and xAI API keys, or the user's own OpenAI-compatible endpoints), and below full access inside Harness Relay's own OS sandbox.

- **Server**: Node.js ≥ 22.13, TypeScript, [Hono](https://hono.dev), run with `tsx` (no build step). It owns conversations, decides who speaks next, spawns the agent CLIs and stores everything in SQLite (`node:sqlite`). It never calls model APIs itself.
- **Client**: React 19 + Vite. It renders the chat and gets live updates over Server-Sent Events.

Read these before a larger change; they are kept up to date and go deeper than this file:

- [docs/architecture.md](docs/architecture.md): components, conversation model, turn scheduling, CLI adapters, approvals, workspaces, security, known limitations.
- [docs/developer-guide.md](docs/developer-guide.md): project layout, request flow, HTTP API, adding a CLI, database changes, prompts, translations, tests.
- [docs/open-agents.md](docs/open-agents.md): the open agents: model backends, their homes, the generic ACP turn, permissions, the relay sandbox, and one section per agent.
- [docs/sandboxing.md](docs/sandboxing.md): every OS sandbox the runs use, Harness Relay's own included, by platform.
- [docs/adding-a-coding-agent.md](docs/adding-a-coding-agent.md): the procedure for adding a coding-agent CLI, step by step, from finding out how it really behaves to checking it on each system.

| `npm run typecheck` | `tsc --noEmit` over `src`, `test`, `scripts`, `e2e` and the config files |
| `npm test` | All Vitest tests (offline) |
| `npx vitest test/store.test.ts` | One test file |
| `npm run test:e2e` | End-to-end tests (Playwright): the built UI in Chromium against the real server, with fake CLIs (`e2e/`); builds the UI first when it is out of date, also a development build of it (`dist/web-dev`, where React's StrictMode runs each effect twice) |
| `npm run test:e2e:install` | Once: the Chromium they drive (on Linux `npx playwright install --with-deps chromium`) |
| `E2E_LIVE_OLLAMA=<url>/v1 npm run test:e2e:live` | The live tests (`e2e/live/`, `playwright.live.config.ts`): the real CLIs, signed in as you are, on your own Ollama or vLLM server (and their own cloud models with `E2E_LIVE_CLOUD=1`); never on CI, each test skipped unless the environment names what it needs (developer guide, "Live tests") |
| `npx playwright test e2e/specs/chat.spec.ts` | One end-to-end spec (`--ui` to watch them, `npx playwright show-report` for the last run) |
| `npm run build` | Build the UI into `dist/web` |
| `npm start` | One process: API + built UI on :8787; prints a one-time sign-in link |
| `npm run login` | Print another one-time sign-in link (`scripts/login.ts`) |
| `npx tsx scripts/sandbox-check.ts` | Run Harness Relay's own sandbox for real on this computer (macOS, or Linux with bubblewrap, socat and ripgrep) and check what it allows; `--only <text>` runs the checks whose name contains it, `--keep` keeps its scratch folder. Run it after changing `relaySandbox.ts`, `relaySandboxHost.ts`, `sandboxProcs.ts` or an adapter's sandbox needs |
| `npm run site:preview` | Serve the landing page (`site/`) on 127.0.0.1:4180, as GitHub Pages will |
| `npm run icons` | Redraw the home-screen icons and the web app manifest in `src/web/public/` (`scripts/app-icons.ts`) |
| `npm install --prefix desktop` | Once, for the desktop app only: Electron and electron-builder (`desktop/` is a package of its own) |
| `npm run desktop` | Build the UI and the desktop app (`desktop/build/`) and run it without installing it |
| `npm run desktop:dist` | The same, then make the installer for this system in `desktop/release/` (`.dmg`, `.exe`, `.AppImage`; not signed); `npm run desktop:dist -- --output <folder>` puts it elsewhere |
| `npx tsx desktop/scripts/check-package.ts` | Check the packaged app in `desktop/release/` as a release is checked: its fuses, its resources, no `github_pat_` token in the server's files nor as text in the app's, the repository and the token (encoded) that `RELAY_UPDATES_REPO` and `RELAY_UPDATES_TOKEN` name in its own environment (give it the build's), and its own `--smoke-test`, in which the e2e fake CLIs answer a question (on Linux, under `xvfb-run`) |
| `npm run desktop:typecheck` | Typecheck the desktop app (`desktop/tsconfig.json`) |
| `npm run release:next` | Today's next release and release candidate versions (from GitHub's tags) |
| `npm run release:check -- <version>` | Check a release version against the rules (`scripts/release.ts`), as the Release workflow does (add `--remote` after the version for GitHub's tags) |
| `npm run release:notes -- <version> --remote` | Print the list of changes a release's notes have, as the Release workflow writes it: every commit into `main` since the version before, read from GitHub through `gh` (`--target <commit>` for a release not made yet) |
| `npm run demo` | Record the README and landing-page demo again with the real CLIs, then update the videos, stills and chapter rails (`scripts/demo/`; see the developer guide, "Recording the demo") |

Before you commit, run `npm run typecheck`, `npm test` and `npm run build` (and `npm run desktop:typecheck` when you changed `desktop/`, and `npm run test:e2e` when you changed the UI, the HTTP API, the orchestrator or an adapter; and `npm run test:e2e:live` on each system you can when you changed an adapter, the sandboxes or the model backends and have a model server). CI ([`.github/workflows/ci.yml`](.github/workflows/ci.yml)) runs the same three on Node 22 and 24 (and on Windows with Node 24) for every pull request and every push to `main`, and also typechecks the desktop app, builds it and runs its bundled server as the app does (`desktop/scripts/smoke.ts`), and packages it for Linux and Windows and checks it (`desktop/scripts/check-package.ts`). [`.github/workflows/e2e.yml`](.github/workflows/e2e.yml) runs the end-to-end tests on Linux, macOS and Windows for the same events. The tests on Windows, the packaged app and the end-to-end tests run only when the change touches a file they depend on (`scripts/ci-scope.ts`, whose `IGNORES` list for each what it does not depend on): when one of them comes to read, import or ship a file on its list, take the file off the list in the same commit. Each workflow's last check (`CI passed`, `End-to-end passed`) stands for all its jobs. Releases are made only by the Release workflow ([`.github/workflows/release.yml`](.github/workflows/release.yml)), run by hand: see the developer guide, "Releasing". Never make a release or a version tag any other way.

## Where things are

- `src/shared/`: code shared by server and client. `types.ts` (all shared types, `PROVIDERS`), `mentions.ts` (the `@mention` rule, and `unknownMentions`), `links.ts` (where a bare URL ends, also before Chinese text written right after it), `ask.ts` (`[ASK_USER]`), `media.ts`, `schedule.ts` (a schedule's next times), `notify.ts` (when the user is told that agents finished or need them, and what the notification says), `search.ts`, `family.ts` (families of branched conversations: each one's parent and top, for the sidebar's tree and for moving a family between groups as one), `share.ts` (a shared page's placeholder links to the files that go along, in their own gist).
- `src/server/app.ts`: routes, security middleware, SSE (`createApp()`, testable with `app.request()`).
- `src/server/orchestrator.ts`: team runs: speakers by mode, prompt delivery, streaming into messages, auto team, the message queue, pausing for the user's answer, retry and resend.
- `src/server/prompt.ts` and `planner.ts`: agent briefings and turn prompts; the auto-team lead agent's prompt and reply parsing; `roleGuides.ts`: how each model family takes a role best (from its makers' own prompting guides), which the lead's prompts give it, only for the families its CLIs can run, where it writes roles.
- `src/server/push.ts`, `alerts.ts`: push notifications (Web Push: browsers' subscriptions, removed with their signed-in browser; VAPID keys, kept in the database, never in the OS keyring, whose unlock prompt a service cannot answer; encryption and signing with `node:crypto`; only to `PUSH_HOSTS`), and the watcher that sends them when agents finish or need the user, holding them while the browser's page is in front.
- `src/server/scheduler.ts`: sends each schedule's message when it comes due (missed times, busy retries), through `Orchestrator.sendScheduled()` (`sendInNewChat()` for a new chat each time; `designForSchedule()` has the lead agent design a schedule's team).
- `src/server/grouping.ts`: the lead agent sorts a new conversation into the user's sidebar groups.
- `src/server/agents/`: one adapter per CLI. `claude.ts` (stream-json), `codex.ts` (`codex app-server`), `grok.ts` (ACP), `cursor.ts` (ACP, `cursor-agent acp`: no OS sandbox, so below full access every command asks, but those on a Cursor team's auto-run allowlist; a private config folder per run, with its settings and deny rules), `antigravity.ts` (ACP, `agy acp`: no sandbox, so below full access every command asks, and a refusal ends its turn; settings of its own per run, in the folder `--cli_dir_name` names; the account's home through `--gemini-dir`), `copilot.ts` (ACP, `copilot --acp`: its own sandbox below full access, with its policy checked before each turn, and a refusal ends its turn; a run home of its own per turn, with Harness Relay's settings, the account's sign-in state and links to its sessions (`session-state`, and except on Windows `session-store.db`, where AgentsView reads their token counts); a project's own hooks asked about before it starts), `muse.ts` (ACP, `muse acp`: its own OS sandbox below full access (on Windows only once Muse's own elevated setup has run), under a permission profile of Harness Relay's (from `:ask-me`, with deny rules for the protected paths) in a config folder of its own per run (`XDG_CONFIG_HOME`), its approval judge off and no workspace trusted below full access; a session resumed only with the permission and protected paths it was made with, since Muse keeps them; the account's home through its XDG folders), `acp.ts` (the JSON-RPC peer, and the ACP helpers Grok, Cursor, Antigravity, Copilot and Muse Code share: prompt blocks, MCP servers, permission answers, content text), `index.ts` (registry). The open agents ([docs/open-agents.md](docs/open-agents.md)): `opencode.ts`, `goose.ts`, `cline.ts`, `openhands.ts` (ACP, through the generic turn in `acpTurn.ts`), `pi.ts` (JSONL RPC, with its gate extension `piGate.js`), and what they share around their process in `open.ts`.
- `src/server/db.ts`, `store.ts`, `settings.ts`, `secrets.ts`: SQLite and migrations (and the lock one server holds its data folder with, `lockDataDir`), persistence, provider settings, each CLI's accounts (a home and an API key of their own; agents and the lead agent name theirs; Cursor's besides the default one sign in with an API key only, since Cursor keeps one sign-in per computer user: `CURSOR_SHARED_SIGN_IN`; Antigravity's too, with a Gemini API key, since agy keeps its Google sign-in in the system keyring, and Muse Code's, with a Meta API key, since muse keeps its Meta sign-in in the macOS login keychain: `keyOnlyAccount()`) and child-process env (including the CLIs' own homes), API keys in the OS keyring, or without one in the database encrypted with the key in `secrets.key` (`openSecretStore()`; the key file a protected path, withheld from the Files panel and downloads).
- `src/server/ports.ts`: Harness Relay's ports (8787 for `npm start` and the desktop app, 8789 and Vite's 5173 for `npm run dev`, `PORT` over either).
- `src/server/backends.ts`, `relaySandbox.ts`, `relaySandboxHost.ts`: the open agents' model backends (API keys and custom endpoints, keys in the OS keyring; Claude Code, Codex, Grok and Copilot run on the endpoints too, `endpointModel()`) and Harness Relay's own sandbox around them below full access (srt; one host process per run, which runs the sandbox for that run alone); `sandboxProcs.ts` finds a run's leftover processes on macOS by their sandbox; `fsRemove.ts` removes what a run left without following links (giving the owner's permissions back only at a start whose sweeps found nothing left). `scripts/sandbox-check.ts` checks the real sandbox on this computer; `npm test` never starts one.
- `src/server/agentsview.ts`: sends each conversation to AgentsView as one thread and links the agents' own sessions under it; for the CLIs whose sessions AgentsView cannot read where they are (Cursor and the open agents: `AGENTSVIEW_SESSIONS`), it sends each member's session as Harness Relay recorded it (`memberTranscript`).
- `src/server/config.ts`: what the environment sets at startup besides the port, host and data folder (accounts per CLI, team size, the turn timeout, voice input's download folders and folder), checked once; the server refuses to start on a value that is not valid. The UI gets the limits from `GET /api/limits` (`src/web/limits.ts`, `useLimits()`), never from constants of its own.
- `src/server/workspace.ts`: git: auto init, snapshots, worktrees, diffs, apply.
- `src/server/process.ts`: spawning, streaming and killing child processes; `winLaunch.ts`: what to start on Windows for a CLI that is a `.cmd` (npm's shims, Cursor's and Muse Code's launchers).
- `src/server/parent.ts`: the desktop app that started the server, if any (Electron's `parentPort`): the server says when it listens, the app asks it for sign-in links, how many conversations have agents at work (`Orchestrator.busy()`, which an update waits on), and to shut down, and tells it its updates. `updates.ts` keeps those for the chat (`GET /api/update`) and passes the chat's asks (check now, update) back to the app.
- `desktop/`: the desktop app (Electron), a package of its own. `src/main.ts` (the chat's window, the tray menu, updates, its own check `--smoke-test`, and the app's life; the only file that imports `electron`), `supervisor.ts` (starting, watching and stopping the server, and asking it for sign-in links and how many conversations have agents at work), `env.ts` (the login shell's environment, Windows' at a restart, the server's), `tailscale.ts`, `autostart.ts` (open at login on Linux), `prefs.ts`, `profile.ts` (the window's browser folder, kept from agents), `log.ts` (the server's log), `update.ts` (updates to GitHub's newest release, a release candidate only for an app that is one, for this system's processor, switching once no conversation has agents at work), `updateSource.ts` (the repository it downloads its updates from, and a token for a private one: `RELAY_UPDATES_REPO` and `RELAY_UPDATES_TOKEN`, fixed when it is built; the token goes into the app, where anyone can read it; and the Release workflow's checks that the repository can be read before anything is built, that the installers were built with them and that an app can download the copies, `repositoryReadable()`, `sameUpdateSource()`, `copiesReadable()`), `traymenu.ts` (the tray menu while it is open: changed in place and opened again to show what changed, and a moment after it closed), `selftest.ts` (what the app needs of the server over HTTP, a team of the e2e fake CLIs answering a question included), `manifest.ts` (the app folder's `package.json`), `i18n.ts`, `icons.ts`, `lifecycle.ts` (its decisions without Electron, the window's guards); `scripts/build.ts` bundles the server and the app into `desktop/build/` (with Harness Relay's own sandbox host, Pi's gate extension and the sandbox runtime's packages beside the server) (as `RELAY_VERSION` for a release, else a `-dev` build of the day; downloading its updates as `RELAY_UPDATES_REPO` and `RELAY_UPDATES_TOKEN` say, and writing their fingerprint, `build/update-source.txt`, for the Release workflow); `scripts/smoke.ts` runs the bundled server as the app does, with `scripts/parent-port.mjs` standing in for Electron's `parentPort`; `scripts/dist.ts` is `npm run desktop:dist`; `scripts/check-package.ts` (with `scripts/packaged.ts`) checks the packaged app; `electron-builder.yml` makes the installers, with `entitlements.mac.plist` and `macos/` (the microphone's reason in each language); `README.md` (and `README.zh-TW.md`) is the app's page for developers.
- `mirror/`: the website's download mirror, a Cloudflare Worker (`worker.ts`, with `wrangler.toml`; deployed by hand) in front of an R2 bucket that the Release workflow uploads each release's installers to (never a release candidate's), for the visitors GitHub's downloads are slow for. It serves a release's installers only, sends any it does not have to GitHub, and for each download it serves asks GitHub for the installer's first byte as a download there does, so that GitHub's download counts still count it (tested in `test/mirror.test.ts`). Under the copies' names (`UPDATE_INSTALLERS`) it serves the same files to the desktop app's updates, which try it first and count themselves on GitHub against the copy once they have the file (`downloadUpdate()`, `countUpdate()` in `desktop/src/update.ts`); those it never counts nor redirects, so that an update never counts as a new install. It also keeps the codespaces count (`POST /codespaces`, from `.devcontainer/count.sh`): how many codespaces were made a day, in a D1 database (`COUNTS`, which `wrangler deploy` makes), with nothing else (Workers Logs keeps the requests a few days, as it keeps the downloads); a browser's request (with `Origin`) is refused. The website uses it when `MIRROR` in `site/assets/downloads.js` names it; see the developer guide, "Releasing".
- `scripts/ci-scope.ts`: which of CI's slower jobs a change needs (the tests on Windows, the packaged desktop app, the end-to-end tests), run by the first job of `ci.yml` and `e2e.yml`: each runs unless every file the change touches is on its `IGNORES` list, and everything runs when the change cannot be told; tested in `test/ci-scope.test.ts`, which also follows the imports of the end-to-end tests and the packaged app.
- `scripts/release.ts`: the release version rules (dates: `YYYY-MM-DD`, `.N` patches, `-rc` after either for a release candidate of it and `-rc.N` for its patches; today in Taiwan; the next one only), used by `npm run release:next`, `npm run release:check` and the Release workflow; and the notes' list of changes (`npm run release:notes`): every commit that came into `main` since the version the notes start from, pushed or merged from a pull request, never only the pull requests.
- `src/server/tools.ts`: the tool library: MCP servers (their secret values in the OS keyring, by server id), skills and memory, and what each agent gets from it.
- `src/server/native.ts`, `grokTrust.ts`: what each CLI loads by itself (asked without a prompt; Cursor's read from the files it reads, as are Antigravity's MCP servers and instruction files and Copilot's hooks and custom agents, and Muse Code's MCP servers and hooks from its settings); recording Grok's trust in a project root.
- `src/server/usage.ts`: each account's plan usage, asked of its CLI without a prompt in that account's home (Claude Code's `get_usage` control request, Codex's `account/read` and `account/rateLimits/read`, Grok's `_x.ai/billing` over ACP, `muse usage --json`, Copilot's `account.getQuota` on its headless server `copilot --headless --stdio` (`Content-Length` framing), Antigravity's `/usage` and `/credits` in print mode; Cursor's plan only, from `about`), kept a while by `ProviderService.usage()` and shown in each account's box in Settings (`components/UsagePanel.tsx`, its pure logic in `src/web/usage.ts`); none, without asking, for an account on a key its provider bills by use (`BILLED_KEY_ENV`).
- `src/server/files.ts`: browsing a chat's working directory and agents' worktrees (inside the folder only, never `.git`), and what a folder's ZIP download holds; `zip.ts` writes that ZIP file as it is sent.
- `src/server/protect.ts`: what agents below full access may not reach (the browsers' folders, the database, and in a GitHub codespace its token files and gh's sign-in; Harness Relay's own folder in edit mode), handed to each CLI's sandbox by its adapter (to Copilot's as its policy's denied paths; to Cursor, which has none, as deny rules for its own file tools; to Antigravity, which has none either, as refusals when it asks to read or write one; to Muse Code as deny rules in its permission profile, which its file tools follow too).
- `src/server/auth.ts`: signed-in browsers (one-time codes, sessions of a cookie and a key, hashes only); `src/shared/auth.ts` and `src/web/auth.ts` hold the parts the UI shares.
- `src/server/folderPicker.ts`: the system's own folder dialog for the working directories box (`POST /api/cwds/pick`): which one this computer has (AppleScript, zenity / kdialog, Windows PowerShell), its command and its answer.
- `src/server/share.ts`: a shared conversation as a secret gist through the user's own `gh` (in a GitHub codespace without the codespace's `GITHUB_TOKEN`, which cannot make gists: `ghEnv()`; signed in from the share dialog when it is not: `GhLogin`, gh's device sign-in through `src/server/login.ts`, which the CLIs' sign-ins in Settings run too) (create, delete; read on gistpreview.github.io), and the files its replies link to, of any kind, pushed with git into a second one. The page itself is made in the browser from the chat on screen (`src/web/sharePage.tsx`; its DOM-free parts in `src/web/share.ts`).
- `src/server/about.ts`: which Harness Relay this is and on what, for a problem report (`GET /api/about`; the desktop app's server bundle sets `__RELAY_VERSION__`). `screenshots.ts`: a problem report's screenshots, checked to be images and uploaded as a secret gist through the user's `gh` (`filesToGist()` in `share.ts`), for the mail to link to.
- `src/server/i18n.ts`, `presets.ts`: server-side messages and built-in team templates, both in two languages.
- `src/web/`: the React client. `components/`, `locales/` (`zh-TW.ts`, `en.ts`), `chat.ts` (ChatView's pure logic), `backends.ts` (the endpoint form's pure logic, for `components/BackendsSettings.tsx`, Settings → Model backends), `copy.ts`, `highlight.ts` (the file browser's highlighting, with the lowlight replies' code blocks use: one copy of highlight.js), `tour.ts` (whether the guided tour was seen; the tour, Settings and the dialogs a chat opens load when first opened, `lazyPart` and `Deferred` in `components/Deferred.tsx`, and only the language shown is loaded, `loadMessages()` in `i18n.tsx`, its file asked for by the page's head, `languagePreload` in `vite.config.ts`), `chunks.ts` (a part loaded when first needed that could not be, as in a page open across an update: the page reloads once for it, `loadPart`, then `Deferred` says so), `signin.ts` (signing in with a link: the page's first check, shared by both runs of App's effect in development; where the sign-in page points), `report.ts` (a problem report by email: the mail, its mailto and Gmail links, the screenshots it may link to), `update.ts` (the desktop app's updates in the chat: Settings' Version card, the dialog offering a new version once; and reloading a page open across an update), `dialogs.ts` (the dialogs open on the page: only the top one takes keys), `alerts.ts` (notifications and sound when agents finish or need the user, in this browser: Settings → Notifications and sound, the push subscription, `components/NotificationsSettings.tsx`), `api.ts`, `public/` (the web app manifest and home-screen icons, written by `npm run icons`, don't edit them by hand; and `sw.js`, the service worker that shows push notifications, written by hand).
- `test/`: Vitest tests, roughly one file per module. The open agents', Antigravity's, Copilot's and Muse Code's adapters replay messages recorded from the real CLIs (`test/fixtures/<agent>/`) through stand-ins (`test/fake-*.ts`).
- `e2e/`: end-to-end tests (Playwright, `playwright.config.ts`). `fake-cli/` holds a fake for each of the twelve CLIs (`agents/<provider>.cjs`, sharing `lib/`; `fake-cli.cjs` picks one by the name it runs under), speaking each CLI's protocol and steered by `e2e:` directives in the user's message, bundled into one script when installed (scripts on macOS and Linux, Node single executables on Windows: `support/fake-cli.ts`; the desktop app's checks, `smoke.ts` and `check-package.ts`, use them too); below full access the open agents' fakes run in Harness Relay's own sandbox for real (macOS, Linux). `support/clis.ts` answers the specs' questions about each CLI from its facts (`support/clis/<provider>.ts`, changed with its fake); `support/relay.ts` starts a server of its own for each test (temporary data, homes and working directory, under `/tmp` on macOS and Linux, the fakes first on PATH, keyring off) with a fake model endpoint beside it (the model backend `e2e` and the open agents' default model, which a sandboxed fake also sends its log lines to); `support/app.ts` holds the UI steps; `global-setup.ts` builds the UI and a development build of it (`DEV_WEB_DIR` in `support/paths.ts`, for a spec to serve), and checks once whether Harness Relay's own sandbox works here (`E2E_RELAY_SANDBOX`); `specs/` the tests; `README.md` (and `README.zh-TW.md`) the scenarios the offline ones cover, spec by spec. `live/` (with `playwright.live.config.ts`) holds the live tests: the real CLIs, signed in as the user is, on real models, never on CI (`startRelay({ live: true })`: no fakes, the user's own homes).
- `.devcontainer/`: the dev container for GitHub Codespaces ([docs/codespaces.md](docs/codespaces.md)): `devcontainer.json` (the container options bubblewrap needs: `securityOpt`, and a TUN device for Copilot's sandbox; the sshd and GitHub CLI features), `setup.sh` (the sandboxes' packages and the seven CLIs that are not open source, once: npm's, and the makers' own installers linked into `/usr/local/bin`), `start.sh` (the server on the codespace's forwarded address, `RELAY_ALLOWED_HOSTS` set to it, and its sign-in links rewritten to it; another link when it runs already), `count.sh` (`postCreateCommand`: the codespace counted once at the download mirror, an empty `POST /codespaces`; only this repository's on `latest-release`, never outside Codespaces, on a rebuild or with `DO_NOT_TRACK` set), `codespace.sh` (what both read of Codespaces' variables). The README's and the website's Codespaces links open the `latest-release` branch, which the Release workflow moves to each release (`CODESPACES_BRANCH`), so that a codespace runs the newest release.
- `data/`: runtime data (`relay.db`, worktrees). Git-ignored; never commit it.
- `.github/`: the workflows, the issue forms (`ISSUE_TEMPLATE/`) and the pull request template, each form and the template in both languages. The bug form's CLI, mode and permission options follow `PROVIDER_LABEL` and the locales' labels (`test/community.test.ts`).
- `CODE_OF_CONDUCT.md`, `SECURITY.md`: the code of conduct (reports by email, to `REPORT_EMAIL` in `src/web/report.ts`), and where to report a vulnerability and what counts as one; each with its `.zh-TW.md`.
- `site/`: the landing page on GitHub Pages (static HTML, `index.html` and `zh-TW/index.html`), published by `.github/workflows/pages.yml`. Follow `site/DESIGN-GUIDELINES.md` when you change it, and change both languages together. `site/assets/downloads.js` points the download buttons at the newest release's installers, never a release candidate's (tested in `test/site-downloads.test.ts`); keep its file name endings (`INSTALLERS`, which the app's updates and the Release workflow's installer check also read) in step with the Release workflow's installer names. `UPDATE_INSTALLERS` names the copies of them the workflow publishes in a repository of their own, under the same tag (`UPDATES_REPO`, or the workflow's variable of that name; `updateCopyName()`, `updateCopyUrl()`; with the `UPDATES_TOKEN` secret), which the app downloads to update itself (with the `UPDATES_READ_TOKEN` it was built with, for a private one; the installer itself where a copy cannot be had), so that GitHub's download counts tell updates from new installs and the release page lists the installers alone. `MIRROR` names the download mirror (`mirror/`) the buttons go to once it says it has the visitor's installer (`mirrorHas()`, a `HEAD` whose redirect is never followed: GitHub would count it); the Worker imports `INSTALLERS` too, so deploy it again when they change.

## Rules

### Code

- Strict TypeScript, ES modules. Shared types live only in `src/shared/types.ts`.
- Spawn child processes only through `src/server/process.ts`, so they are tracked and killed on shutdown; a quick probe the server waits for (`lsof`, `ps`, `chflags`) goes through its `runSync()`, which kills it after its timeout. The relay sandbox's host (`relaySandboxHost.ts`) is a program of its own and starts the agent itself. Start programs directly, never through a shell; a shell script (`runShellScript()`, or `sh -c` given to `spawnDetached()`) is fixed text, and the values it needs (paths, names, settings) go in its environment, never in its text or its arguments. On Windows a CLI found as a `.cmd` (npm's shims, Cursor's and Muse Code's launchers) is started as the program it runs (`src/server/winLaunch.ts`), never through `cmd.exe`.
- Keep CLI output parsers pure (lines in, `AgentEvent`s out) so they can be tested with recorded output.
- Tests run in a Node environment without a DOM. Put client logic you want to test in plain modules (like `src/web/chat.ts` and `src/web/copy.ts`), not inside components.
- `node:sqlite` cannot bind `undefined`: pass optional values through `nul()`, and wrap multi-statement writes in `transaction(db, fn)` (it doesn't nest).

### Security

The server can start agents with write access, so keep its defences intact (see [Architecture → Security](docs/architecture.md#security)):

- New routes go under `/api/` so they get the middleware's Host/Origin checks, the JSON content-type check on writes, sign-in and the request language. Don't weaken these checks. Only a read-only route the browser loads by itself (an `<img>`, a download link) may join `BROWSER_LOADS` in `app.ts`, which takes the cookie without the key.
- Never send secrets to the client (`SettingsView` returns masked keys only). API keys belong in the OS credential store (`secrets.ts`), never in the database as they are: without a credential store they go to the database encrypted, under the key in `secrets.key` (`openSecretStore()`), through the same `SecretStore`.
- The server binds to `127.0.0.1`. Agent replies cannot make the browser load remote content (images are links; local media goes through the media endpoint's path checks). Keep it that way.
- An open agent's process starts only through `startOpenProcess()` (`src/server/agents/open.ts`): below full access it runs in the relay sandbox, which fails closed. Never run one around it. Model keys go to the CLI in environment variables (only the run's own backend's), never into the config files its adapter writes; everything a run writes goes in the conversation member's own state folder (`home(root, state)`, `<home>/private/<key>`); the files that decide what the CLI does when it starts are its `configPaths`, read-only in the sandbox. A sandbox opening (`localPorts`, `connectPorts`, `allowPty`, `allowUnixSocketsInTmp`, `allowTlsTrustd`, `quietlyDeniedHosts`) is asked for by one adapter for its own CLI only, and documented in `docs/open-agents.md` and `docs/sandboxing.md`.

### Database

- To change the schema, append a new SQL string to `MIGRATIONS` in `src/server/db.ts`. Never edit a migration that has been released.
- Update the row types and queries in `store.ts` / `settings.ts`, and the tests in `test/store.test.ts`.

### Prompts and languages

- Prompts to agents (briefings, turn prompts, the planner prompt) stay in English; agents answer in the user's language.
- Every user-facing string exists in Traditional Chinese (`zh-TW`) and English (`en`):
  - **UI**: add the key to `src/web/locales/zh-TW.ts` first (it defines the `Messages` shape), then to `en.ts`. `test/i18n.test.ts` checks that both have the same shape.
  - **Server**: add both translations in `src/server/i18n.ts` and call `t()` where the text is produced. Don't cache translated text in long-lived objects; the language follows the request.
  - **Built-in templates**: `src/server/presets.ts`, in both languages.

### Documentation

- Docs come in pairs: `README.md` / `README.zh-TW.md`, `CONTRIBUTING.md` / `CONTRIBUTING.zh-TW.md`, `CODE_OF_CONDUCT.md` / `CODE_OF_CONDUCT.zh-TW.md`, `SECURITY.md` / `SECURITY.zh-TW.md`, `docs/<name>.md` / `docs/<name>.zh-TW.md`, and the READMEs of `e2e/` and `desktop/` (`README.md` / `README.zh-TW.md` in each). When a change affects behaviour, the HTTP API, the schema, settings, environment variables or the test list, update both languages in the same commit.
- The developer guide lists the HTTP API and what each test file covers; keep those lists current.
- `e2e/README.md` lists every end-to-end scenario. Whenever you add, change or remove an end-to-end test (a spec, a test in it, what it checks, or where it is skipped), update `e2e/README.md` and `e2e/README.zh-TW.md` in the same commit: the area's table, the test counts, "Each CLI at a glance", "Platforms and browsers" and "What they do not cover".
- `desktop/README.md` is the desktop app's page for developers. When its files, commands or checks change, update it and `desktop/README.zh-TW.md` in the same commit.
- `CONTRIBUTING.md` restates the rules in this file for people. When you change a rule here that applies to everyone, change it there too, in both languages.

### Tests

- Add or update tests with every behaviour change.
- Keep tests offline: no real CLI runs, no network, no real credential store. Follow the existing patterns: a fake runner swapped into `runners` (`test/orchestrator-harness.ts`), recorded CLI messages for adapters, real temporary git repositories for `workspace.ts`, `app.request()` for the HTTP API, and a fake keyring passed to `SettingsStore`. End-to-end tests use the fake CLIs (`e2e/fake-cli/`): something new an agent should do there is a new `e2e:` directive in the fake, not a real CLI. Every change to their scenarios goes into `e2e/README.md` and `e2e/README.zh-TW.md` too (see Documentation).
- Keep tests passing on Windows too (CI runs them there): paths built with `join()` / `resolve()`, not POSIX literals; what only macOS or Linux have (permission bits, signals, `/bin/sh`, stand-in CLIs started by their `#!` line) skipped with `skipIf(process.platform === 'win32')`; time limits from `test/timeouts.ts`. See the developer guide, "Testing".

### Worktrees

- If you work in a separate git worktree, put it inside this repository, in your own CLI's folder at the root: Claude Code in `.claude/worktrees/<name>`, Codex in `.codex/worktrees/<name>`, Grok in `.grok/worktrees/<name>`. Any other agent uses `.<agent>/worktrees/<name>` the same way. For example: `git worktree add .codex/worktrees/fix-links -b fix-links`.
- Don't create worktrees next to the repository (such as `../harness-relay-<branch>`) or anywhere else outside it. Remove one with `git worktree remove` when you are done.
- `.gitignore` ignores these folders. If you add a folder for another agent, add it to `.gitignore` in the same commit.
- A new worktree has no `node_modules/`; run `npm install` in it before the commands above.
- These are your own worktrees for changing this code. They are separate from the worktrees the app makes for parallel mode under `data/`.

### Commits

- Write commit messages in English. The subject is an imperative sentence about what the user gets, for example `Let agents ask the user before answering, and wait for the answer`.
- In the body, use short bullet points, grouped under headings when a commit spans several areas: what changed and why, any schema version bump, and which docs and locales were updated.

## Gotchas

- `npm run dev` restarts the server on every server file change, and a restart aborts any running agent turn.
- One server per data folder (`data/server.lock`, `lockDataDir()` in `src/server/db.ts`): a second one on the same folder (`npm run dev` beside an `npm start` of the same checkout, say) refuses to start. Give it another with `RELAY_DATA_DIR`.
- The relay sandbox puts its sockets in the data folder (`data/srt/`), so the data folder's path must be short: at most 70 characters on macOS, 61 on Linux, or the open agents refuse to run below full access. A worktree's `data/` (under `.claude/worktrees/<name>/`) is usually too deep: set `RELAY_DATA_DIR` to a shorter folder there.
- Harness Relay refuses edit mode in a working directory that holds itself (`src/server/protect.ts`). To work on this repository with Harness Relay, run the copy you use from another checkout.
- `desktop/` has its own `package.json` and lockfile, so a root `npm install` never downloads Electron. Its pure modules are tested from the root `test/` (`desktop-*.test.ts`); keep `electron` imports in `desktop/src/main.ts` only.
- `npm run desktop:dist` refuses to start while a Harness Relay runs from `desktop/release/` (it would replace the files under it): quit it first, or build with `-- --output <folder>`. Opening a new build while another Harness Relay runs only brings the running one forward.
- The desktop app's Electron may not run as Node (its fuses), so Harness Relay's own sandbox host runs there on the Node.js 22.12 or later on the login shell's `PATH` (`hostNode()` in `relaySandbox.ts`); without one, the open agents work only with full access. A file the server runs or hands to a CLI apart from `server.mjs` (like `relaySandboxHost.mjs` and `piGate.js`) must be written next to it by `desktop/scripts/build.ts`, and checked by `desktop/scripts/smoke.ts` and `check-package.ts`.
- electron-builder leaves out a `node_modules` folder at the top of an `extraResources` folder, so the keyring module the server needs is listed as an entry of its own in `desktop/electron-builder.yml`.
- The desktop app passes the server its own environment (`desktop/src/env.ts`): `PORT` and `HOST` from the user's shell are ignored, and `RELAY_WEB_DIR` points at the app's copy of the UI.
- You can run Harness Relay from inside a Claude Code session: the server strips Claude Code's nesting variables (`CLAUDECODE`, `CLAUDE_CODE_*`) before it spawns `claude` (`src/server/settings.ts`).
- The Vite proxy key is `/api/` with a trailing slash on purpose: a bare `/api` would also capture the client module `/api.ts`.
- Worktrees in parallel mode contain only what is in the snapshot, so ignored files such as `node_modules/` are missing there.
- Kept snapshot refs live under `refs/harness-relay/…`, and parallel-mode branches under `relay/*`. They belong to the app; don't delete them by hand while it runs.
