# AGENTS.md

Guidance for coding agents (Claude Code, Codex, Grok and others) working in this repository. People should start with the [README](README.md), [CONTRIBUTING.md](CONTRIBUTING.md) and the [developer guide](docs/developer-guide.md).

## What this is

Harness Relay is a local web app, a task assistant: in one chat, the real `claude`, `codex`, `grok`, `cursor-agent` (Cursor), `agy` (Antigravity) and `copilot` (GitHub Copilot CLI) and `muse` (Muse Code) CLIs, and five open-source coding-agent CLIs (OpenCode, Goose, Cline, OpenHands, Pi: the "open agents"), work with the user and with each other. The open agents have no sign-in in Harness Relay: they run on the model backends the user sets up (OpenAI, Anthropic and xAI API keys, or the user's own OpenAI-compatible endpoints), and below full access inside Harness Relay's own OS sandbox.

- **Server**: Node.js ≥ 22.13, TypeScript, [Hono](https://hono.dev), run with `tsx` (no build step). It owns conversations, decides who speaks next, spawns the agent CLIs and stores everything in SQLite (`node:sqlite`). The agent CLIs handle inference, but for RLM mode's sub-model (`RELAY_RLM`, `src/server/llmQuery.ts`), which the server asks itself.
- **Client**: React 19 + Vite. It renders the chat and gets live updates over Server-Sent Events.

Read these before a larger change; they are kept up to date and go deeper than this file:

- [docs/developer-guide.md](docs/developer-guide.md): project layout, request flow, HTTP API, adding a CLI, database changes, prompts, translations, tests.
- [docs/open-agents.md](docs/open-agents.md): the open agents: model backends, their homes, the generic ACP turn, permissions, the relay sandbox, and one section per agent.
- [docs/sandboxing.md](docs/sandboxing.md): every OS sandbox the runs use, Harness Relay's own included, by platform.

Before you commit, run `npm run format`, `npm run typecheck`, `npm test` and `npm run build` (and `npm run desktop:typecheck` when you changed `desktop/`, and `npm run test:e2e` when you changed the UI, the HTTP API, the orchestrator or an adapter; and `npm run test:e2e:live` on each system you can when you changed an adapter, the sandboxes or the model backends and have a model server). CI ([`.github/workflows/ci.yml`](.github/workflows/ci.yml)) checks the formatting (`npm run format:check`) and runs the same three on Node 22 and 24 (and on Windows with Node 24) for every pull request and every push to `main`, and also typechecks the desktop app, builds it and runs its bundled server as the app does (`desktop/scripts/smoke.ts`), and packages it for Linux and Windows and checks it (`desktop/scripts/check-package.ts`). [`.github/workflows/e2e.yml`](.github/workflows/e2e.yml) runs the end-to-end tests on Linux, macOS and Windows for every release candidate (the Release workflow calls it, and publishes the release candidate only once they pass), and for a pull request, but not a maintainer's (`MAINTAINERS` in `scripts/ci-scope.ts`, whose changes the release candidate's run tests), never for a push to `main`. On a pull request, the tests on Windows, the packaged app and the end-to-end tests run only when it touches a file they depend on (`scripts/ci-scope.ts`, whose `IGNORES` list for each what it does not depend on); a push to `main` runs the first two. When any of the three comes to read, import or ship a file on its list, take the file off the list in the same commit. Each workflow's last check (`CI passed`, `End-to-end passed`) stands for all its jobs. Releases are made only by the Release workflow ([`.github/workflows/release.yml`](.github/workflows/release.yml)), run by hand, a release only once its newest release candidate is out: see the developer guide, "Releasing". Never make a release or a version tag any other way.

## Where things are

- `src/shared/`: code shared by server and client. `types.ts` (all shared types, `PROVIDERS`), `mentions.ts` (the `@mention` rule, and `unknownMentions`), `links.ts` (where a bare URL ends, also before Chinese text written right after it), `ask.ts` (`[ASK_USER]`), `media.ts`, `schedule.ts` (a schedule's next times), `tracking.ts` (a tracked goal: a reply's `<progress>` block, its notes, the waits before a retry), `notify.ts` (when the user is told that agents finished or need them, and what the notification says), `search.ts`, `family.ts` (families of branched conversations: each one's parent and top, for the sidebar's tree and for moving a family between groups as one), `review.ts` (lead review's shared parts: the words a review quotes found as the chat shows them, where a review starts reading, what a review says for search), `share.ts` (a shared page's placeholder links to the files that go along, in their own gist), `diff.ts` (the note that ends a diff the server cut short: written by `diffText()`, told apart by the diff dialog), `scheduleProposal.ts` (a schedule a member proposes in its reply: its `<schedule>` block taken out, read, hidden while it streams, made in the user's time zone), `cliVersions.ts` (the version each agent CLI was last checked with: Settings installs the open agents' from it, the user guide lists the same, `scripts/cli-check.ts` compares it with what was released; and the oldest one Harness Relay starts, `MIN_VERSIONS`, the oldest with every subcommand it is started with).
- `src/server/app.ts`: routes, security middleware, SSE (`createApp()`, testable with `app.request()`).
- `src/server/orchestrator.ts`: team runs: speakers by mode, prompt delivery, streaming into messages, auto team, the message queue, steering (with a conversation's `steer` on, a message sent while members work goes into their running turns where their CLI can take one, `STEER_PROVIDERS`, `RunOptions.onSteer`; else it queues: `steerOrQueue()`), pausing for the user's answer, retry and resend, and the lead agent's review once the team has answered (the lead agent's turns asking Claude Code and Codex for their JSON shape, `RunOptions.outputSchema`, the text parsers kept as the fallback).
- `src/server/prompt.ts` and `planner.ts`: agent briefings and turn prompts; the auto-team lead agent's prompt and reply parsing; `roleGuides.ts`: how each model family takes a role best (from its makers' own prompting guides), which the lead's prompts give it, only for the families its CLIs can run, where it writes roles. `reviewer.ts`: lead review, the lead agent reviewing the team's replies once it has answered (what it reads, its prompt, its answer checked; `src/shared/review.ts` finds the words it quotes, for the server and the chat, which marks them, `src/web/review.ts`). `approvalReview.ts`: "Approve for me", the permission level the UI shows between Edit and Full access, which is Edit with `approvals: 'auto'` (`permissionLevel()`, `levelSettings()`, `approvalsOf()` in `src/shared/types.ts`): the lead agent reviewing each approval request, read-only and told to use no tools, before the user is asked (its prompt, its answer, what it never reviews: pushing and publishing, more access for the turn, a request that does not say what it would do); the orchestrator's `startReview()` and `reviewApproval()` run it in `requestApproval`.
- `src/server/checks.ts`: team checks (`ConversationSettings.checks`): the rules Harness Relay checks itself once the team has answered, whichever CLI each member runs on (protected paths compared on disk, ignored files too: `takeManifest()`; the commits a run made: `commitsSince()` in `workspace.ts`; a subject matched in a `node:vm` context with a time limit; the apps a run made opening in the preview: `appProblems()` in `previewTarget.ts`, the orchestrator's `previewOutcome()`), `RunCheck` for one run (its baseline before the first turn, who changed what after each turn, its result once the team has answered; a failing result's baseline carried into the next run), `recheck()`; `src/server/checkCommands.ts`: its commands (`runCheckCommand()`: a fixed shell script reading the command line from the environment, an environment of its own, below full access in Harness Relay's own sandbox with no network and only the openings the user turned on for that command, every local port on macOS or every Unix socket on Linux; `sandboxDenial()` reads the sandbox's refusals from the output, which make a check could not run, never failed); the orchestrator's `startChecks()`, `finishChecks()`, `recheckChecks()` (commands in the background), `tryCheckCommand()`, `checkBeforeApply()` (a parallel result checked before it is applied, in a check tree with the installed dependencies linked in: `linkDependencies()`; held back when it does not pass, until applied anyway), `skipChecks()` and `fixChecks()` (and `startAutoFix()`, the same fix sent by itself at a run's end, `CheckList.autoFix`, at most `CHECK_LIMITS.autoFixes` in a row), the result in the next turn's prompt (`renderChecks()` in `prompt.ts`) and the queue held while it fails (`checksHold()`). `src/shared/checks.ts`: the patterns and where a conversation's latest result stands; `src/web/checks.ts`: the editor's and the card's logic (`components/ChecksEditor.tsx`, `components/ChecksCard.tsx`).
- `src/server/push.ts`, `alerts.ts`: push notifications (Web Push: browsers' subscriptions, removed with their signed-in browser; VAPID keys, kept in the database, never in the OS keyring, whose unlock prompt a service cannot answer; encryption and signing with `node:crypto`; only to `PUSH_HOSTS`), and the watcher that sends them when agents finish or need the user, holding them while the browser's page is in front.
- `src/server/inbox.ts`: the notification inbox (the sidebar's bell): every alert the team gives, by the rule push follows (`AlertTracker`), kept in the database whether or not a browser is open (`notifications`, `Store.addNotification()`; the newest 200, removed with their conversation), the same for every signed-in browser.

- `src/server/memory.ts`: long-term memory (`LongTermMemory`, `orchestrator.memory`), off by default (`MemorySettings.enabled`): notes agents save with `<remember>` / `<forget>` blocks in their replies (parsed in `src/shared/memory.ts`, taken out by the orchestrator's `takeMemory()` into a `memory` part), one row each in `memories`; the pinned notes in every briefing (`longTermSection()` in `prompt.ts`), the others recalled by matching words in the turn prompt once per session (their ids in `seen` as `memory:<id>`); nothing an agent does deletes a note, and the user's own notes change only when they say; the lead agent tidying the notes in the background (`buildTidyPrompt()`, `applyTidy()`). Settings → Labs → Long-term memory (`components/LongTermMemory.tsx`, in `LabsCard`; `src/web/memory.ts`), `/api/memory…` ([Architecture → Long-term memory](docs/architecture.md#long-term-memory)).
- `src/server/handoffs.ts`, `src/server/fixedCommands.ts`, `src/shared/handoffs.ts`: secrets and fixed commands ([Architecture → Secrets and fixed commands](docs/architecture.md#secrets-and-fixed-commands)): the reply blocks (`<secret>`, `<command>`, `<command-run>`: `splitHandoffs()`, pure) taken out of a finished reply into cards that wait for the user (`takeHandoffs()` in the orchestrator); ## Rules

### Code

- Strict TypeScript, ES modules. Shared types live only in `src/shared/types.ts`.
- Prettier formats the code (`npm run format`, before you commit; CI checks it). Leave `.prettierrc.json` as it is: a change there reformats the whole repository, so it is a commit of its own, with nothing else in it. Markdown is not formatted: keep the docs' tables and line breaks as they are.
- Spawn child processes only through `src/server/process.ts`, so they are tracked and killed on shutdown; a quick probe the server waits for (`lsof`, `ps`, `chflags`) goes through its `runSync()`, which kills it after its timeout. The relay sandbox's host (`relaySandboxHost.ts`) is a program of its own and starts the agent itself. Start programs directly, never through a shell; a shell script (`runShellScript()`, or `sh -c` given to `spawnDetached()`) is fixed text, and the values it needs (paths, names, settings) go in its environment, never in its text or its arguments. A program that gives what it runs an environment of its own (`sudo`, `pkexec`) runs `env NAME=value … /bin/sh -c <fixed text>`, the values Harness Relay's own (`sandboxSetup.ts`). On Windows a CLI found as a `.cmd` (npm's shims, Cursor's and Muse Code's launchers) is started as the program it runs (`src/server/winLaunch.ts`), never through `cmd.exe`.
- Keep CLI output parsers pure (lines in, `AgentEvent`s out) so they can be tested with recorded output.
- Tests run in a Node environment without a DOM. Put client logic you want to test in plain modules (like `src/web/chat.ts` and `src/web/copy.ts`), not inside components.
- `node:sqlite` cannot bind `undefined`: pass optional values through `nul()`, and wrap multi-statement writes in `transaction(db, fn)` (it doesn't nest).

### Security

The server can start agents with write access, so keep its defences intact (see [Architecture → Security](docs/architecture.md#security)):

- New routes go under `/api/` so they get the middleware's Host/Origin checks, the JSON content-type check on writes, sign-in and the request language. Don't weaken these checks. Only a read-only route the browser loads by itself (an `<img>`, a download link) may join `BROWSER_LOADS` in `app.ts`, which takes the cookie without the key.
- Never send secrets to the client (`SettingsView` returns masked keys only). API keys belong in the OS credential store (`secrets.ts`), never in the database as they are: without a credential store they go to the database encrypted, under the key in `secrets.key` (`openSecretStore()`), through the same `SecretStore`.
- Escape or encode a value for the place it goes, all of it, with what is made for that place: never with `replace()` given a string, which changes the first match only (CodeQL's "Incomplete string escaping or encoding", `js/incomplete-sanitization`, which fails a pull request's CodeQL check; #115 had one). A URL's path segment or query value goes through `encodeURIComponent()` (or `URLSearchParams`), each segment on its own, never a whole path at once (`npmName()` and `githubRepo()` in `scripts/cli-check/versions.ts`); text put in a regular expression through a `g` expression over every special character (`s.replace(/[.*+?^${}()|[\]\\]/g, '\\$&')`, as `escapeRegExp` in `src/shared/search.ts`); a quoted string written by hand (IMAP's) with the escape character itself in the same `g` expression (`/[\\"]/g` in `src/server/connectors/imap.ts`), so that a backslash cannot undo the quote; HTML through React, never by hand; a program's values never through a shell at all (see Code). A `replace()` with a string is for changing one known part of a fixed text (a word in a message, a date's `T`), never for making a value safe.
- The server binds to `127.0.0.1`. Agent replies cannot make the browser load remote content (images are links; local media goes through the media endpoint's path checks). Keep it that way.
- An open agent's process starts only through `startOpenProcess()` (`src/server/agents/open.ts`): below full access it runs in the relay sandbox, which fails closed. Never run one around it. Model keys go to the CLI in environment variables (only the run's own backend's), never into the config files its adapter writes; everything a run writes goes in the conversation member's own state folder (`home(root, state)`, `<home>/private/<key>`); the files that decide what the CLI does when it starts are its `configPaths`, read-only in the sandbox. A sandbox opening (`localPorts`, `connectPorts`, `allowPty`, `allowUnixSocketsInTmp`, `allowTlsTrustd`, `quietlyDeniedHosts`) is asked for by one adapter for its own CLI only, and documented in `docs/open-agents.md` and `docs/sandboxing.md`.
- Harness Relay's own tools (`src/server/gateway.ts`) reach the server only over the gateway's socket, with a token made for one turn and kept in a file under `data/tmp`, or over its loopback HTTP endpoint (`GATEWAY_OVER_HTTP`), with the token only in the CLI's memory (given over its stdin, in its session's MCP servers), never through the HTTP API, an environment value or a command line. A CLI joins `GATEWAY_OVER_HTTP` only once `scripts/mcp-headers-check.ts` shows that it writes an MCP server's headers to no file. Their credentials stay in the server. Calls that reach other people and proposed Google Docs or Obsidian note writes (tier `send`) wait in the outbox (`src/server/outbox.ts`). Only the user's explicit confirmation (`POST /api/conversations/:id/outbox/:itemId`) sends the message or writes the approved text. What a tool returns from elsewhere (a page, a mail) is given to agents as data, never instructions.
- A secret the user gives on an agent's card (`src/server/handoffs.ts`) is kept only through `SecretStore` and goes only to the fixed commands that name it: in a file of their run's own folder in Harness Relay's own sandbox (`RELAY_SECRETS_FILE`, `src/server/fixedCommands.ts`), never into a message, the database as it is, the UI, an agent's environment, a command line or a log; a fixed command's output is masked (`maskValues()`) before it goes anywhere. A fixed command runs only in Harness Relay's own sandbox, whatever the conversation's permission, reaching only its own hosts, and only while its pin holds (the code in its folder as the user saved or approved it); never run one around `runFixedCommand()`, nor let an agent's block run one without the user's click. Keep the relay sandbox's run folders in the other CLIs' protected reads (`agentProtectedReads()`).
- An interactive command (`src/server/interactive.ts`) starts only on the user's click on its card, never from an agent or an automation's run, through the fixed shell script with the command line in the environment, an environment of `checkEnv()`'s kept variables without `CI` (never the server's), in an empty folder of its own unless the user picks the working directory; what is typed hidden and the folder's secrets are masked in its output, which reaches the agents only when the user sends it. A browser handed to the user (`browser_hand_over`, `src/server/browser/handover.ts`) keeps every launch argument and rule of the chat's browser but `--headless=new`, and gives the agent only how it ended. Files panel writes (`src/server/fileEdit.ts`) go only into a conversation's working directories where edit mode is allowed, never through a link, never while a run writes in that folder.
- `run_code` (`src/server/runCode.ts`, only while Settings → Labs has one of its modes on) runs an agent's code only in Harness Relay's own sandbox (`sandboxedRunner()`), in every permission, full access included: read-only, no host allowed and none asked about, no opening, an environment of the server's locale and time zone only, and no run where that sandbox cannot start. Its runner reaches the server only over its own stdin and stdout, never with a token, and its calls go only through the `GatewayScope` it is given, so each is decided by its tier as the turn's own call would be, and never reaches `run_code` itself or another `scoped` tool. Never give it a token, the network, a writable working directory or the server's environment, nor let it call a tool around `ToolGateway.call()`. In RLM mode its `llm_query()` questions come over the same stdio and the server asks the sub-model itself (`llmQuery.ts`): a plain completion with no tools, sent only to its model connection's own host through `pinnedSend()` with no redirect, the key never leaving the server, within `RLM_LIMITS`; or, through a CLI (`cli:<provider>[:<account>][/<model>]`), a turn of Claude Code, Copilot or Muse Code only (`SUB_MODEL_CLIS`) with `RunOptions.toolless`, read-only, in an empty folder of its own (`cliSubModel.ts`); never let the sub-model take tools or `run_code`, and add a CLI to `SUB_MODEL_CLIS` only once its toolless run was seen to offer the model no tool at all (`scripts/cli-check.ts`'s `toolless` scenario).
- The browser tools' Chromium (`src/server/browser/session.ts`) connects only through its own proxy (`proxy.ts`), which checks the address each connection goes to: never start it without `--proxy-server` and `--proxy-bypass-list=<-loopback>`, nor let anything it loads reach the network another way. Its page scripts run in an isolated world, and its environment is `launchEnv()`'s (`browserEnv()`'s, and on Linux its config and cache folders in its profile, where its crash reports go), never the server's, nor may it write in the user's own browsers' folders.
- Harness Relay's own git commands (`git()` in `src/server/workspace.ts`) run outside any sandbox, in repositories agents can write: every one runs with `CONFIG` (hooks, fsmonitor, rerere, gc and maintenance off), every one but the plumbing over objects and refs alone (`needsDriverGuards()`) with the repository's drivers emptied first (`repoDriverGuards()`), and every one that writes into the git folder refuses one where what it writes into is a link, or whose git folder it cannot tell without blocking (`refuseGitDirLinks()`, `gitDirLink()`). A worktree's turn is committed with plumbing, never `git commit`, and only in a worktree of the repository's own (`refuseForeignWorktree()`). Read a file an agent can replace (a `.git` file, `commondir`, the index) only as `regularFile()` does: without following a link, without waiting on a pipe. Add a command to that plumbing only once nothing a repository holds can make it run a driver or read the working tree (`write-tree` cannot be: it runs a clean filter), and test each of these in `test/workspace.test.ts`.
- Two routes take something else instead of a browser's sign-in. A schedule's webhook (`POST /api/hooks/:id`) takes its own token: keep it hashed (`schedules.hook_hash`, compared in constant time) and its body an `<event>` block of data. The OAuth callback (`POST /api/oauth/callback`, in `OPEN` in `app.ts`) takes a sign-in's state (an account's, or a library MCP server's own), since the provider's redirect brings no key and, in the desktop app, comes to the system browser: keep the state random, made for one sign-in a signed-in browser started, good once and for minutes, compared as a hash, with the PKCE verifier kept in the server, and its answer to how that sign-in went.
- Accounts that sign in with OAuth keep their refresh tokens in the credential store and their access tokens in memory, and neither ever goes to the UI or to a CLI. A token goes only to its provider's hosts and never follows a redirect (`hostOnlyFetch()` in `src/server/oauth/broker.ts`); a provider's description names those hosts, and a calendar added through an account must be on them. A token for mail goes only to the provider's own IMAP and SMTP servers as its description names them (`mailLogin()`), never to servers saved with the mail account (which cannot be changed: 409), over TLS or STARTTLS (plain TCP only to a stand-in on this computer). A library MCP server's own sign-in (`src/server/oauth/mcp.ts`) keeps its refresh token in the credential store and its access token in memory, never shows either to the UI, and gives the access token to a CLI only in that server's headers, for one turn, for the host it signed in at over https (plain http to this computer only); its discovery, registration, token and revocation requests go over https (plain http to this computer only for a server that is itself there), read little and follow no redirect, and for a server elsewhere only to addresses on the internet, checked and pinned (`src/server/oauth/net.ts`); a redirect's `iss` that is not the sign-in's issuer is refused (RFC 9207), and a sign-in page or token endpoint off the issuer's origin opens only once the user confirmed it.

### Database

- To change the schema, append a new SQL string to `MIGRATIONS` in `src/server/db.ts`. Never edit a migration that has been released.
- Update the row types and queries in `store.ts` / `settings.ts`, and the tests in `test/store.test.ts`.

### Prompts and languages

- Prompts to agents (briefings, turn prompts, the planner prompt) stay in English; agents answer in the user's language.
- Every user-facing string exists in Traditional Chinese (`zh-TW`) and English (`en`):
  - **UI**: add the key to `src/web/locales/zh-TW.ts` first (it defines the `Messages` shape), then to `en.ts`. `test/i18n.test.ts` checks that both have the same shape.
  - **Server**: add both translations in `src/server/i18n.ts` and call `t()` where the text is produced. Don't cache translated text in long-lived objects; the language follows the request.
  - **Built-in templates**: `src/server/presets.ts`, in both languages.

### Documentation

- Docs come in pairs: `README.md` / `README.zh-TW.md`, `CONTRIBUTING.md` / `CONTRIBUTING.zh-TW.md`, `CODE_OF_CONDUCT.md` / `CODE_OF_CONDUCT.zh-TW.md`, `SECURITY.md` / `SECURITY.zh-TW.md`, `docs/<name>.md` / `docs/<name>.zh-TW.md`, and the READMEs of `e2e/` and `desktop/` (`README.md` / `README.zh-TW.md` in each). When a change affects behaviour, the HTTP API, the schema, settings, environment variables or the test list, update both languages in the same commit.
- The README is a short overview: each section sums up its topic in a few lines and links to the doc that has the details (the user guide, architecture, sandboxing, the developer guide…). Put the details in those docs, never only in the README; a new feature gets at most a line in its features list, with a link.
- The developer guide lists the HTTP API and what each test file covers; keep those lists current.
- `e2e/README.md` lists every end-to-end scenario. Whenever you add, change or remove an end-to-end test (a spec, a test in it, what it checks, or where it is skipped), update `e2e/README.md` and `e2e/README.zh-TW.md` in the same commit: the area's table, the test counts, "Each CLI at a glance", "Platforms and browsers" and "What they do not cover".
- `desktop/README.md` is the desktop app's page for developers. When its files, commands or checks change, update it and `desktop/README.zh-TW.md` in the same commit.
- `CONTRIBUTING.md` restates the rules in this file for people. When you change a rule here that applies to everyone, change it there too, in both languages.

### Tests

- Add or update tests with every behaviour change.
- Keep tests offline: no real CLI runs, no network, no real credential store. Follow the existing patterns: a fake runner swapped into `runners` (`test/orchestrator-harness.ts`), recorded CLI messages for adapters, real temporary git repositories for `workspace.ts`, `app.request()` for the HTTP API, and a fake keyring passed to `SettingsStore`. End-to-end tests use the fake CLIs (`e2e/fake-cli/`): something new an agent should do there is a new `e2e:` directive in the fake, not a real CLI. Every change to their scenarios goes into `e2e/README.md` and `e2e/README.zh-TW.md` too (see Documentation).
- When Harness Relay comes to start a CLI with a subcommand (or a flag that decides how it runs) its minimum version does not have (`MIN_VERSIONS` in `src/shared/cliVersions.ts`), raise the minimum to the first version that has it, in the same commit, with the user guide's line in both languages: an older CLI started without a terminal takes the subcommand for a prompt.
- Move a CLI's checked version forward (`src/shared/cliVersions.ts`) only once `npx tsx scripts/cli-check.ts <cli> --bin <the new one>` found nothing left to fix and its live tests ran, in one commit with the new version's shapes (`--accept`), the user guide's line in both languages, and, once they were tried again with it, the other docs that say which version a behaviour was seen with (`docs/open-agents.md`'s sections, `docs/sandboxing.md`'s "What was tested", the landing page in `site/`).
- Keep tests passing on Windows too (CI runs them there): paths built with `join()` / `resolve()`, not POSIX literals; what only macOS or Linux have (permission bits, signals, `/bin/sh`, stand-in CLIs started by their `#!` line) skipped with `skipIf(process.platform === 'win32')`; time limits from `test/timeouts.ts`. See the developer guide, "Testing".
- Keep the end-to-end tests fast: every test starts a server, a browser and agents of its own, so a second more in each adds minutes to every run. A test server has Claude Code alone installed (`DEFAULT_CLIS`): install another CLI only for the tests that use it (`withClis()`, `eachCli()`), as each one installed is probed whenever a page opens; give a test that needs more time its own limit (`test.setTimeout()`, `TURN_MS` for what a turn shows) rather than leaving it near the default. On CI, `scripts/e2e-budget.ts` warns after each job of the tests that passed past 70% of their limit, on every system, and the workflow's last check adds up each system's whole suite (both halves) against its budget (`BUDGET_MINUTES`): over it, or when Linux's could not be counted, the check fails on Linux. Raise the budget only in a commit that says why. The per-turn git processes are counted in `test/workspace.test.ts`: a new git command in a turn's snapshot or what follows it needs a reason worth its half second on Windows.

### Worktrees

- If you work in a separate git worktree, put it inside this repository, in your own CLI's folder at the root: Claude Code in `.claude/worktrees/<name>`, Codex in `.codex/worktrees/<name>`, Grok in `.grok/worktrees/<name>`. Any other agent uses `.<agent>/worktrees/<name>` the same way. For example: `git worktree add .codex/worktrees/fix-links -b fix-links`.
- Don't create worktrees next to the repository (such as `../harness-relay-<branch>`) or anywhere else outside it. Remove one with `git worktree remove` when you are done.
- `.gitignore` ignores these folders. If you add a folder for another agent, add it to `.gitignore` in the same commit.
- A new worktree has no `node_modules/`; run `npm install` in it before the commands above.
- These are your own worktrees for changing this code. They are separate from the worktrees the app makes for parallel mode under `data/`.

### Commits

- Write commit messages in English. The subject is an imperative sentence about what the user gets, for example `Let agents ask the user before answering, and wait for the answer`.
- In the body, use short bullet points, grouped under headings when a commit spans several areas: what changed and why, any schema version bump, and which docs and locales were updated.

## Gotchas

- `npm run dev` restarts the server on every server file change, and a restart aborts any running agent turn.
- One server per data folder (`data/server.lock`, `lockDataDir()` in `src/server/db.ts`): a second one on the same folder (`npm run dev` beside an `npm start` of the same checkout, say) refuses to start. Give it another with `RELAY_DATA_DIR`.
- The relay sandbox puts its sockets in the data folder (`data/srt/`), so the data folder's path must be short: at most 70 bytes on macOS, 61 on Linux, or the open agents refuse to run below full access. A worktree's `data/` (under `.claude/worktrees/<name>/` or `.codex/worktrees/<name>/`) is usually too deep: set `RELAY_DATA_DIR` to a shorter folder there. The gateway's socket (`data/gateway/relay.sock`) copes with a deep one: past 84 bytes on macOS, 88 on Linux, it is listened on from the server's working folder, and the gateway refuses to start (its log says so) only when that is too long as well.
- Harness Relay refuses edit mode in a working directory that holds itself (`src/server/protect.ts`). To work on this repository with Harness Relay, run the copy you use from another checkout.
- `desktop/` has its own `package.json` and lockfile, so a root `npm install` never downloads Electron. Its pure modules are tested from the root `test/` (`desktop-*.test.ts`); keep `electron` imports in `desktop/src/main.ts` only.
- `npm run desktop:dist` refuses to start while a Harness Relay runs from `desktop/release/` (it would replace the files under it): quit it first, or build with `-- --output <folder>`. Opening a new build while another Harness Relay runs only brings the running one forward.
- The desktop app's Electron may not run as Node (its fuses), so Harness Relay's own sandbox host runs there on the Node.js 22.12 or later on the login shell's `PATH` (`hostNode()` in `relaySandbox.ts`); without one, the open agents work only with full access. A file the server runs or hands to a CLI apart from `server.mjs` (like `relaySandboxHost.mjs` and `piGate.js`) must be written next to it by `desktop/scripts/build.ts`, and checked by `desktop/scripts/smoke.ts` and `check-package.ts`.
- electron-builder leaves out a `node_modules` folder at the top of an `extraResources` folder, so the keyring module the server needs is listed as an entry of its own in `desktop/electron-builder.yml`.
- The desktop app passes the server its own environment (`desktop/src/env.ts`): `PORT` and `HOST` from the user's shell are ignored, and `RELAY_WEB_DIR` points at the app's copy of the UI.
- You can run Harness Relay from inside a Claude Code session: the server strips Claude Code's nesting variables (`CLAUDECODE`, `CLAUDE_CODE_*`) before it spawns `claude` (`src/server/settings.ts`).
- The Vite proxy key is `/api/` with a trailing slash on purpose: a bare `/api` would also capture the client module `/api.ts`.
- Worktrees in parallel mode contain only what is in the snapshot, so ignored files such as `node_modules/` are missing there.
- Kept snapshot refs live under `refs/harness-relay/…`, and parallel-mode branches under `relay/*`. They belong to the app; don't delete them by hand while it runs.
